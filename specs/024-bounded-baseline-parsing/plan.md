# 024 实施计划

## 分期

**阶段 0（前置，不写实现代码）** —— 拧旋钮拿数。`sync_chunk_size` 两档对照 + 分段峰值
RSS。这一步的产出直接决定后面还做不做，见 ADR-042 §12。

**阶段 1** —— 遍历式分批与 mem 批容器：FR-1、FR-2、FR-3、FR-4、FR-5。此时补链仍沿用今天
的全量路径产物（即阶段 1 结束时基线仍需要一次全量拓扑），先把批的骨架跑通。

**阶段 2** —— 索引对账取代整文件解析：FR-6。做完这一步 `read_full_basic_data` 才从基线
路径上摘掉，NFR-1 才真正成立。

**阶段 3** —— 幽灵收口与失败语义：FR-7、FR-8，以及全部验收。

阶段 1 与阶段 2 的顺序不可换：先证明分批骨架能跑通并逐表等价，再动 issue #10 那块死角。

## 关键风险

**R1：本方案可能省不下多少。** 第 5 条让拓扑全程常驻，属性层本来就有旋钮，所以整套改造
**实际只省掉「整份文件字节」这一项**。阶段 0 就是为了在动手前把这个量测出来。若它不是
大头，正确的结论是关掉本 spec，只改 `sync_chunk_size` 的默认值。

> **R1 实测结论（2026-08-22，阶段 0 / T03，已排除）** —— 留证见
> `gen-model-parallel-gen/docs/evidence/2026-08-22-baseline-parse-memory-breakdown.md`。
>
> 库 `ams7351_0001`（dbnum=7351，3 345 855 refno，磁盘 1180.9 MiB）。**解析段峰值三轮实测
> 1709.2 / 1708.8 / 1709.1 MB，两档之间极差 0.4 MB（0.023%），纹丝不动** ——
> ADR-042 §12 的退化分支不触发，**大头在 `DbBasicData`，阶段 1–3 继续做**。
>
> 今天峰值 1904 MB 的四层拆分：底噪 51 / **整份文件字节 1181（62%）** / 拓扑 319（17%）/
> 属性层 353（19%，chunk=10_0000 在飞一批）。文件字节那一项是实测的：RSS 单步跃迁
> +1181.4 MB，与磁盘文件 1180.9 MiB 差 0.5 MB。**R1 担心的「整份文件字节不是大头」不成立
> ——它是四层里最大的一块。** 024 做完服务侧峰值 ≈ 723 MB，省 ~1181 MB（62%）。
>
> 三条随之固定下来的口径：
>
> 1. **`sync_chunk_size` 默认值仍值得单独改，但它不是本 spec 的替代品。** 10_0000 → 5000
>    买到 1904.2 → 1722.6 = 181.6 MB（9.5%），一行配置、零风险、与本 spec 正交，不必等。
>    两者省的是不同的层。
> 2. **阶段 2 砍不得**（与 T15「做完这一步 NFR-1 才成立」一致）。1181 MB 全部来自把
>    `read_full_basic_data` 从基线路径上摘掉；**只做阶段 1 的话一分不省**，动的只是属性层
>    那 353 MB，而那一层本来就有旋钮。
> 3. **R4 的 journal 与 FR-3 的批上限按实测单价标定：** KV 侧关系行 3.03 KB/元素、PE 行
>    1.42 KB/行，合 ~4.4 KB/元素，**一批 10 万元素的 `mem://` 容器约 440 MB**。同一轮里
>    KV 峰值 8.5–11.7 GB，是服务自己 1.7–1.9 GB 的 5–7 倍：本 spec 把服务侧压下 62%，
>    机器总占用只降约 9%。「内存有界」要在机器层面成立，上限口径必须同时管住 `mem://`
>    批容器。

**R2：动的是 issue #10 已修好的死角。** 补链轮 + `member_prune` 这一对修的是「已删子树整
棵复活」，现象是「增量检测得到、树上永远看不见」，现场排查成本极高。FR-6 与 FR-7 都在
重写它。缓解：权威口径（元素自己那条记录的成员块）一个字不改，只换取数来源；并保留
issue #10 的现有回归用例作为不变的钉子。

**R3：随机 I/O 换顺序 I/O。** 按需分页把「一次顺序读全文件」换成「按记录随机 seek」。
PDMS 项目目录常在网络盘上，这个差异不是百分比级的。缓解：批内把 refno 按 `(pgno, offset)`
排序后再读；`PagedDbSession` 已有页缓存与预取，逐项统计（`physical_pages_read` /
`cache_hits` / `prefetched_pages`）可用来判断预取是否生效。

**R4：journal 文本吃掉一部分省下的内存。** FR-5 选了 journal + 分块重放，每批多一份 SQL
文本常驻。缓解：`ResourceGauge` 把 mem 与 journal 分开计量，上限对两者分别设；若实测
journal 占比过高，退路是把批上限调小而不是改写回路径。

**R5：批未完成时持久库不得有该批任何一行。** 这条要求解析路径上现有的所有直写点都改成
写 mem。遗漏一处就破坏 FR-5，而且不会有任何用例变红。缓解：加一道源码形状门——基线解析
路径内不得直接调用持久层写入入口（照 023 `concurrency.rs` 的 `mod shape` 形状做）。

## 与既有决策的关系

- **ADR-021 §3 不动。** 本方案只用 `mem://` 实例与读路由，不开暂存窗口、不需要
  finalize plan。
- **ADR-025 不动。** 阶段划分（数据 → 模型 → 空间 → 房间）不变，本 spec 只在数据阶段内部
  分批。
- **ADR-038 复用。** 写回沿用 TX_CHUNK 分块与块指纹，不新立一套。
- **ADR-041 §5 是本方案的隐含前提。** 读路由的 fail-closed 纪律就是「生产端禁止回读本次
  产物」的执行机制；本轮不做生成，所以片内依赖闭包预载留到下一轮。
- **ADR-041 关于 ZONE 的表述被 ADR-042 §3 改写**：ZONE 从「内存分片单位」降为「遍历顺序
  与封批点的默认配置值」。

## 度量

阶段 0 与最终验收共用一套：五段（解析 / 生成 / 写回 / 空间树 / 房间）各自的壁钟与峰值
RSS。注意「各段之和 − 总时长」不能直接称作重叠——重叠与段外空档可以同时存在并互相抵消。
要区分二者，得记区间端点再求 union 与两两 intersection。
