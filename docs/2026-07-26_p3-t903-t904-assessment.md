## T903 · D3：`async_watch` 事件缓冲与串行处理

**结论：原判定「风险低」成立，且可以给出机制层面的理由，不只是靠水位兜底这一句。建议按「已评估、维持现状」关闭，只补一条注释说明为什么安全。**

### 现状

`AiosDBManager::async_watch`（`src/data_interface/increment_manager.rs:778`）用容量 1 的 mpsc
通道接 `PollWatcher`：

- 生产侧回调是 `futures::executor::block_on(async { let _ = tx.send(res).await; })`；
- 消费侧是 `while let Some(res) = rx.next().await` 的单循环，循环体里同步做补偿 drain、
  头部扫描、增量落库和模型重生成。

### 为什么不丢事件

三层机制叠加，任何一层单独成立都够：

1. **通道满时是阻塞，不是丢弃。** `Sender::send` 在容量耗尽时等待，所以不存在「通道把事件丢了」
   这条路径。代价是回调线程被卡住。
2. **PollWatcher 是快照差分，不是事件流。** 它每轮 `stat` 整棵被监控目录树，与上一轮快照比
   mtime / 新增 / 删除。回调被阻塞期间轮询停摆，但恢复后仍与**停摆前的那份快照**比对，因此
   这期间的所有改动会**合并成一次事件**上报，而不是消失。
3. **真正的工作量由水位而非事件决定。** 事件只是「去看一眼」的触发器；实际增量窗口由
   `SesnoRangeResolver` 按 `applied_sesno` 与文件最新 sesno 重新算。合并成一次事件后，
   算出的区间仍覆盖期间的全部会话。

所以串行处理的实际后果是**延迟**而非**丢失**：有效轮询间隔从 30s 退化为
「30s + 上一轮处理耗时」。冷启动时首轮处理可能很长，但那段时间本来也无法并发处理。

### 顺带记录的两个相邻缺口（不属 D3，未修）

- `increment_manager.rs:809` `watcher.watch(x).expect("文件监控设置失败")`：某个监控目录不可达
  （远程共享掉线）会直接 panic，而不是跳过该目录继续监听其余目录。
- `while let Some(res) = rx.next().await` 结束后 `async_watch` 静默返回 `Ok(())`，而
  `db_model.rs:79/156` 两处调用方是 `.unwrap()`；看门狗静默退出不会有任何告警。

## T904 · D4：`raw_dchc_code` 覆盖度

**结论：`raw_dchc_code` 的文档注释已经过时——它说的「需活 E3D 会话或字典导入才能补全」，
那个字典导入 ADR-008 已经做完了，产物就在仓库里。属性级 DCHC 码可以从当前的 2 个提升到 329 个
非零码，且完全离线。但这不等于 G10/P8 收工：导出的是**属性级**码，不是文档反复强调的
**per-(noun, attr)** 码表。**

### 证据

`output/noun_attr_fields.json`（4.7 MB，ADR-008 用 `scripts/e3d/NounLayoutExport.cs` 从 E3D
属性字典导出）为 4271 条属性记录各带 57 个 `DbAttributeField`，其中**就有 `DCHC`**：

```json
"836950": { "name": "NUMBDB", "f": { "DCHC": { "i": 0 }, "CASC": {}, "TYPE": {} } }
```

全表 DCHC 分布（按唯一属性名计，共 4270；原始记录 4271 条，有 1 组重名）：

| DCHC | 属性数 |
|---:|---:|
| 0 | 3941 |
| 1 | 7 |
| 2 | 4 |
| 3 | 3 |
| 4 | 315 |

抽样与现有效果分类高度自洽，说明这份导出可信且语义与我们的三态判定同源：

| 属性 | DCHC | `model_impact` 现有归类 |
|---|---:|---|
| `NAME` / `DESC` | 0 | DataOnly |
| `POS` / `ORI` | 3 | TransformOnly |
| `SPRE` / `CATR` / `PARA` / `DESP` | 4 | Regen / DependencyCascade |

注意 `REDRAW` 与 `INTUBE` **不在**这份导出里，与 ADR-002「只有 `UI_REDRAW` 串、`INTUBE` 连静态
串都没有」一致——它们是内核伪属性。因此现有两个 forced code 必须保留为特例，不能被导出覆盖。

### 与现有硬编码清单的交叉核对

拿 `attribute_affects_model` 的 227 个条目对字典 DCHC 做集合比对：

| 项 | 数量 |
|---|---:|
| 清单条目 | 227 |
| 其中能在字典里按名字找到 | 130 |
| 找不到（短名/伪属性） | 97 |
| 可比条目中 DCHC ≠ 0（吻合） | 111 / 130 ≈ 85% |
| 清单收了但 DCHC = 0 | 19 |
| DCHC ≠ 0 但清单没收 | 218（其中 213 个是 code 4） |

**这几个数字不能直接当结论用**，有三个必须先处理的口径问题：

1. **命名口径不一致。** 清单用 PDMS 短名，字典用全名。`DEPT` 落在「找不到」里，而 `DEPTH`
   落在「清单没收」里——同一个东西被两边各计一次，把两个差集都撑大了。要先有短名↔全名
   别名表，比对才有意义。
2. **`OWNER` / `CHILDREN` / `NOUN` / `TYPE` 本来就不是字典属性**，是元素元数据，永远查不到，
   属于正常缺席而非缺口。
3. **DCHC = 0 不等于「可以不重建」。** 那 19 个里 `HREF` / `TREF` / `FSPREF` / `SCREF` 都是引用
   属性，代码是按 `att_type == ELEMENT` 走 DependencyCascade 的，与设计变化码是两条正交的
   判据。删掉它们会真漏更新。

另外，218 个「清单没收」**不构成正确性缺口**：未命中清单的属性会落到 `Unknown`，采集层保守
触发重生成。这是精度与可观测性问题，不是漏更新问题。

### 建议的后续动作（按性价比排序，均未执行）

2. **补别名表**，把命名口径拉齐，让上面的数字收敛到真实差异。
3. **再决定要不要让 `raw_dchc_code` 读导出。** 若要，参照 `noun_flags.json` 的
   `include_str!` 内嵌方式，保留 REDRAW / INTUBE 特例，并明确标注「属性级近似，非

4. **G10 / P8 不变**：逐 `(noun, attr)` 码表仍需活 E3D 会话导出，本文的发现不能替代它。

# 追加：别名表尝试与三源交叉核对

> 2026-07-26 续。数据源三份：字典导出 `output/noun_attr_fields.json`（4270 属性名 + DCHC）、
> 运行库 schema `all_attr_info.json`（339 noun / 6554 个 (noun,attr) 对 / 701 个属性名）、
> dabacon noun 表 `noun_flags.json`（1931 noun）。

## 一、别名表结论：前缀匹配不可靠，只救得回 6 条

对 97 个「清单有、字典无」的名字做双向前缀匹配（`F.startswith(S)` 或 `S.startswith(F)`），
得到 17 条唯一匹配。但逐条抽查后**大部分是误匹配**：

- `POSI` → `POS` **错**。`POSI` 在运行库 schema 里是独立的 BOOL 属性（hash 722860），
  不是 `POS` 的缩写。
- `PXDI` → `PX`、`PYDI` → `PY`、`PZDI` → `PZ` **全错**。P-point 方向和顶点坐标是两回事。
- `EXTR` → `EXTREF`、`REVO` → `REV`、`PANE` → `PANESI` **错**。左边三个都是 noun 名，
  被前缀规则硬凑给了不相干的属性。

站得住的只有 6 条：

| 清单短名 | 字典全名 | DCHC |
|---|---|---:|
| `LEVEL` | `LEVE` | 4 |
| `SPREF` | `SPRE` | 4 |
| `GMREF` | `GMRE` | 4 |
| `THIC` | `THICKNESS` | 4 |
| `PARAM` | `PARA` | 4 |
| `DEPT` | `DEPTH` | 4 |

**教训：别名不能靠前缀猜。** 可靠判据是双向验证——源名在任何一份属性表里都不存在，
且目标名确实是属性。单纯的前缀包含会把 noun 名和同前缀属性硬配成对。

## 二、227 条清单的真实构成

| 类别 | 条数 | 说明 |
|---|---:|---|
| 字典里有，可比 DCHC | 130 | 其中 111 条 DCHC ≠ 0（吻合 85%），19 条 DCHC = 0 |
| 是运行库真实属性，但字典导出里没有 | 9 | `DETR` `LBOR` `NAPP` `OWNER` `POSI` `PSPREF` `PTCD` `TYPE` `UNIPAR` |
| **是 dabacon noun 名，不是属性名** | **40** | 见下 |
| 两者皆非 | 48 | 多为目录/设计参数短名与 P-point 参数 |

顺带量到字典导出本身的缺口：运行库 701 个属性名里有 **70 个不在** 4270 名的字典导出里，
所以那份导出不是全集，接它的时候要有「查不到就退回现有判定」的兜底。

## 三、发现一：40 条 noun 名是永远不会命中的死分支

这 40 条与 dabacon noun 表精确同名，且**在字典 4270 名和运行库 701 名里都不存在**；
反过来，清单里没有任何一条同时既是 noun 又是属性（交集为 0）：

```
ADIR AEXTR ATTA BRCO CMPF DDAT DDSE DEPT EXTR NREV NSEX NSRE NXTR PANE PLIN
POHE POIN POLOOP POLPTL POLYHE PORI PPOS PTAX PTCA PTMI PTPOS REVO SCOM
SCREED SCTN SDIS SEXT SLOO SPCO SPRO SPVE SREV STWALL SVER TMPL
```

它们不可能命中，理由是闭合的：

1. `normalize_attribute_name`（`model_impact.rs:129`）只做 trim、去 `att.` / `ATT.` 前缀、
   按 `.` 取首段、转大写——**没有缩写展开，也没有截断**，所以 `matches!` 是严格相等。
2. `attribute_affects_model` 全仓只被 `classify_attribute_effect`（`:152`）调用，
   而后者的输入来自 `collect_modified_attribute_names`，取的全是属性名。

**这不是正确性缺陷**：清单没收的属性会落到 `Unknown`，采集层保守触发重生成。但它说明
清单把 noun 和属性混在了一张表里，而真正该收的「这些几何 noun 自己的形状属性」很可能
压根没进清单——只是被 `Unknown` 兜住了，所以一直没暴露。

## 四、发现二：TRANSFORM_ONLY 有 7 条与字典分类不一致（需要复核）

`TRANSFORM_ONLY_ATTR_NAMES` 的 9 条全在字典里，但只有 2 条落在同一个码上：

| 属性 | 字典 DCHC | 我们的处理 |
|---|---:|---|
| `POS` `ORI` | 3 | TransformOnly → 只更新 world transform |
| `CPOS` `NPOS` `POSE` `POSL` `POSS` `YDIR` `ZDIR` | **4** | TransformOnly → 只更新 world transform |

后面 7 条拿到的是和 `SPRE` / `CATR` / `PARA` / `DESP` 同一个码 4，却走了「不重建 mesh」
的便宜路径。如果码 4 意味着需要重建几何，这就是一处**少算**——正好是整个 spec 想防的
「模型陈旧」方向，和别处「宁多勿漏」的取向相反。

**但先别急着改，DCHC 的语义还没证实**（已在第七节查清，结论见下）。 观察到一个很整齐的模式：

| DCHC | 命中属性 |
|---:|---|
| 1 | `HBOR` `HDIR` `HPOS` `HSTU`（全是 H 开头 = head 端） |
| 2 | `TBOR` `TDIR` `TPOS`（全是 T 开头 = tail 端） |
| 3 | `POS` `ORI` |
| 4 | 其余 315 条 |

H 端全 1、T 端全 2，说明 **DCHC 更像是「变化类别」枚举而不是严重度分级**；再加上逆向确认
的 forced code `INTUBE=1`（管件端连通性）、`REDRAW=4`（通用重画）也正好落在这个解释上。
若如此，码 4 只表示「通用变化类」，不能直接推出「必须重建几何」。

所以这一条的正确定性是：**一条值得查的线索，不是已确认的 bug。** 要坐实得先弄清 1/2/3/4
各自的语义，或者直接对 `POSL` / `YDIR` 这类属性做一次改动前后的实库对拍。

## 五、发现三：DATA_ONLY 清单是干净的

`DATA_ONLY_ATTR_NAMES` 唯一一份「直接跳过、不做任何事」的清单，3 条能对上字典的
（`NAME` / `DESC` / `PURP`）**全部 DCHC = 0**。这是这轮最让人安心的结果：唯一一处
「跳过」判定被一个完全独立的数据源确认，不存在假中性。

## 六、修正后的后续动作建议

1. **先查 DCHC 语义**（新增，优先级最高）：1/2/3/4 分别代表什么。这是发现二能否定性的前提，
   也决定了这份字典数据到底能不能驱动判定。可从 `attlib.dat` 的枚举定义或活 E3D 会话取。
2. **守护测试改口径**：不要钉「清单 vs 字典」的原始差集（含 40 条死分支和命名噪声），
   改钉三件确定的事——DATA_ONLY 全零、TRANSFORM_ONLY 的 2/7 分裂、40 条 noun 名的存在。
   任一漂移即失败。
3. **清理 40 条 noun 死分支**（零风险，但建议连同「补上这些 noun 的真实几何属性」一起做，
   否则只是把隐性缺口从「死分支」变成「没有分支」）。
4. 别名只落那 6 条确定的，不要引入前缀规则。
5. G10 / P8 不变：per-(noun, attr) 权威码仍需活 E3D 会话导出。
## 七、DCHC 语义已查清（本节结论优先于第四节的保留意见）

把码 1/2/3 的**成员全集**连同字典自带的描述列出来，语义就没有歧义了——这三类一共只有 14 条：

| DCHC | 属性 | 字典描述 |
|---:|---|---|
| 1 | `HBOR` `HDIR` `HPOS` `HSTU` `HZAXI` `LHEA` | Head bore / Head direction / Head position / Head tube specification / head Z axis / Logical head flag |
| 1 | `TZAXI` | tail Z axis ← **唯一的异类，落在 head 类里** |
| 2 | `LTAI` `TBOR` `TDIR` `TPOS` | Logical tail flag / Tail bore / Tail direction / Tail position |
| 3 | `BFORI` `ORI` `POS` | Bent Feature Orientation / Orientation / Position |
| 4 | 其余 315 条 | —— |

所以：

- **1 = 元件头端（head / arrive）连通性变化**
- **2 = 元件尾端（tail / leave）连通性变化**
- **3 = 元件自身刚体位姿**
- **4 = 通用兜底类（其余一切）**

逆向确认的两个 forced code 正好落在这个解释上：`INTUBE`（管件是否在管内，头尾连通概念）= 1，
`REDRAW`（通用重画）= 4。

**结论：DCHC 是「变化类别」枚举，不是严重度分级。** 第四节里「码 4 = 必须重建」的推断不成立。
`TZAXI` 落在 head 类是唯一说不通的地方，如实记下不做圆场。

### 但这反而让发现二更站得住，不是更弱

关键在于**内核专门给「纯位姿变化」留了一个类（3），而且只放了 3 条属性进去**。我们的
`TRANSFORM_ONLY_ATTR_NAMES` 却放了 9 条。把两边摊开看：

| | 我们的 TRANSFORM_ONLY | 内核位姿类（DCHC=3） |
|---|---|---|
| 交集 | `POS` `ORI` | `POS` `ORI` |
| 只有我们有 | `CPOS` `NPOS` `POSE` `POSL` `POSS` `YDIR` `ZDIR` | —— |
| 只有内核有 | —— | `BFORI` |

再看那 7 条的字典描述，问题就具体了：

| 属性 | 字典描述 | 为什么不像纯位姿 |
|---|---|---|
| `CPOS` | conditioning position for curve geometry | 描述里直接写了 **curve geometry** |
| `POSS` | Start point position | 线性元件的起点——改起点改的是**长度和形状** |
| `POSE` | End point position | 同上，改终点 |
| `POSL` | Positioning line | 定位线，不是元件自身位姿 |
| `NPOS` | Position in owner | 在 owner 内的位置 |
| `YDIR` | Preferred Y axis direction | 轴向偏好 |
| `ZDIR` | Additional axis direction | 附加轴向 |

`POSS` / `POSE` / `CPOS` 这三条最值得警惕：走 TransformOnly 意味着**只重算 world transform、
不重建 mesh**，而起点/终点变了以后 mesh 的长度本身就该变。这不再只是「和内核分类口径不一致」，
而是有具体机制的**少算**嫌疑。

反方向的 `BFORI`（内核算位姿类、我们没收）只是错失一次便宜路径——它会落到 `Unknown` 走全量
重建，慢但安全。

**定性：仍需一次实证再下最终结论**（改一个 `POSS` 或 `POSE` 看 mesh 是否陈旧），但优先级
应该从「可查的线索」提到「疑似漏更新，优先验证」。

### 属主 noun 反查：发现二基本坐实

把这 7 条属性挂在哪些 noun 上查出来（数据源 `all_attr_info.json` 的 339 noun schema，
括号内是 dabacon 几何 flag）：

| 属性 | 属主 noun |
|---|---|
| `POSS` `POSE` | `SCTN`、`STWALL` |
| `CPOS` | `CURVE`(geo) |
| `POSL` | `CMFI`(geo) `ENDATU`(geo) `FITT`(geo) `PLDATU`(geo) `SCOJ`(geo) `SJOI`(geo) `SEVE` |
| `YDIR` | `ENDATU`(geo) `PLDATU`(geo) `RPATH`(geo) `SPINE`(geo) |
| `ZDIR` | `CURVE`(geo) `SBFI`(geo) `SUBJ`(geo) |
| `NPOS` | `PNOD` |
| 对照：`POS` / `ORI` | 118 / 108 个 noun（真正的通用位姿属性） |

**`POSS` / `POSE` 只挂在 `SCTN` 和 `STWALL` 上**，而 `SCTN`（结构型材）的几何就是把目录截面
沿 `POSS`→`POSE` 这条线拉伸出来的。改起点或终点改的是型材的**长度和走向**，mesh 必须重建；
走 TransformOnly 只会把旧长度的 mesh 搬个位置。`CPOS` 挂在 `CURVE` 上、`YDIR` 挂在 `SPINE`
上也是同一回事——都是定义几何的参数，不是元件位姿。

再对照 `POS`/`ORI` 挂在 118/108 个 noun 上，是真正的通用位姿属性，这个反差很能说明问题。

`BFORI` 在这份 339 noun 的快照里没有任何属主，所以把它补进 TRANSFORM_ONLY 对当前项目没有
实际影响。

**三条独立证据现在指向同一结论**：内核把它们排除在位姿类之外、字典描述写的是几何、属主
noun 的几何本身就由它们定义。距离「已确认的 bug」只差一次实库对拍（改一根 `SCTN` 的 `POSE`
看 mesh 长度跟不跟），但已经足以把它当作疑似漏更新来排期，而不只是口径不一致。
### 第六节后续动作的修订

原第 1 条「先查 DCHC 语义」已完成，替换为：

1. **验证 `POSS` / `POSE` / `CPOS` 是否真的漏更新**（新的最高优先级）：挑一个用到这些属性的
   线性元件，改起点/终点后看几何是否跟着变。这是唯一还挡在结论前面的一步。
2. 守护测试口径再加一条：钉住「我们的 TRANSFORM_ONLY 与内核 DCHC=3 类的 2/7/1 三段分布」。
3. 其余各条不变。

# 已实施的改动（2026-07-26）

## `TRANSFORM_ONLY_ATTR_NAMES` 收窄为 `POS` / `ORI`

`src/data_interface/model_impact.rs:104`。移出 `POSL` `POSS` `POSE` `NPOS` `CPOS` `YDIR` `ZDIR`
七条，并把上面第七节的依据写进 doc 注释。

这七条本来就在 `attribute_affects_model` 清单里，而 `classify_attribute_effect` 的判定顺序是
DATA_ONLY → STRUCTURAL → **TRANSFORM_ONLY** → CASCADE → affects_model，所以移出后它们自动落
`DirectGeometry` 走完整重生成，不需要另外加分支。方向上回到项目自己的「宁多勿漏」，代价是
这几类属性变更从便宜路径转为重建。

`BFORI` 没有补进来。内核把它归在位姿类（码 3），但**往便宜路径里加属性是「少算」方向**，
在没有实证之前不做；何况它在当前 339 noun 的快照里没有任何属主，补了也没有实际作用。

验证：`cargo test --lib` **160 passed / 0 failed / 27 ignored**；`model_impact` 模块 25 项全过。
唯一直接相关的断言是遍历常量本身的循环（`model_impact.rs:812`），会随常量自动收敛；两处遍历
全部 noun 的守护测试用的都是 `POS`，不受影响。

**仍未做**：实库对拍（改一根 `SCTN` 的 `POSE` 看 mesh 长度是否跟随）。这一步做完才能把
「疑似漏更新」正式定性；在那之前，本次改动的定位是**按内核口径收窄到安全侧**，而不是
「已确认 bug 的修复」。

## 五张分类名单合并为一张 attr → effect 映射（`ATTRIBUTE_EFFECT_TABLES`）

分两个提交落地：`fa99ea9c`（守护测试先行）、`dfae60b8`（结构重构）。

### 动机：顺序即语义，重名即静默失效

旧 `classify_attribute_effect` 是 if-else 链逐张表试：DATA_ONLY → STRUCTURAL →
TRANSFORM_ONLY → CASCADE，都不中再落到 `attribute_affects_model` 的 `matches!` 大列表。
两个结构性问题：

1. **归类由位置决定**：一个属性写进两张表时谁先谁赢，语义被链的顺序绑架。上一节
   TRANSFORM_ONLY 收窄之所以「移出即自动落 DirectGeometry」，正是踩着这个顺序才成立——
   改动本身安全，但这条知识只存在于链的形状里，读代码看不见。
2. **重名静默失效**：`matches!` 大列表与前四张表有 73 条重名，短路之后永远走不到；
   错写、漏写、两边不一致都不报错。

### 设计

- 五张 `pub const` 数组保留（按效果分组声明、各带 doc 注释，分组本身就是文档）；
  原 `matches!` 大列表显式化为第五张 `DIRECT_GEOMETRY_ATTR_NAMES`，那 73 条重名在
  显式化时剔除、只保留在原先胜出的表里，归类不变。
- 新增唯一事实源 `ATTRIBUTE_EFFECT_TABLES: &[(&[&str], AttributeEffect)]` 把每张表与其
  效果配对，`attribute_effects()` 用 `OnceLock<HashMap>` 惰性合并成一张查找表。
- `classify_attribute_effect` = 查映射 → `PARA` 前缀回退（`PARA1`/`PARAM7` 这类序号
  变体不逐个登记）→ `Unknown`。`attribute_affects_model` 改为纯派生：
  `!(DataOnly | Unknown)`，不再自持第二份名单。
- 组间顺序不再携带语义；跨表重名从「静默按顺序仲裁」变成守护测试直接报错。

## 环境备注

本轮为了跑通测试，踩到三个与代码无关的环境问题，记下来省得下次再查：

- `CARGO_TARGET_DIR=D:\Rust\target` 是**多个会话共享**的。并发构建会互相把对方的产物判成陈旧
  删掉，表现为「cargo 刚生成的 build-script exe 转头就不见了」（os error 3）和无谓的全量重建。
- 全量重建时 `manifold-sys` 的 build script 需要 `LIBCLANG_PATH`（本机在 `D:\LLVM\bin`）。
- `occ` 是默认特性，测试二进制运行时需要 OCCT（`C:\tools\occt-7.8.0\bin`）**和**它的第三方
  依赖（`C:\tools\3rdparty-vc14-64\*\bin`，其中 `openvr_api.dll` 在 `bin\win64` 子目录）。
  `scripts/extract_3rdparty.ps1` 原本把这些平铺复制到 `D:\Rust\target\debug`，但那份拷贝会被
  上面的目录争用清掉——加进 PATH 比复制进 target 目录耐用。
