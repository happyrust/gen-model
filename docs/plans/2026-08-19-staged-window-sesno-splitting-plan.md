# 2026-08-19 方案：暂存窗口按 sesno 拆窗

关联：ADR-017（暂存窗口提交，2026-08-19 修订第 4 条留下的台账）、ADR-011（单数据队列）、
ADR-021（水位数据支撑）、ADR-022 / ADR-031（净窗口收集）、ADR-025（严格初始化相位）

状态：**已实施**（形态 C，同日落地；口径入 ADR-017「2026-08-19 修订（二）」）。
开放问题的落地答案：Q1 = 不预估、按固定会话数定窗（②），精度让给第二层；
Q2 = `epoch_id > 0` 一律不收窄，拆窗不碰相位链路；Q3 = 预算单位就是会话数
（`AIOS_STAGING_WINDOW_MAX_SESSIONS`），元素数标定不做；Q4 = 仍待业主签字。

## 要解决的是什么

phase-1 审计留下的那条：暂存资源三级状态机**没有出口**。`Abandon` 只在
`StagedExecutor::execute` 的语句入口 bail，冒泡上来是一条普通失败 → 窗口阻断 → DROP →
重算 → 同一个会话区间必然再次触顶。`absorb_extend` 只会把窗口变大，代码里搜不到任何
按 sesno 拆窗的机制。于是一段长时间离线攒下来的积压，唯一出路是调高
`AIOS_STAGING_ABANDON_BYTES`——把「不许 OOM」这条纪律往后挪，而不是让它过得去。

2026-08-19 的修订已经把这个状态记成了可执行的阻断（带测得数值与旋钮名），但那只是让人
看得懂，没让它自己走得通。

## 地基：水位本来就支持部分推进

不需要发明新的持久化概念。今天的事实是：

- `applied_sesno` 是唯一的完成真值（ADR-021），窗口的尾事务把它推到 `finalize.end_sesno`；
- 一个窗口提交的就是 `start..=end` 这一段，原子性由尾事务保证；
- `ActiveStagedWindow::align_end_sesno` 已经允许「实际应用范围比建窗时窄」——它本来就是
  为「冻结重扫看到的右端 > 解析出的应用窗口右端」准备的。

所以**拆窗 = 把一段积压跑成若干个更小的窗口，每个自己原子**。提交侧一行不用改。

## 必须守住的不变量

**绝不在一个 sesno 内部切开。** 一个 sesno 就是 E3D 里的一次 SAVEWORK，是用户视角的一次
原子保存。只在会话边界切，意味着读者能看见的每一个中间状态都对应源模型真实存在过的某个
保存点——不是半批。这是 ADR-017 §1 那条不变量能被合法削弱的唯一理由，也是要拿去和业主
对齐的那句话。

## 三个候选形态

### A. 触顶后减半重试（reactive）

跑窗口，撞 `Abandon` 就整窗口丢掉、上界减半重来。自调节、不需要任何预估模型。
代价：已经付出的解析与生成（分钟级）整个作废，而且最坏要作废 log₂n 次。

### B. 就地收窗（在生成中途停在会话边界）

跑到一半发现档位不对，就把窗口停在当前已完成的会话上、按那个右端提交。零浪费。
**但它跑不通**：净窗口收集（ADR-031）是拿 `root(start-1)` 与 `root(end)` 两棵 B+ 做净差分，
先定右端才有差分，不是逐会话累加的流程；而且生成阶段更不能中途停——已应用数据触及的根
必须全部生成完，否则提交的就是「新属性 + 旧模型」，正是 ADR-017 要挡的东西。

### C. 预算式定窗 + 触顶收窄兜底（推荐）

- **第一层**：开窗**之前**按预算定右端。预算单位候选见开放问题 Q3。
- **第二层**：万一还是触顶，不再只阻断，而是把上界收窄一档后自动重排（收窄次数有界，
  地板 = 1 个会话）。单个会话自己就超预算 → 才是真阻断：这时候「一次保存大过内存预算」
  是事实，答案只有调高上限或走应急直写，不该由拆窗假装解决。

推荐 C。A 是 C 的第二层，B 单独不成立但它的思路（会话边界）是 C 的地基。

## 落地形状

1. **`FrozenBatch` 加 `apply_upper_bound: Option<i32>`**（None = 用 `file_latest_sesno`）。
   两个来源：冻结点的预算定窗（第一层），或收窄重排（第二层）。
2. **`execute_one_dbnum` 同样加这个参数**，且**绝不通过篡改 `cand.file_latest_sesno` 实现**。
   那个字段喂给 `FileObservation` → `DbnumState::record_observation` 与身份异常分类；把它
   改小，水位表里「文件里最新是第几个会话」就成了假的，而且会话号回退这类异常会被顺手
   掩掉。上界只约束 `IncrementPipeline::collect_window` 的右端。
3. **提交侧不动**。尾事务已经按 finalize 的 `end_sesno` 推水位，`align_end_sesno` 已经容纳
   更窄的右端。
4. **余量重排**。截断窗口提交成功后，`applied_sesno < file_latest_sesno` 自然成立，下一轮
   重扫会重新发现它——但等重扫太慢。worker 应在本批收尾时立刻按 `k+1..=latest` 重新入队
   （同 dbnum 恒串行，队列语义不变）。
5. **回执与日志说清楚**：`DataBatchResult` 要能表达「本批只应用到 sesno k，余量 k+1..=latest
   已重新排队」，否则面板上看到的是一个「成功但水位没追平」的批次，没人分得清它是截断了
   还是漏了。
6. **`absorb_extend` 不得越过上界**：吸收扩窗只能在预算之内抬右端。

## 会被牵动的三处语义

- **原子单元变小**。从「整段积压」变成「预算内的若干次保存」。读者因此能看见子窗口之间的
  中间态——但每一个都对应真实保存点（见不变量那节）。**需要业主签字**。
- **同一个根可能被生成两次**。根 R 在 sesno 5 与 9 都被改，切成 `..=6` 与 `7..=` 之后 R 生成
  两遍。结果正确，代价是重复生成。预算越小越明显。
- **ADR-025 的相位记账**。截断批次不等于「这个 dbnum 的 Design 相位做完了」。
  `InitializationCoordinator` 的 phase totals 是按批次记的，截断会让它提前认为相位可以推进。
  这一处必须先看清楚再动（Q2）。

## 开放问题（编码之前必须有答案）

- **Q1：预算定窗需要额外一趟收集吗？** 净窗口收集本身要先定右端。可选答案：①用会话索引
  差分（ADR-022）先拿到逐会话触达集规模，再据此定右端，多付一趟索引扫描；②不预估，直接
  按固定会话数上限定窗（粗但零成本），把精度让给第二层收窄。
- **Q2：截断批次在 ADR-025 相位记账里算什么？** 需要它「不满足相位完成」，但也不能被记成
  失败。要找到 phase totals 的记账点，确认能表达「同一 dbnum 的第 n 个子窗口」。
- **Q3：预算的单位是什么？** 变更元素数（开窗前知道得到）还是暂存字节（只有跑过才知道）？
  倾向元素数，但需要一次标定把「元素数 → 实测暂存字节」的比例摸出来——现成的数据源是每个
  窗口写回前那行日志（`journal=… 字节，暂存语句=… 字节，预计写入行=…`），把历史日志拉一遍
  就能回归出系数，不必新加埋点。
- **Q4：业主接不接受变小的原子单元？** 见上。这是唯一一个不靠读代码能回答的。

## 验收（TDD 顺序）

1. 纯函数：预算切分器——给定逐会话规模与预算，切点必须落在会话边界、地板为 1 个会话、
   预算大到装得下时不切。
2. 源码钉：上界不得改写 `FileObservation.file_latest_sesno`（回退即红）。
3. mem 引擎集成（仿 `staging/issue10_add_node.rs`）：一段超预算的积压跑成两个子窗口，终态与
   一次大窗口逐字一致；水位单调推进；中途对持久层拍快照只看得见已完成的子窗口。
4. 回归：单个会话自己超预算时，仍然按资源原因阻断，不许被拆窗掩盖。
5. 回归：截断批次的余量确实被重排，不依赖下一轮重扫。

## 不做什么

- 不改写回协议、不动 `STAGED_COMMIT_SERIAL`、不碰 phase-2 方向。
- 不提供「降级提交」——截断的每一段仍然是全成才落盘（ADR-017 §1 那条纪律原样保留）。
- 不解决资源计量本身的两处低报（SQL 文本字节做摄入代理、`estimate_write_rows` 对带 WHERE
  的集合写按 1 行计）。它们与拆窗正交，仍在台账上。
