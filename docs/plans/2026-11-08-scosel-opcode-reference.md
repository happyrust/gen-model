# SCOSEL 序列化栈机 —— opcode 参考（IDA 取证）

GPSET 的规则成员存在 `SCOSEL` 隐式属性里，是一段 int 数组。本文是 IDA 反编译（`core.dll`，
`idalib-14972`，`D:\ida_scratch\plant3\core.dll.i64`，只读无状态）得到的 opcode 语义表，供
G3 / M4 实现 `scosel.rs` 使用。

**结论一句话**：`SCOSEL` 不是自定义指令集，是 `DB_Collection` 的序列化栈机——E3D 里「选择集」这套
结构（class 过滤 + 表达式过滤 + 显式成员）通用的编码，GPSET 只是把它存在元素属性里。

取证样本见 `2026-11-08-gpwl-gpset-group-nodes.md` §0「SCOSEL 字节码（样本聚类）」，
aps250204 的 27 个纯规则组（`members[0]`，成员链为空）。

**证据分级**：本文标「确证」的都有反编译地址 + 与样本字节对上的双重支持；标「推断」的只有其中
一项。实现遇到推断项一律按「未知即报错」处理，不要猜。

## 1. 整体形状

```
[word_count] 100016 1  100009 <N> {100007,<attr_hash> 100015,<len> 1 <expr>* 402} | {100001,<len> 1 <expr>*}
```

- `100016` 出现 2 次、值恒为 `1`：属性 id 段，头部固定。
- 随后是 class 段（`100009`）与 filter 表达式段（`100015`）。
- 段之间可同存：`100007`（规则组）与 `100001`（显式成员组）能在一个 SCOSEL 里同时出现。

## 2. 容器层 opcode

解码入口：`DB_Collection::decodeStack` @ `0x59BAA30`，`DB_Collection::decodeClass` @ `0x59BA470`，
编码对称入口 `DB_Collection::encodeClass` @ `0x59BB000`。

| opcode | 语义 | 备注 |
|---|---|---|
| `100016` | 属性 id | 头部固定，值 `1` |
| `100009` | class 段 | 后跟 class 数 `N` |
| `100007` | 规则组 | 段类型标记，后接 `100015` 表达式段 |
| `100001` | 显式成员组 | 后接**表达式**（与 `100015` 同格式），不是 refno 列表 |
| `100046` | 类型组 | |
| `100015` | filter 表达式 | 后跟 `len`，然后 `1` + 表达式流 |
| `100003` | scope | |
| `100010` | volume | |
| `100008` / `100017` / `100036` | 标志位 | 具体位含义未查清 |
| `100040` / `100043` | 字符串源 | |
| `100011` / `100012` | 段边界 | |
| `100050` | 引用属性 | |

### 2.1 `100009,<N>` 的长度口径（确证）

`N` 是段**内容**的字数，**不含 `N` 自身**。循环边界 `i < N`，起点是 `N` 之后第 2 个字
（首字是段类型标记：`100007` / `100001` / `100046`）。见 `decodeClass` @ `0x59BA470`。

**推论（重要）**：`100015` 段**不在** `100009` 段内。`100009` 的 `N` 只覆盖 class 段自身，
读完 `N` 个字就回到容器层。

### 2.2 `100015,<len>,1,<expr…>` 的长度口径（确证）

`len` 是该段**总字数**：含 `len` 自身、含紧跟的那个 `1`、含表达式流、含终止符。

`len` 后的 `1` 是版本 / 样式标志，`getExpressionTree` @ `0x59C8F70` 用 `v4 + 2` 跳过它再开始
读表达式。解码**靠 `len` 定边界，不靠 `402` 停**——`402` 是表达式内容的一部分，不是段终止符。
见 `decodeExpression` @ `0x59BA640`。

### 2.3 `100001` 显式成员组（确证）

`100001` 后跟**一个与 `100015` 同格式的 len-prefixed 表达式**（不是 refno 列表、没有 index），
随后可选 `100008` / `100017` 标志，读到 `100009` 段末尾。

- `decodeClass` 的 `100001` 分支把解析出的 `DB_Expression` push 进 `this+24` 的
  `vector<DB_Expression>`。
- 求值走 `preProcessInclusions` @ `0x59BEE10`：遍历 `this+588` 的表达式做「单条包含」展开，
  **不走 `evaluateDB`**。
- `encodeClass` 对称：`100009, 3, 100001, <expr 数组>, [100008], [100017]`。

这条推翻了我先前的猜测（「`100001` 后面是 GPITEM refno 链」）。**没有 refno、没有 index**。

## 3. 表达式层 opcode

分派入口：`DBE_Builder::getExpressionTree` @ `0x59C8F70`。**按 `opcode / 100` 分族**。

| opcode | 语义 | 族（/100） |
|---|---|---|
| `106` | 属性引用 | 1 |
| `118` | 文本字面量（`118,<len>,<ASCII>`） | 1 |
| `120` | 点号成员名（独立分支 `addDotNameMember` @ `0x59E1570`） | 1 |
| `122` | 点号属性名（独立分支 `addDotNameAttribute` @ `0x59E14E0`） | 1 |
| `104` | 变量名 | 1 |
| `1602` | id-of（见 §3.2） | 16 |
| `1701` | 零操作数终止符（见 §3.3） | 17 |
| `1702` | 未命名 | 17 |
| `1703` | noun 限定 | 17 |
| `402` | 字符串相等（全串相等，见 §3.4） | 4 |
| `401` | 数值相等 | 4 |
| `403`–`413` | 相等族其余成员 | 4 |
| `501`–`513` | 不等族 | 5 |
| `601`–`608` | 比较 | 6 |
| `609` / `610` | between | 6 |
| `611`–`614` | 日期 | 6 |
| `615`–`618` | Blob | 6 |
| `1306` | **after**：取 b **之后**的子串 | 13 |
| `1307` | **before**：取 b **之前**的子串 | 13 |
| `1308` / `1311` | match：返回匹配位置 + 1（double） | 13 |
| `1317`–`1319` | matchwild：通配匹配，`popList(2/3/4)` | 13 |
| `301` | **OR（并集）** | 3 |
| `302` | **AND（交集）** | 3 |
| `303` | **NOT** | 3 |
| `304`–`307` | 未查清，语义名为推断 | 3 |

### 3.1 `13xx` 族全是字符串函数，不是比较（确证，推翻先前理解）

`getTreeStringFunctions` @ `0x59CC790`：

- `1306` = `DBE_After`：取第二个操作数**之后**的子串。
- `1307` = `DBE_Before`：取第二个操作数**之前**的子串。
- `1308` / `1311` = `DBE_Match`：正则 / 模式匹配，返回匹配位置 + 1（double，0 表示不匹配）。
- `1317` / `1318` / `1319` = `DBE_MatchWild`：`popList(2/3/4)`，通配符是 **`*`(42)** 与
  **`?`(63)**，`matchWild` @ `0x59B7E70` 是标准回溯通配匹配。

**这直接改掉了本文旧版的一条错误结论**：旧版写「NAME 前缀判定要用 `1307`」——错的。`1307` 是
取子串，返回字符串，不能当布尔谓词用。

### 3.2 `1602` 的布局（确证）

`1602` 后跟一个 count 前缀的 int 数组。`4` = 数组**总字数（含自身）**，共 4 个字：

```
[4][X][noun_hash][类型标记]
```

末字是类型标记：`6` = noun（走 `DB_Noun::findNoun`）、`4` = IdName、`3` = IdRef。
见 `DBE_IdExpression` @ `0x59CF930`、`buildExpression` @ `0x59D09A0`。

**推断**：index 1 那个 `X` 的语义未查清（疑似父级 / 作用域 id）。

### 3.3 `1701` 是零操作数终止符（确证）

`1701` 不消费任何操作数，只前进 1 个字。旧版把它当「属性终止符」带操作数，是错的。

### 3.4 `402` 是全串相等，不是 startswith（确证）

`402` 走 `LicFeatureCheckOut_StrEq` @ `0x5819BF0`：先比长度，长度不等直接 false；然后逐 4 字节
比较。**全串相等**。想做前缀匹配只有两条路：

1. `1317`（matchwild）+ 字面量 `"*前缀"` —— 通配在尾部，语义上等于「以该前缀结尾」；
2. `1304` / `1312`（SubString2，取前 N 个字符）+ `402` —— 截断后再全串比。

真库那 27 组前缀规则到底用哪个 opcode，**未查清**（缺原始 SCOSEL 字节，样本聚类里也没有
`1307` 出现）。这是 M4 第二批必须先解决的问题。

### 3.5 `106` 的尾部由 `DBE_Attribute` 消费（确证）

`106` 在 `getExpressionTree` 里**没有分支**，落到 `getTreeValues` 的 case `106`，交给
`DBE_Attribute::constructFromIntArray` @ `0x59D7B30`。由它消费：`attr_hash` + 2 个 flag 字 +
1 个 subscript 字，以及可选的 `2100`（参数表）/ `2200`（noun）/ `1601` / `1602` / `1701` /
`1702` / `1703`。

### 3.6 两条容易踩的语义

1. **`120` / `122` 是独立 opcode 分支**（`addDotNameMember` / `addDotNameAttribute`），
   **不是** `106` 的尾字。旧版把点号名当成 `106` 的一部分，错。
2. **`301` 是 OR 不是 AND**。G3 只做 NAME 前缀子集时，两条前缀规则合并走 `301`；
   同一属性上的多个条件才是 `302`。

## 4. 求值域

- `evaluateMDB` @ `0x59BC330` → `DB_MDB::instance()` + `findELementsTypeActual`：
  **求值域是当前 MDB 的全量元素**，先由 class 列表（`100009` 段）缩窄。
- 单库 `evaluateDB` @ `0x59BBF00`。
- 不是「同一个库内的元素」。这条对 gen-model 的落点很关键：SCOSEL 规则组求值出来的成员
  可以散落在 MDB 的任意库，和 GPREF 跨库是同一类问题。

## 5. 未查清（实现时按「未知即报错」处理，不要猜）

| 项 | 影响 |
|---|---|
| 真库 27 组前缀规则实际用哪个 opcode | **M4 第二批的首要未知**；决定 G3 要不要实现 `1317` |
| `1602` 数组 index 1 的语义 | 只影响 id-of 的完整还原 |
| `106` 的 2 个 flag 字 + 1 个 subscript 字语义 | 属性引用的限定信息 |
| `304`–`307` 语义名 | 只影响错误信息措辞，不影响已确认子集 |
| `preProcessClassIds` 的实际调用者 | 决定 class 段是否在解码期就被改写 |
| `100008` / `100017` / `100036` 位含义 | 标志位，v1 可只记录不解释 |
| `100013` / `100018`–`100034` 旧版兼容 opcode | 老工程文件里的 SCOSEL 可能带这些 |

## 6. G3 实现约束（与开发计划 §3.1 G3 一致）

1. **开关 `group_scosel` 默认关**。关着时 GPSET 只看 GPITEM 链，行为与 M3 完全一致。
2. **未知 opcode 报错，不静默**。错误信息带上 opcode 数值与在数组里的下标，
   让人拿真库样本能直接定位。绝不「跳过不认识的字」继续读——栈机会整体错位。
3. **v1 只做已确认子集**：
   - 容器层：`100016` / `100009` / `100015` / `100007` / `100001` / `100011` / `100012`。
     解码必须按 §2.1 / §2.2 的长度口径走：`100009` 的 `N` 不含自身，`100015` 的 `len` 含自身。
   - 表达式层：`402`（字符串相等）+ `118`（文本字面量）+ `106`（属性引用）+ `301` / `302`
     （合并）+ `1306` / `1307`（取子串）。
   - **前缀匹配的实现方式待定**（见 §5 第一条）。在查清真库用哪个 opcode 之前，`1317`
     按 `unsupported` 报错，不要凭语义猜着实现。
   - 其余一律 `unsupported opcode`。
4. **树里规则成员为 `rule: true, via: null`**。`ResolvedMember` 加 `Rule { element }` 变体
   （`via()` 回 `None`），`ResolvedMember::element()` 照常给元素，解析视图把它和
   `Reference` 成员一起按存储原序去重。
5. **求值域是 MDB 全量**：规则成员可能跨库，和 `GPREF` 一样走 store 的按 refno 路由，
   不要假设同库。
6. **坏槽要单独报**：规则求值里「属性不在模板上」「字面量不是 ASCII」这类，进
   `unresolved`，原因码另起一族（如 `scosel_unsupported` / `scosel_eval_failed`），
   不要混进 `gpref_missing` / `db_not_in_mdb` / `target_missing` 那三个。
7. **契约快照**：`group_scosel` 关与开各一份基准，键名沿用 `tests/fixtures/group-contract/`
   现有四份的口径；`rule` 字段已经在契约里（见 `-dev-plan.md` §2），不需要新增字段。
8. **`encode` 与 `decode` 必须对称**：`encodeClass` @ `0x59BB000` 是现成的对称参考。
   `word_count` 自检（首字等于总字数）在 encode 里显式算一遍，别从 `len()` 推。
