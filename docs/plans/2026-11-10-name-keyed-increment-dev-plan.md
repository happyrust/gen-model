## 0. 一句话

在 gen-model 里加一条只读接口。给它一个库（或库里的若干节点）和一个比较基准，它按 E3D 里存的名称（`NAME`）把基准一侧和当前一侧的构件配成对，
不看参考号，比过内容之后给每个有真实名字的构件一行：新增、删除、修改或未修改，并标明是否换了参考号、属于哪个最小交付单元。结果按需算，不落库。

rs-server 提资时，对有真实名字的单元用它决定跳过还是重发；没有真实名字的单元不在结果里，rs-server 对它们保持现在的做法。
plant-ui 的提资预览用同一份结果分类展示。现有的增量处理、任务回执、模型落库和接口都不改：换了参考号的构件，内部仍按新参考号重新生成、落库。

## 1. 先约定几个词

| 词 | 在本文里的意思 |
| --- | --- |
| 参考号（refno） | E3D 给每个元素的内部编号，形如 `24384/26616`。元素删掉重建后参考号是新的。 |
| 名称（`NAME`） | 设计人员给元素起的名字，形如 `/1RCV0102A/B1`，带前导斜杠。最小交付单元的名称在业务上叫位号。 |
| 会话 | E3D 每次保存（SAVEWORK）在库文件里追加的一个版本。按会话号可以读回当时的整库状态。 |
| 应用水位 | 一个库已经写进数据库的那个会话号。rs-server 提资读的是数据库，所以它看到的就是这个会话的状态。 |
| 最小交付单元 | 独立交付的那一级元素，类型由 gen-model 的配置定，缺省是 `BRAN / HANG / SUPPO / EQUI`（`CONTEXT.md`「最小交付单元」）。下文简称单元。 |
| 提资 | 把单元的数据交给数据中台，由 rs-server 执行、plant-ui 发起。需求表里的「发布」「预发布」「二次发布」说的都是它。本仓词汇表里的「发布」另有所指（模型记录落地），所以本文一律说提资。 |
| 提资版本记录 | `datacenter_version` 表的一行，记一个提资过的单元：实例编码、状态、上一次提资时的指纹。rs-server 在提资成功时写。下文简称版本记录。 |
| 交付删除记录 | `datacenter_delete` 表的一行：已提资的单元被删或被改名时，gen-model 的增量记下它原来的位号。前端的「待删除列表」展示的就是这张表。 |
| 现有路径 | rs-server 今天判断一个单元跳不跳过的办法：版本记录的状态加指纹（§2.2）。 |
| refno 口径 | 现状：参考号相同才是同一个构件。 |
| 名称口径 | 本文要加的：同一个库里名称相同就是同一个构件，不看参考号。 |
| 自动命名 | 以 `/Copy-of-` 或 `/Copy-(数字)-of-` 开头的名称，是 E3D 复制元素时带出来的，不是设计人员起的。 |
| 真实名字 | 设计人员起的名称：`NAME` 不为空，并且不是自动命名。 |
| 有名构件 | 有真实名字的元素。名称口径只给有名构件出行。 |
| 名下 | 一个有名构件名下的东西，是它自己加上挂在它下面、没有真实名字的成员（无名的和自动命名的）。 |
| 换号 | 同一个名称前后对应的参考号不同。它是标注，不是类别。 |
| 接替 | 已提资的单元被删掉之后，同库里又出现同名的新单元：新单元接替旧单元。原单元是先改名让出名称的，也按接替算（P7）。 |
| 基准、目标 | 一次对比的两侧。基准是较早的状态（缺省是上一次提资时），目标是较新的状态（缺省是当前）。 |
| 提资基准 | 缺省入口拿来和当前比的那个会话：版本记录上的「提资时的会话号」；旧记录没有这个数时，退回用记录上已有的那个会话号（D16）。 |

- 提资按参考号记版本记录的单元，与 gen-model 的最小交付单元不完全重合：工艺、仪控的支吊架是 ZONE，电气接地和一部分电缆支架是 STRU，

## 3. 设计

每条写决定、理由、没有采用的做法。§3.1 是前三轮问答的共识，括号里是共识的条目号。§3.2 是第四轮定下来的，括号里是第四轮的第几条回答，
以及它对应上一稿的哪个开放问题。§3.3 是由这些决定推出的做法。§3.4 是定稿之后又向用户确认的、给用户看过的。

### 3.1 前三轮的共识（D1–D15）

#### D1　叫「名称口径」，现状叫「refno 口径」（共识 1）

- **决定**：这项能力叫名称口径，不叫「过滤」。
- **理由**：它不筛掉任何数据，只是换一种认身份的办法；「过滤」在本仓已经有两个词条明确避开（监听限定域、模型增量类型限定）。
- **没有采用**：「按名称过滤的增量更新」（用户最初的说法）、「名称增量」。

#### D2　判定放在 gen-model，rs-server 和 plant-ui 来取结果（共识 2）

- **决定**：配对、比内容、给类别都在 gen-model 做。rs-server 的提资和 plant-ui 的提资预览调接口取结果。#99、#113、#100 三张票原来写的是
  「rs-server（主要）」，分工相应改写（§14）。
- **理由**：第一，判定要读「上一次提资时」的内容，只有按会话读库文件才拿得到，这套读法在 gen-model；rs-server 只看得到库里的当前状态，
  所以它今天只能在提资时存一个指纹。第二，成员顺序、属性字典的变化类、生成读取集合都在 gen-model。第三，提资和预览要同一个结果，放在一处算才不会各判各的。
- **没有采用**：按 #92 定稿在 rs-server 里新做一个「内容指纹」。指纹只能回答相同还是不同，给不出逐个构件的类别和变化摘要；
  要让它覆盖「引用按目标名称比」「成员按顺序比」，等于在 rs-server 里再造一遍 gen-model 已有的读法。
  rs-server 现有的「状态 + 指纹」判断不删，留给名称口径不覆盖的单元（D17）。

#### D3　认定规则：同库内，名称整串精确相同（共识 3）

- **决定**：用 E3D 里存的 `NAME` 原文，带前导斜杠，只去首尾空白，区分大小写，整串精确比较。只在同一个库（同一个库号）里配对。
  别的库里出现同名元素不配对，只在结果里提示。
- **理由**：E3D 只在一个库文件里保证名称唯一；不同库之间的同名元素可以同时存在，配不出一对一。
- **没有采用**：忽略大小写或去掉斜杠（会把 E3D 认为不同的两个名称并成一个）；跨库配对；用提资的实例编码配对
  （编码把斜杠等字符换成下划线，不同的名称可能撞成同一个编码）。

#### D4　没有名字的和自动命名的元素不出行（共识 4）

- **决定**：没有 `NAME` 的元素不出行。名称以 `/Copy-of-` 或 `/Copy-(数字)-of-` 开头的元素（自动命名）也不出行。前缀做成可配置的清单。
- **理由**：没有名字就没有可认的身份。自动命名不是设计人员起的，复制一次就会多出一批。
- **没有采用**：给无名元素用「属主 + 类型 + 序号」认身份并出行（RVM 对拍的做法，序号会漂移）；把自动命名当真实名字。

#### D5　每个有名构件一行，带上所属单元（共识 5）

- **决定**：每个有名构件一行，行上带它所属的最小交付单元（参考号、类型、名称），供提资按单元汇总。
- **理由**：提资以单元为单位决定重发还是跳过；而用户要的「按名称作为唯一参照的提取接口」是元素级的。一行带上单元，两种用法都够。
- **没有采用**：只按单元出行（看不出单元里哪个构件变了）。

#### D6　比较基准是上一次提资（共识 6，沿用 #92）

- **决定**：缺省的基准是上一次提资时的状态，不是第一次提资时的。
- **理由**：中台上存的是上一次提资的内容。改过一次并提资、之后又改回原样的，必须重发。
- **没有采用**：以第一次提资为基准（需求原文写的是「第一次（或者上一次）」，#92 定稿取了上一次）。

#### D7　比有名构件自己的内容；引用按目标的名称比；纯元数据不算（共识 6，沿用 #92）

- **决定**：
  - 比有名构件自己的属性。
  - 引用类属性按目标的名称比：目标被删掉重建但名称没变，算没变；换成另一个名称的对象，算实质变化。目标怎么描述见 D23。
  - 纯元数据的变化不算。判定沿用 #92 的三条（属性字典的变化类为 0、生成器不读、提资不读），再加 `CACHID`、`SPAMAP` 两个戳。
    `NAME`、`DESC`、全部 UDA（用户自定义属性）一律算实质。第三条要用的清单见 D20。
- **理由**：见 #92 口径草案的问题 2、问题 3。
- **没有采用**：引用按目标的内容比（要给规格件、目录件、详图、材料各定义一遍「内容」）；手抄一份纯元数据清单（提资代码一加读点清单就过期）。

#### D8　无名成员上卷到所属的有名构件（共识 6）

- **决定**：无名成员不出行，但它的增、删、改要让所属的有名构件判为「修改」。无名成员只是换了参考号、内容和顺序都没变的，不算。
  成员按顺序比，不带成员自己的参考号。
- **理由**：管件常常不命名。无名弯头改了角度，管线的几何和提资内容都变了，必须重发。
- **来历**：用户一开始选的是「无名成员的变化一律忽略」。看到后果（无名弯头改了角度而管线算未修改，提资会跳过）之后改成了上卷。
- **没有采用**：一律忽略无名成员；给无名成员单独出行（D4）。

#### D9　「模型没变」按生成器要读的属性判，不重新生成（共识 6）

- **决定**：判断模型有没有变，看生成几何要读的那些属性有没有变，不为此重新生成两侧的几何。测试里用实际生成的几何对照，
  确认两种判法在验收用例上一致（§9）。
- **理由**：重新生成两侧的几何很贵；而换号的构件，现有管线本来就会按新参考号重新生成一遍，没有必要为了「比一比」再生成一次。
- **已知盲区**：目录库变了而设计属性没变时看不出来（§11 第 3 条）。
- **没有采用**：两侧各生成一遍几何再比。

#### D10　四个类别，加标注；改名记成一删一增（共识 7）

- **决定**：类别只有新增、删除、修改、未修改四种。另带标注：是否换号（旧参考号、新参考号）、是否从未提资过。
  改名（参考号没变、名称变了）记成旧名「删除」加新名「新增」，两行互相指明。
- **理由**：名称就是身份，名称变了就是换了一个身份；中台按位号认实例，改名在提资时本来就是旧位号删除加新位号新增（#97）。
- **没有采用**：把「仅换号」单列成第五类（换号的构件既可能未修改也可能修改，它和类别是两个维度）；给改名单设一个类别。

#### D11　底层是「任意两个会话之间按名称对比」，缺省入口读版本记录找基准（共识 8）

- **决定**：底层做成给定同一个库的两个会话就能按名称对比。缺省入口由 gen-model 读版本记录上的会话号当基准。
  版本记录上没有会话号的旧单元按已修改处理。从未提资过的单列。基准具体用哪个数见 D16。
- **理由**：底层和提资无关，可以单独验证，也能给别的用途（比如看两次保存之间按名称变了什么）。
- **没有采用**：把基准内容存一份快照（要落库，见 D12）。

#### D12　按需算，不落库；新开一条只读接口；现有的都不动（共识 9）

- **决定**：结果每次按需算出来，只进进程内缓存，不落库。新开一条只读接口（§6）。现有的增量处理、任务回执和接口都不动：
  换了号的构件在内部仍按新参考号重新生成、落库。
- **理由**：与 ADR-081、ADR-079 同一条纪律，模型面不添第二份持久事实。规则（跳过清单、纯元数据清单）一改，落库的结果就全部作废，按需算没有这个问题。
- **没有采用**：对现有增量数据做一遍后处理并存成表（用户最初的说法）；改造现有管线让它直接按名称认身份（模型记录以参考号为键，
  见 vendor/e3d-model `src/elmodl.rs:169-188` 的 `GeometryId`，换了号就必须按新参考号重新生成）。

#### D13　分工（共识 10）

- **决定**：
  - gen-model：配对、比内容、给类别；在待删除列表里标「已被接替」。
  - rs-server：据此跳过或重发；不为被接替的旧参考号推送删除；把版本记录转到新参考号；用脚本扫出「提资读取清单」交给 gen-model。
  - plant-ui：提资预览按类别展示。
- **理由**：每一方只做靠自己手里的数据就能做对的事：按会话读库文件在 gen-model，中台的实例编码、版本号和推送在 rs-server。

#### D14　重名：不配对，报出来（共识 11）

- **决定**：用户确认业务上不会重名。万一同一个库的同一侧出现两个同名的元素，这些元素不配对，并在结果里报出来。
- **理由**：配错比不配更糟：配错会把两个不同的构件判成「未修改」而跳过提资。
- **没有采用**：重名时挑一个配对（比如取第一个，或者再按类型、属主去分）。

#### D15　无名子件的编码：不处理，作为已知后果（共识 12）

- **决定**：无名子件在提资内容里用参考号当编码。单元换号后被跳过，中台上留的是旧参考号。不为此重发，也不做专门的标记。
  用户的原话是「没有命名的直接跳过」。
- **后果**：见 §11 第 1 条。
- **没有采用**：单元换号时为了刷新无名子件的编码而重发；在结果里给这种单元加专门的标记。

### 3.2 第四轮定下来的（D16–D29）

#### D16　基准会话号：rs-server 另记一个「提资时的会话号」（第四轮回答 1，原开放问题 1）

- **决定**：rs-server 在提资成功时，在版本记录上另记一个「提资时的会话号」（字段名草案 `published_sesno`），gen-model 以它为基准。
  旧记录没有这个数时，退回用记录上已有的那个会话号（`published_fingerprint.max_sesno`）。两个数都没有的，按已修改处理。
- **理由**：记录上已有的那个数是「提资时单元子树里最后一次写入的会话」，不是「提资当时这个库处在哪个会话」。D21、D23 要看子树之外的东西
  （上级的位置、被引用对象改名）。例：单元最后一次被写是会话 100；会话 150 时它所在的 ZONE 整体移动；会话 200 时提资，中台拿到的是移动之后的坐标。
  拿会话 100 当基准，位置对不上，判修改、重发；重发之后这个数还是 100，下一次仍判修改，每次都重发。
- **代价**：版本记录多一个字段。
- **没有采用**：只用已有的那个数；由 gen-model 自己记一份（违反不落库，gen-model 也不知道提资何时成功）。
- 写法上的约束见 P6；旧记录退回基准时的一个盲区见 §11 第 9 条。

#### D17　没有真实名字的交付单元不在结果里，rs-server 对它们保持现在的做法（第四轮回答 2，原开放问题 2）

- **决定**：交付单元自己没有名字、或者是自动命名的，名称口径的结果里完全不出现：没有单元汇总，不参与换号配对。
  rs-server 对这些单元保持今天的代码路径，今天怎么做见 §2.3。
- **用户做这个选择时看到的数**：开发库里自动命名的 EQUI 937 个、BRAN 589 个（§2.4）。
- **发布票之前的确认**：第四轮问这一题时，对 rs-server 今天做法的转述与代码不完全相符。把 §2.3 更正后的事实告诉用户之后又问了一次，
  用户维持这个选择（§3.4 确认一）。
- **理由**：与共识 4（没有真实名字的元素不出行）、共识 12（「没有命名的直接跳过」）是同一个态度。
- **没有采用**：上一稿建议的「按参考号认，照样给类别」；一律判修改。
- **后果**：纯元数据的改动不触发重发、换号不重发，这两条只对有真实名字的单元生效（§11 第 2 条）。由此推出的做法见 P1、P2、P5。

#### D18　有名成员各判各的；单元的类别由属于它的各行得出（第四轮回答 3，原开放问题 3）

- **决定**：一个有名构件的类别只看三样：它自己的属性、它名下没有真实名字的成员、它下面有哪些有名成员以及它们的顺序。
  有名成员自己内容的变化只记在它自己那一行。按单元汇总时，属于这个单元的行里只要有一行不是「未修改」，单元就算修改。
- **理由**：#92 的回归场景 6「成员增删或换顺序：重发（E3D 里成员顺序就是管路走向）」；提资以单元为单位重发，所以单元的类别要汇总它下面所有的行。
- **没有采用**：有名成员一变，它上面每一级有名构件都判修改；上级完全不看有名成员。
- **后果**：有名成员删后重建，如果落在成员表里的另一个位置，上级判修改。单元类别的细化见 P3。

#### D19　自动命名的成员和无名成员一样上卷（第四轮回答 4，原开放问题 4）

- **决定**：挂在有名构件下面的自动命名成员，与无名成员同样处理：不出行，它的增、删、改算所属有名构件的修改。它的名称本身不参与比较。
- **理由**：rs-server 对复制件的做法是「不发实例，长度照算」（rs-server `src/datacenter/gy.rs:1195`）：复制件不单独提资，但仍然影响所在管段的提资内容。
- **没有采用**：完全忽略；当作普通的有名构件出行。

#### D20　「提资读取清单」由 rs-server 用脚本扫出，gen-model 收进仓库；到位前只认两个戳（第四轮回答 5，原开放问题 5）

- **决定**：rs-server 用脚本从自己的代码里扫出提资读了哪些属性，并加护栏测试；gen-model 把清单文件收进仓库，与现有的生成读取集合并排。
  清单到位之前，只把 `CACHID`、`SPAMAP` 当纯元数据，其余一律算实质。
- **理由**：两边各有一份可审阅、可对比的文件，运行时不多一条依赖；`src/data_interface/generation_read_set.json` 就是这个做法。
  到位前不能只靠现成的两票：`DESC`、`TSPE`（伴热规格）两票都过，但提资在读。
- **没有采用**：rs-server 运行时提供一个接口；写进共用数据库里的一张配置表；清单到位前先用 #92 草案里那 54 个候选。

#### D21　单元之外的变化计入（第四轮回答 6，原开放问题 6）

- **决定**：上级（ZONE、SITE 等）移动使单元的世界位置变了，算这个单元的修改，记在单元自己那一行。提资从上级或被引用对象身上读的属性变了，也算；
  读了哪些由 D20 的清单声明，清单到位之后才生效。
- **理由**：生成器沿属主链往上读位置（vendor/e3d-model `tests/ancestor_reads_guard.rs:1-7`），上级一动几何就动了；提资内容里有坐标（rs-server `src/datacenter/gy.rs:1419`）。
- **没有采用**：只看单元子树（今天的指纹就是这样）。

#### D22　目标一侧取应用水位（第四轮回答 6，原开放问题 7）

- **决定**：缺省入口的目标会话取这个库的应用水位。显式两会话入口不受影响。
- **理由**：rs-server 提资读的是数据库里的状态，也就是应用水位那个会话。
- **没有采用**：取库文件里最新的会话（可能比数据库新，rs-server 还读不到）。

#### D23　引用的目标怎么描述（第四轮回答 6，原开放问题 8）

- **决定**：
  - 目标有真实名字：用它的名称。
  - 目标没有真实名字：用「最近的有名祖先的名称 + 从那里往下逐级的类型与序号」。
  - 目标在别的库（目录库，或另一个设计库）：两侧都用目标现在的名称。
  - 目标还是同一个对象，只是它自己改了名：同一个库里的，算引用方的修改；别的库里的看不出来。
  - 引用为空，或者目标已经不存在：各用一个固定记号。
- **理由**：无名目标的写法在常见情形（有名 BRAN 里的无名管件）下与 #92 的「单元位号 + 成员序号」相同，单元没有真实名字时也能用。
  别的库在基准时刻处在哪个会话无从知道。提资内容里有从目标名称取的值（相邻件编码取自 `CREF` 目标的名称，材料编码取自 `SPRE` 目标的名称，
  见 #92 草案问题 2、问题 4），所以同库里目标改名要算。
- **没有采用**：#92 原来的「目标所在单元的位号 + 成员序号」；目标改名不算引用方的修改。

#### D24　有名构件换了属主或换了单元，算修改（第四轮回答 6，原开放问题 9）

- **决定**：出一行，类别是修改，标明旧属主和新属主、旧单元和新单元。新旧两个单元都判修改。
- **没有采用**：旧单元里记一行删除，新单元里记一行新增。
- **范围**：说的是构件挪到了别的属主或别的单元下面。上级只是改了名、构件没有挪动，不在这一条里（P9）。

#### D25　同名但类型不同，不配对（第四轮回答 6，原开放问题 10）

- **决定**：旧的记删除，新的记新增，并标注类型变了。
- **理由**：中台的实例带对象类型；E3D 自己改类型也是先整体删除再重建（vendor/e3d-model `src/element_diff.rs:116-119`）。
- **没有采用**：算同一个构件，判修改。

#### D26　换号且内容有变的单元重发后，中台上旧参考号编码的无名子件不处理（第四轮回答 6，原开放问题 11）

- **决定**：与 D15 同样对待：不清理，不做标记。
- **后果**：见 §11 第 1 条。
- **没有采用**：rs-server 重发前按旧版本记录把旧的无名子件删掉。

#### D27　容器在缺省入口不出行；基准会话不在会话链上按已修改处理（第四轮回答 6，原开放问题 12、13）

- **决定**：SITE、ZONE、PIPE 这些不属于任何单元的有名元素没有版本记录，缺省入口不出这些行，显式两会话入口照出。
  库的会话被合并之后，基准会话读不回来，这些单元按已修改处理并标注原因，多发一次。
- **没有采用**：给容器找一个替代基准。

#### D28　自动命名的判法两边各管各的（第四轮回答 6，原开放问题 14）

- **决定**：gen-model 按「以前缀开头」判（D4）。rs-server 现有的 `is_copy_tag` 按「名称里含有」判，保持不变。联调时把两边判得不一样的元素列出来看。
  开发库里那 1 个 `/-Copy-of--RX-CSV-S2018-BAR-3` 缺省不算自动命名，要算就加进前缀清单。
- **没有采用**：统一成一份规则。

#### D29　接口路径、取数通道（第四轮回答 6，原开放问题 16、17）

- **决定**：接口路径暂定 `GET /api/v1/name-diff`；范围参数给上级节点，不逐个列单元；只用 GET（ADR-081 的约定）。
  plant-ui 的提资预览经 rs-server 现有的提资预览接口取数，由 rs-server 去调 gen-model。
- **理由**：一次提资可能有几百个单元，逐个写进查询串放不下。预览和真正提资经同一个通道，用的是同一套入参。
- **没有采用**：plant-ui 直接调 gen-model。

### 3.3 由决定推出的做法（P1–P14）

下面每一条都是按上面的决定推出来的，起草时都**没有单独问过用户**。发布票之前，P1–P3 单独列给用户看过，用户没有反对；
P4 留下的缺口问过用户；票发布之后，P5–P7 连同说明文档给用户看过，用户没有反对；P8–P14 仍然没有逐条给用户看过（§3.4）。
P1–P4 会改变结果里有什么；P5–P7 是 rs-server 一侧的契约细节；P8–P14 是边角。

#### P1　所在单元没有真实名字的有名构件：显式入口出行，缺省入口不出行

- **做法**：一个有名构件挂在没有真实名字的单元下面时（比如无名 BRAN 上有位号的阀门），显式两会话入口照常给它出一行，行上的所属单元为空，
  并标明原因是「所在单元没有真实名字」。缺省入口不出这一行。
- **依据**：共识 5 说每个有真实名字的元素一行，所以显式入口要出。D17 说这种单元不在结果里、rs-server 对整个单元走现有路径，
  所以缺省入口里这一行既没有基准、也没有使用方。这与 D27 对容器的处理是同一个道理。

#### P2　上卷不越过交付单元的边界

- **做法**：没有真实名字的成员往上找所属的有名构件时，走到所在交付单元的根为止。单元的根没有真实名字，这个成员的变化就不看。
  没有真实名字的单元，在它上级容器的内容里也不占位置：增、删这样一个单元，不算上级容器的修改。
- **依据**：D17「完全不出现」；共识 6 的「所属的有名构件」。

#### P3　单元类别的细化

- **做法**：单元自己那一行是新增或删除时，单元就取这个类别；否则按 D18 汇总。改了名的单元，新名那一条是「新增」，指明旧名，不标「从未提资」；
  旧名那一条是「删除」，指明新名。rs-server 对它照 #97 办（旧位号删除加新位号新增）。
- **依据**：D10、D18。第四轮回答 3 的选项原文只说了「只要有一行不是未修改，单元就算修改」，没有说单元自己是新增或删除的情形。

#### P4　名称口径里的「单元」取 gen-model 配置的最小交付单元类型

- **做法**：所属单元按 gen-model 配置的类型找（缺省 `BRAN / HANG / SUPPO / EQUI`）。提资按别的类型记版本记录的那些单元（§2.3：工艺、仪控的支吊架是
  带 `:SUPP` 自定义类型的 ZONE，电气接地和一部分电缆支架是 STRU）不在结果里，rs-server 对它们走现有路径。
- **依据**：共识 5 说的是「最小交付单元」；ZONE 在 gen-model 里恒不算单元。
- **这是一个覆盖面上的缺口**：这些支吊架今天按现有路径判断，以后也是，「仅参考号变化不重发」对它们不生效。缺口有多大，要在实施时量（§12 的 V10）。
- **用户的决定**（发布票之前问过，§3.4 确认二）：先按现在的方案开票；做到 S5 时先数出这类单元有多少，再决定补不补；在那之前它们按现有路径判断。

#### P5　rs-server 走哪条路径，只看单元在不在 gen-model 的结果里

- **做法**：rs-server 不自己判断名字是不是真实名字。结果里有这个单元，就用它的类别；没有，就走现有路径。
  rs-server 现有的「不发」过滤（§2.3）原样保留，并且先于类别生效。gen-model 调不通时，全部单元走现有路径。
- **依据**：D17、D28。这样两边不用共享一份命名规则，结果之外的单元（没有真实名字的、类型不属于最小交付单元的）自动落到现有路径上。

#### P6　版本记录的写法

- **做法**：指纹照旧对所有单元计算和登记。每次提资成功，对这次发出去的每条版本记录，「提资时的会话号」要么写成这次提取之前问到的目标会话号，
  要么清空，不能留着上一次的值。
- **依据**：D16。留着旧值，下一次会拿过时的基准去比。例：第二次提资没有问到目标会话号、又没有清空，记录上还是第一次的会话号；
  之后内容改回第一次的样子，就会被判成未修改，而中台上存的是第二次的内容。清空之后退回用指纹里的会话号，是安全的。

#### P7　接替按交付删除记录配对，删除和改名两种原因都算

- **做法**：一个有真实名字的单元没有自己的版本记录时，在同库的交付删除记录里找旧位号等于它的名称、类型相同、而且旧参考号有版本记录的那一条。
  找到就是接替，不管记录的原因是删除还是改名。
- **依据**：D10、共识 10。#113 的「复制一份、改回原名、再删掉原件」，实际次序是原件先被改名或删掉，名称才能让出来（同库不能重名）；
  原件先改名时，留下的是原因为改名的记录，同一个参考号只保留首次事件。

#### P8　引用的目标一直到库顶都没有有名祖先时，退回用参考号比

- **依据**：D23 的写法在这种情形下没有可用的名称；用参考号偏保守，目标换号会判修改。

#### P9　有名构件的「属主」按最近的有名祖先认

- **做法**：D24 说的换属主，指这个构件挪到了另一个有名祖先下面，或者挪进了另一个单元。在同一个有名祖先下面的无名层级之间挪动，
  不算这个构件自己的修改；结构的变化由那个有名祖先的内容体现。
- **怎么算换了**：两侧各取最近的有名祖先，所属单元同样处理。名称相同就是没换，它的参考号换没换都一样；名称不同、但还是同一个元素
  （参考号相同，也就是它自己改了名，D10），也是没换；其余才是换了。
- **上级只是改名，不算换了属主**：管线、区域或者单元自己改了名，下面的有名构件没有挪过地方，不因此判修改。改名的那个上级自己照 D10 出两行
  （旧名删除、新名新增）。它的名称变了对下面的单元有没有影响，归 D21 的后一半：提资读取清单到位之后，提资读了这个名称的单元判修改；
  到位之前看不出来（§11 第 12 条）。
- **依据**：D18、D24、D10、D21。按直接属主认的话，无名属主的序号一变，下面的有名构件就会被连带判成修改。
  按名称认属主的话，上级一改名，紧挨着它的有名构件立刻都判修改，D21「清单到位之后才生效」就落空了，也与 S3（#136）的验收对不上
  （「清单声明从上级读的属性变了（例如所属 PIPE 改名）：读它的单元判修改」）。

#### P10　同名但类型不同时，结果里有两行同名

- **做法**：一行删除、一行新增，名称相同，靠类型区分，都标「类型变了」。
- **依据**：D25。

#### P11　库还没有入库时，缺省入口报错

- **依据**：D22。没有应用水位就没有目标会话，rs-server 也没有东西可提。

#### P12　一次提资涉及多个库时，rs-server 按库各问一次

- **依据**：D3（只在同一个库里配对），接口以库为单位。

#### P13　提资预览里，结果之外的单元单独归一栏

- **做法**：没有真实名字的单元、类型不属于最小交付单元的单元，在预览里单独一栏，只分「照发」和「跳过」两个数，依据是现有路径。
- **依据**：D17、P4；#100 的验收要求数量与实际提交结果一致。

#### P14　重名的构件所在的单元按修改处理

- **依据**：D14 说重名的构件不配对；不配对就判不了，判不了的不能判成未修改（§7 gen-model 的第 3 条承诺）。

另有一条**建议**（可以不做，不影响正确性，同样没有问过用户）：判为未修改而跳过的单元，rs-server 把它的版本记录刷新成与这次判断一致
（状态回到 `Insert`，「提资时的会话号」前移，指纹不动）。理由见 §7 第 5 条。

## 4. 数据从哪来

| 要的数据 | 来源 | 现成的读法 |
| --- | --- | --- |
| 两个会话各自的元素树、名称、属性 | E3D 库文件，按会话钉住读 | `SessionSets`；`DbElement` 的 `stored_name / members / owner / extraction` |
| 两个会话之间哪些元素动过 | 会话索引差分 | `e3d_model::increment::collect_window` |
| 一个元素属于哪个单元 | 沿属主链往上找 | `resolve_unit_root`；`configured_delivery_unit_types` |
| 谁引用了某个元素 | 库文件自带的反向引用表 | `src/data_interface/reverse_reference.rs` 用的那一套点查 |
| 上级各级的位置和方向 | 沿属主链逐级读 `POS`、`ORI` | vendor/e3d-model `src/transform.rs:52`（`PLACEMENT_ATTRIBUTES`）、`:89`（`world_matrix`） |
| 哪些属性算纯元数据 | 两个戳；属性字典的变化类；生成读取集合；rs-server 交来的「提资读取清单」（新） | `attribute_is_cache_stamp`、`raw_dchc_code`、`generation_read_set` |
| 上一次提资的基准 | 版本记录（rs-server 写）：「提资时的会话号」，没有时用指纹里的会话号 | gen-model 已有的两处读法（§2.1） |
| 被删掉或改名的已提资单元原来叫什么 | 交付删除记录（gen-model 的增量写） | `datacenter_delete_reader` |
| 当前一侧取哪个会话 | 这个库的应用水位 | 预览应答里的 `applied_sesno`（`docs/specs/web-service-api.md:235`） |

名称口径不读任务变更清单、任务回执这些 refno 口径的产物。它和现有管线共用的是同一份库文件和同一套读法，不是互相的输出。
用户原话里的「对现在增量更新的数据进行一遍后处理」，落到实现上是「对同一份源数据换一种认法再算一遍」。

## 5. 算法

### 5.1 底层：同一个库的两个会话之间按名称对比（显式两会话入口）

输入：库号、基准会话 A、目标会话 B、范围（若干节点，缺省是整个库）。

1. **校验并打开两侧**。A、B 都要在这个库文件的会话链上，A 在 B 之前（按链上的先后，不按数字大小）。打开两侧各自钉住的只读视图。
2. **建名称表**。每一侧扫一遍，得到「名称 → 参考号」的表；名称只去首尾空白。逐个名称归类：真实名字，或自动命名（命中前缀清单）。
   一侧里同一个真实名字对到多个元素的，记为重名，不参与配对，放进结果的重名清单（D14）；它们所在的单元按修改处理（P14）。
   名称表进进程内缓存，键是（库号、会话号、文件身份）。
3. **圈范围**。给了节点的，只看这些节点子树里的元素；一个名称只要有一侧落在范围里就算在范围内。
4. **找出动过的有名构件**。没动过的一律是未修改，缺省不出行，只计数。下面几种都算动过：
   - A→B 的索引差分候选（新增、删除、修改的参考号），各自沿属主链往上找到所属的有名构件（含自己；走到所在单元的根为止，P2）。
   - 只在一侧出现的名称；两侧参考号不同的名称。
   - 候选是上级容器，而且它的位置或方向变了：它下面每个有真实名字的单元（D21）。
   - 候选是有名构件，而且它改了名：同库里引用它的元素所属的有名构件（D23），用反向引用表找。
   - 候选身上变的是清单声明「从上级读」「经引用读」的属性：读它的那些单元（D21，清单到位之后才有）。
5. **逐个名称给类别**：
   - 只在 B 侧有：**新增**。如果这个元素（按参考号）在 A 侧叫另一个真实名字，而且那个旧名称在 B 侧已经没有了，这是改名，
     行上写 `renamed_from`，旧名称那一行写 `renamed_to`（D10）。
   - 只在 A 侧有：**删除**。
   - 两侧都有、类型相同：比内容（§5.2）。相同是**未修改**，不同是**修改**并附变化摘要。两侧参考号不同就标**换号**，写上旧参考号、新参考号。
     这个构件挪到了另一个有名祖先下面，或者挪进了另一个单元，直接判修改，摘要里写旧的和新的（D24、P9）。
     上级只是改了名（还是那个元素，参考号没变）不算挪动，下面的构件不因此判修改（P9）。
   - 两侧都有、类型不同：不配对。A 侧那个记删除，B 侧那个记新增，都标类型变了（D25、P10）。
6. **归到单元**。每一行沿属主链往上找最近的、类型属于最小交付单元的祖先（含自己）。删除的行用 A 侧的归属。
   - 这个单元有真实名字：写在行上。
   - 这个单元没有真实名字：行上的所属单元为空，标明原因（P1）。
   - 不在任何单元里（SITE、ZONE、PIPE 这些容器）：所属单元为空。
7. **按单元汇总**。只给有真实名字的单元出汇总（D17）。类别：单元自己那一行是新增或删除就取它；否则属于它的行里有一行不是未修改，就是修改；
   都是未修改，就是未修改（D18、P3）。单元的换号标注取它自己那一行的。
8. **跨库提示**。对新增、删除两类行，查一下别的库里现在有没有同名元素，有就列在提示里。只提示，不配对（D3）。

改名之后旧名称又被别的新构件占用，不需要特别处理：按名称看，旧名称两侧都有（参考号不同），照「两侧都有」比内容；新名称只在 B 侧有，是新增。

### 5.2 内容怎么比

一个有名构件在某个会话的「内容」由下面几样组成。两侧的内容逐项相同才算未修改。

1. **它自己的类型和属性**。取它存的全部属性，去掉纯元数据。纯元数据在清单到位之前只有 `CACHID`、`SPAMAP`；到位之后按三条判定（D7、D20）。
   `NAME` 本身不参与（名称相同是配对的前提）。
2. **引用类属性换成目标的描述再比**，不比参考号（D23）。引用数组逐项这样处理。属主不当作普通的引用比：挪到了另一个有名祖先或另一个单元下面才判修改，
   上级只是改名不算（§5.1 第 5 步，P9）；上级的名称变了算不算单元的修改，归第 6 项。
3. **名下没有真实名字的成员，按成员顺序**（D8、D19）。无名的和自动命名的成员，各取类型和属性（同样去掉纯元数据、引用换成目标的描述），
   再递归到它的成员。不带成员自己的参考号；自动命名成员的名称也不参与。所以成员换号而内容、顺序都没变时，两侧相同；
   成员有增、删、改，或者顺序变了，两侧不同。
4. **下面的有名成员只占一个位置**（D18）：记类型和名称，它自己的内容在它自己那一行里比。
5. **下面没有真实名字的交付单元不占位置**（P2）。
6. **单元自己那一行另外带上上级的位置**（D21）：从单元往上各级的位置和方向。清单到位之后，再带上清单声明从上级读、经引用读的那些属性；
   提资读了上级的名称的话，上级的名称就在其中，所以上级改名要到清单到位之后才算进单元的修改（§11 第 12 条）。

两侧不同时，并排走一遍两侧的结构，把前若干处差异写成变化摘要：哪个属性从什么变成什么、第几个成员增了删了改了、顺序变了、哪一级上级动了。
摘要有条数上限，超出时标明被截断。

内容相同与否可以先各算一个摘要值来比，只有不同时才并排走。摘要值只在一次请求里用，不落库，也不当作对外的指纹。

读不出来、判不了的，一律判修改，不判未修改。

### 5.3 缺省入口：以上一次提资为基准

输入：库号、范围（若干节点，通常就是提资请求里选中的那些根）。目标会话取这个库的应用水位（D22）；这个库还没有入库时报错（P11）。

1. 列出范围里当前有真实名字的单元（类型属于最小交付单元，P4）。没有真实名字的单元只计数（D17）。
2. 批量读这些单元的版本记录，再读这个库的交付删除记录。
3. 逐个单元找基准：
   - **有版本记录**：先用「提资时的会话号」；没有这个数就用指纹里的会话号；两个都没有，按已修改处理，标注「没有基准」（D16）。
   - **基准会话不在会话链上**：按已修改处理，标注原因（D27）。
   - **没有版本记录，但被它接替的旧单元有**（P7）：用旧参考号版本记录上的基准，拿旧单元在基准时的子树和新单元现在的子树按名称对比。
     行上写旧参考号、新参考号，标换号。
   - **都没有**：从未提资过，单元和属于它的行都是新增，并标「从未提资」。
4. 把单元按基准会话分组，每组做一次 §5.1 的对比，范围是这一组单元的子树。
5. 已提资、现在已经不叫原来那个名称、也没有被接替的单元：旧名称出一行删除。元素还在、只是改了名的，新名称那一行是新增，两行互相指明（P3）。
6. 跨单元对账。各单元的基准不同，下面两种情形要多做一步，否则同一个名称会出两行：一个有名构件从一个单元挪到了另一个单元，并成一行修改（D24）；
   改名之后旧名称被别的新构件占用，以接替为准，被接替的名称不再出删除那一行。
7. 汇总、分页、返回。应答里带上本次的目标会话号、每个单元用的基准会话号和它的来源。

缺省入口不出这些行：容器（D27）；所在单元没有真实名字的有名构件（P1）。

### 5.4 待删除列表的「已被接替」

`GET /api/v1/datacenter/deletes` 的每一行，读的时候现算一个标记：这条记录所在的库里，现在有没有一个叫这个旧位号、类型相同、有真实名字的单元，
而且它的参考号与记录上的不同。有，就标为已被接替，并给出接替它的新参考号。记录的原因是删除还是改名都算（P7）。标记不落库。接口的其它字段不变。

## 6. 接口草案

路径暂定 `GET /api/v1/name-diff`（D29），只读，鉴权和身份字段与 `/api/v1` 其它接口相同。枚举值用小写下划线。字段名是草案，实现时可以调整，
调整后写进接口规格。

**入参（查询串）**

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `dbnum` | 是 | 库号 |
| `refno` | 否 | 范围节点，`a/b` 形式，可重复。不给就是整个库。给上级节点，不逐个列单元 |
| `a`、`b` | 否 | 基准会话号、目标会话号。两个都给：显式对比这两个会话。两个都不给：缺省入口，基准读版本记录，目标取应用水位。只给一个：400 |
| `category` | 否 | 只要某几类，逗号分隔：`added`、`deleted`、`modified`、`unchanged` |
| `unchanged` | 否 | 未修改的行出不出。`renumbered`（缺省，只出换了号的）、`all`、`none` |
| `rows` | 否 | `1`（缺省）出元素行；`0` 只出单元汇总。rs-server 提资时用 `0` |
| `limit`、`cursor` | 否 | 分页。`limit` 缺省 500，上限 5000，与接口规格（`docs/specs/web-service-api.md`）§4.15 那一族接口相同 |

**出参**

| 字段 | 说明 |
| --- | --- |
| `dbnum`、`baseline`、`target_sesno` | 库号；基准方式（`published` 或 `sessions`）；本次的目标会话号 |
| `rules` | 本次用的规则：自动命名的前缀清单；纯元数据用的是哪一份（只有两个戳，或清单的版本）。两边联调时用来确认用的是同一份 |
| `counts` | 各类行数，另有换号数、从未提资数 |
| `units[]` | 每个有真实名字的单元一条：`refno`、`noun`、`name`、`category`、`old_refno`、`new_refno`、`renumbered`、`never_published`、`renamed_from`、`baseline_sesno`、`baseline_source`（提资时的会话号、指纹里的会话号、被接替单元的记录）、`baseline_problem`（没有基准、基准不在会话链上）、属于它的各类行数 |
| `rows[]` | 每个有名构件一行：`name`、`noun`、`category`、`old_refno`、`new_refno`、`renumbered`、`never_published`、`unit{refno, noun, name}`（可为空）、`unit_scope`（所属单元为空时说明原因：不在任何单元里，或所在单元没有真实名字）、`changes[]`（变化摘要）、`changes_truncated`、`renamed_from` 或 `renamed_to`、`moved_from`（旧属主、旧单元）、`noun_changed` |
| `duplicates[]` | 重名：名称、在哪一侧、对到哪几个参考号 |
| `same_name_elsewhere[]` | 别的库里的同名元素：名称、库号、参考号 |
| `skipped` | 被跳过的数量：没有名字的元素、自动命名的元素、没有真实名字的单元 |
| `truncated`、`next_cursor`、`elapsed_ms`、`warnings` | 分页与观测 |

一行的例子（示意）：

```json
{ "name": "/1RCV0102A/B1", "noun": "BRAN", "category": "unchanged",
  "old_refno": "24383/73959", "new_refno": "24383/80012", "renumbered": true,
  "unit": { "refno": "24383/80012", "noun": "BRAN", "name": "/1RCV0102A/B1" },
  "changes": [] }
```

**错误情形**（沿用接口规格 §4.15 那一族接口的错误码）

| HTTP | 错误码 | 何时 |
| --- | --- | --- |
| 400 | `bad_request` | 缺 `dbnum`；`a`、`b` 只给了一个；`category` 写错 |
| 400 | `INVALID_REFNO` / `INVALID_VERSION_PAIR` | `refno` 解不出；`a` 不在 `b` 之前 |
| 404 | `REFNO_NOT_FOUND` / `SESSION_NOT_FOUND` | 范围节点两侧都不存在；显式给的会话号不在会话链上 |
| 503 | `SOURCE_NOT_FOUND` | 这个库的文件不在 |
| 504 | `COMPUTATION_TIMEOUT` | 超过 300 秒 |
| 实现时定 | 实现时定 | 缺省入口下这个库还没有入库（P11） |

缺省入口下，单个单元找不到基准不是错误，体现在那个单元的 `baseline_problem` 上。

## 7. 与 rs-server、plant-ui 的契约

**rs-server 要改的**

1. **两条路径并存**（D17、P5）。
   - 提资请求进来、提取数据之前，按库向 gen-model 的缺省入口问一次（范围是请求里选中的根节点，`rows=0`），
     记下每个库的目标会话号和每个单元的类别。目标会话号要取提取之前问到的这一个：宁可偏旧，不可偏新，
     道理同现有的「提取前指纹」（rs-server `src/datacenter/publish_state.rs:16-19`）。请求涉及多个库时按库各问一次（P12）。
   - 结果里有的单元：类别是未修改的跳过，其余照发。不再看版本记录的状态：`status='Modify'` 是 gen-model 的增量按 refno 口径标的，
     纯元数据的改动也会标。
   - 结果里没有的单元：原样走现有路径，这条路径的判断逻辑不改。
   - 现有的「不发」过滤（§2.3）不动，先于类别生效。
   - gen-model 调不通：全部走现有路径，并在回执里说明这一次没有用名称口径。
   - #92 设想的「内容指纹」不做；现有的指纹照旧对所有单元计算和登记。
2. **换号且未修改的单元**：不提资；不为旧参考号推送删除（勾选的、服务端补的、改名带出的三种来源都要排除）；
   把版本记录从旧参考号转到新参考号，实例编码和版本号沿用，「提资时的会话号」写成这次的目标会话号；删掉旧参考号的交付删除记录。
   新记录上的指纹用这次请求里给新参考号算的那一份；拿不到就留空，留空的记录在现有路径上按已变更处理，是安全的。
3. **换号且修改的单元**：按原位号重发，当作这个实例的修改而不是新增，版本号接着旧记录的往下走；不为旧参考号推送删除；
   提资成功后版本记录落在新参考号上，旧参考号的版本记录和交付删除记录删掉。中台上旧参考号编码的无名子件不处理（D26）。
   第 2、3 两条里版本记录的转移都在一个事务里做完，不能出现新旧两条都在、或者两条都不在的中间状态；现有的提资确认本来就是一个事务
   （rs-server `src/datacenter/mod.rs:1083-1084`）。
4. **提资成功时写「提资时的会话号」**（D16、P6）：取第 1 步问到的目标会话号。这一次没有问到的（gen-model 调不通），把这个字段清空。
5. **建议：跳过的单元刷新版本记录**。判为未修改而跳过的单元，把状态写回 `Insert`，把「提资时的会话号」前移到这一次的目标会话号；指纹不动。
   内容等价，所以前移是对的。好处有两个：下一次对比的会话区间不会越拉越长；状态不会一直停在 `Modify`。
   指纹不动，是为了以后万一落到现有路径上时最多多发一次，不会漏发。不做这一条也正确。预览不写任何东西。
6. **出一份「提资读取清单」**（D20）：用脚本从 `src/datacenter/` 的源码扫出提资读了哪些属性。每一条写明属性名、读它的元素类型、怎么读到的
   （直接读、从上级读、经哪个引用读）。加护栏测试，提资代码新增读点时清单跟着变。清单文件交给 gen-model 收进仓库。
7. **提资预览**（#100）按类别展示，经现有的预览接口出（D29）。预览不写任何东西；应答里带上 gen-model 给的目标会话号。
   预览和真正提资之间库可能前进，靠这个会话号发现：真正提资时如果目标会话号与预览时的不同，提示重新预览（plant-ui 第 3 条）。

**plant-ui 要改的**

1. 提资预览分类展示：跳过（未修改，其中换号的单独计数）、重发（修改）、首次提资（新增且从未提资）、删除。改名的单元沿用 #98 已有的改名影响一栏。
   结果之外的单元单独一栏，只分照发和跳过（P13）。能展开看到具体单元。
2. 删除确认和待删除列表里，已被接替的记录要能看出来，并且缺省不勾选。
3. 预览之后库可能又前进了：真正提资时如果目标会话号与预览时的不同，提示重新预览（#100 定稿评论的第 4 条）。
   预览时的目标会话号取自预览应答，真正提资时的是 rs-server 提取之前问到的那一个（rs-server 第 1 步）。
   真正提资总是按当时问到的结果办，所以这一条管的是用户看到的和实际提交的对不对得上，不影响提资本身对不对。
   两个会话号在哪一步比、提示之后这一次提资还继不继续，票里没有写，随 #100 的实现定。

**gen-model 对外的承诺**

1. 同一个目标会话号、同一份规则下，同样的入参得到同样的结果。
2. 只读：这条接口不写任何表。gen-model 的增量照旧标版本记录的状态、照旧写交付删除记录。
3. 判不了的一律往「修改」靠：没有基准、基准不在会话链上、重名、读不出来，都不会判成未修改。
4. 结果里没有的单元，就是名称口径不管的单元，调用方按现有路径处理。

### 9.2 其它验收

- **与实际几何对照**：每条用例里，对判为未修改的单元，两侧各生成一遍几何，比网格内容键、世界变换、包围盒，应当全等；对因几何属性而判为修改的，应当不等。
  这是测试里的对照，不是接口的做法。
- **与 refno 口径并存**：跑完八条用例后，任务变更清单、任务回执、模型记录与加这条接口之前逐项相同。
- **只读**：接口调用前后，版本记录、交付删除记录两张表的内容不变。
- **重名、同名不同类型**：用构造的两侧名称表验证（E3D 里造不出同库重名）。
- **缺省入口的基准情形**：有「提资时的会话号」、只有指纹里的会话号、两个都没有、基准不在会话链上、接替、从未提资，各一条。
- **单元之外的变化**：上级 ZONE 移动后，下面有真实名字的单元判修改；同库里被引用对象改名后，引用方判修改。
  上级只是改名（例如所属 PIPE 改名）：下面的有名构件不判成换了属主；清单到位之前下面的单元未修改，
  到位之后提资读了这个名称的单元判修改（P9、S3）。
- **两条路径并存**（T9 之后）：结果之外的单元，发与不发、跳与不跳，与改动前逐项相同。
- **端到端**（T10 之后）：用例 2 提资后中台既不收到这个位号的删除，也不收到再次提资；用例 4 中台收到这个位号的修改，收不到删除。
  证据取 rs-server 组好的提资内容，不必真的推到中台。

## 10. 不做

- 不改现有的增量处理、任务变更清单、任务回执、模型落库和现有接口。
- 不把名称口径的结果落库，也不存基准内容的快照。
- 不做跨库配对。
- 不给无名元素、自动命名元素单独认身份。
- 不把没有真实名字的单元纳入结果，也不改 rs-server 对它们的做法（D17）。
- 不为判定而重新生成几何。
- 不比目录库的内容（目标名称相同就算相同）。
- 不为无名子件的编码做任何处理（D15、D26）。
- 不改 rs-server 现有的「不发」过滤，不统一两边对自动命名的判法（D28）。
- 不改 #97 的改名提资。
- 不改 plant3d-web 的增量记录页。

## 11. 已知后果

1. **无名子件在中台上留着旧参考号**。单元换号后，不管是被跳过还是重发，中台上用旧参考号当编码的无名子件都留着（D15、D26，用户已定）。
2. **没有真实名字的单元享受不到名称口径**（D17）。其中今天照常提资的那些，子树里任何写入都会重发，换号会被当成首次提资，与今天一样。
   开发库里自动命名的 BRAN 有 589 个，按今天的代码照常提资；自动命名的 EQUI 有 937 个，今天不提资；自动命名的 HANG 有 24 个，
   rs-server 不把 HANG 当提资单元（§2.3、§2.4）。
3. **目录库的盲区**。规格件、目录件的名称没变而内容变了，名称口径看不出来。今天 rs-server 的指纹同样看不出来。
4. **类型不属于最小交付单元的提资单元不在结果里**。工艺、仪控的支吊架（ZONE）和电气的接地、部分电缆支架（STRU）继续走现有路径（P4）。
   补不补这个缺口，等 S5 数出这类单元有多少之后由用户定（§3.4 确认二）。
5. **改名是两行**。同一个构件改名后在结果里是一行删除、一行新增。
6. **重名时宁可不配**。重名的构件没有类别，只出现在重名清单里；所在单元按修改处理。
7. **换号的构件照样重新生成**。名称口径省的是提资，不省模型生成：现有管线仍按新参考号重新生成、落库。
8. **版本记录的状态会和类别对不上**。gen-model 的增量照旧把被改动的单元标成 `Modify`，哪怕名称口径判它未修改。做了 §7 第 5 条的刷新就不会。
9. **旧记录退回基准时有一个盲区**。只有指纹里的会话号的旧记录，如果在那个会话和实际提资之间，单元之外的东西变过（比如上级移动），
   提资之后又改回去，会被判成未修改，而中台上存的是变过之后的内容。今天的指纹同样看不出这种变化；这条记录重发过一次之后就有了准确的基准。
10. **算不回去的基准**。库的会话被合并之后，旧的基准会话读不回来，这些单元只能按已修改处理一次（D27）。
11. **复制后只把单元改回原名、成员还叫 Copy-of 的，判修改**。成员在基准一侧是有名成员，现在是自动命名，内容对不上；它们原来的名称各出一行删除。
12. **清单到位之前，提资从上级读的属性变了看不出来**。比如 PIPE、ZONE、SITE 改名。今天也看不出来（D21 的后一半要等清单）。
    上级只是改名不算下面的构件换了属主（P9），所以这种变化只能靠清单发现。这与 §5.1 第 5 步不冲突：那一步说的是构件挪到了别的属主下面。
13. **第一次冷算有代价**。整库范围要各扫一遍两侧的名称表；缺省入口每个不同的基准会话要建一张名称表。超过 300 秒回 504。
