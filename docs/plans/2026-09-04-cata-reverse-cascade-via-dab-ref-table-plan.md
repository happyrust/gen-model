## 1. 现状与目标（一句话各一条）

- **现状**：direct 形态下 CATA 会话推进 → `ModelTarget.catalogue` 指纹失配 → 下一次 `ensure`
  碰到哪个根就整根重算哪个，**整库全部根都算过期**；启动复核则对 CATA 完全零感知，
  2026-09-04 只补了「点名」（`catalogue_cascade_degraded`，§2.7），没排任何工作。
- **目标**：拿到 CATA 窗口变动的目录件集合，反查「哪些设计件经引用属性指向它们」，
  只把这些设计件所在的生成根排进重算；其余根**凭证前移，不动几何**。

## 2. core 的做法（本计划照抄的那条，取证见 §2.11）

dabacon 文件自带一张**按 (属性, 目标 ref) 有序**的引用表，按库文件存；core 用三个原语点查它：

| opcode | 名字 | 用途 |
|---:|---|---|
| 326 | `db_start_ref_table_search(dbno, attId, targetRef, &handle)` | 起一次游标 |
| 328 | `db_get_next_ref_table_entry(handle, &entry, &key)` | 取下一条 |
| 192 | `db_finish_table_search(handle)` | 收工 |

`DB_MDB::findElements(dbType, refAttr, target)`（core.dll `0x59f4720`）就是「逐 db（按 `db_type`
过滤）起游标 → 取到键变了为止」。**不扫库、不建内存表。**

## 4. 不做什么

- 不动 `ModelTarget.catalogue` 指纹本身：它是「这根是照哪版目录算的」的记录，
  反查是**选根**，两件事不合并。
- 不复刻 core 的 UDA 依赖递归与 `XRPNTR` 正向扩散（ADR-061 已定不做）。
- 不在本计划里碰第 3 类（改挂新旧两根）——那是 09-02 计划 P1-1 的 ledger `Reparented` 补排。

## 5. 退路与风险

| 风险 | 处置 |
|---|---|
| **P0 读不出页布局**（最大风险） | 转 09-02 计划原定的 ②：开库时一次全库扫描建内存反向表。P2/P3/P4 一个字不用改——它们只依赖「给我一个 refno 的引用者」这个接口，不依赖它怎么实现 |
| 引用表可能不含某些引用属性 | P0 的「与全库扫描逐键相等」那道门就是查这个；不等就按「这些属性走扫描、其余走表」混合，或整体退 ② |
| 反查把范围收得过窄 → 陈旧几何 | 护栏是**不对称**的：判不了一律按「影响全部根」，宁可多算 |
| 目录库巨大（`ams7351` 334 万候选） | 正是选 ① 的理由；② 在这种库上是分钟级 |
