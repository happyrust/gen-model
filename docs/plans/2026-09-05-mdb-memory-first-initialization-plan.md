## 0. 一句话

模型面已经是「生成只写内存、适配器负责落库」（`model_memory_store` + `model_db_adapter`）。
本计划对**数据面**做两件事：**内存里只放服务自己要用的关键信息**（不是整份数据），
**库退到关键路径之外当异步备份**。分三层，每层各自可用、可回退。

### 1.1 各档粒度的实测代价（`bin/mdb_memory_probe`，release，串行）

`AvevaMarineSample /ALL`：声明 29 个 DESI，盘上 28 个，**611,345 个元素、文件合计 301.4 MiB**。

| 档 | 装什么 | 串行墙钟 | 按库并行下界 | 常驻 RSS | 每元素 |
|---|---|---|---|---|---|
| `index` | refno 清单 + ref0→dbnum | 0.46s | 0.01s | 5.3 MiB | 9 B |
| **`header`（今天的骨架）** | **加上 noun + owner** | **0.72s** | 0.10s | **19.8 MiB** | **34 B** |
| **`named`（Q1c 的候选）** | **再加上存储的 `NAME`** | **1.13s** | 0.25s | **50.4 MiB** | **86 B** |
| ~~`extract`~~ | ~~每元素整张属性表~~ | 8.02s | 2.92s | **1291 MiB** | 2215 B |

`NAME` 那一格的价钱是 **+0.41s / +30.6 MiB**，而它换掉的是树路径上最后一次逐元素读属性表。
`named` 与 `extract` 差 **26 倍内存**——这正是「关键信息」与「全属性」的分界线在数字上的样子。

**`extract` 那一行是被否决的那条路的价钱，留在这里当理由，不是待选项。** 全属性常驻是文件
体积的 4.3 倍，而那 2215 B/元素里大半是 per-element `HashMap<String, NamedAttrValue>` 的
表示开销（同一个 noun 的几十个属性名在库里重复了十万遍）。**时间从来不是问题**——最贵那档
串行也只要 8 秒；被否决的理由是内存，以及「服务本来就不需要全属性常驻」。

原始数据：`out/q5-20260905/{index,header,extract,owner-parity}.json`。

### 1.2 P0 已落地的东西

`src/data_interface/mdb_memory_store.rs`：进程级 `MdbMemoryStore`，装 `ref0→dbnum` 归属、
`refno→owner`、`refno→noun_hash` 三张表，启动时在 `init_mdb` 之后预热（`lib.rs`），
失败只告警、退回按需现建。三处接线：

| 位置 | 改前 | 改后 |
|---|---|---|
| `DirectTreeService::open` | 第一次树请求时逐库 `indexed_refnos()` | 骨架现成，一次 `Arc` 克隆 |
| `roots()` | `DirectStore::indexes()`——每库一次全树扫描 + 描述符抽取 | 骨架 noun 表 O(1) |
| `ancestors()` | 每上一级抽一整条记录 + 转一张属性表 | 骨架属主表，零解析 |

**验证**：`cargo test --lib` 1524 passed / 0 failed；属主对账 611,345 元素零分歧
（记录头自报的属主 == 属性表的 `OWNER`）；全树快照 37 个 SITE 根 / 402,229 节点 / 12.6s，
37 与改动前记录的基线一致。**未 live**（服务没启过）。

## 2. 设计：三层，各自独立可用

### 2.1 L1 · 关键信息骨架（P0 已落地，边界待收口）

常驻的只有**服务自己判断时要用的那几格**：noun、owner、ref0 归属。属性按需走
`direct_store`（ADR-053），池级缓存归它管（ADR-059）。

**「关键信息」到底包含什么，是 P2 要收口的**（§3 Q1c）。今天三格；候选的第四格是 `NAME`——
树面板显示它、生成根回执带它，实测 **+0.41s / +30.6 MiB**（§1.1）。除此之外**默认不进**：
每加一格都要说得出「谁在热路径上读它、不常驻要付什么」。

### 2.2 L2 · 选根照 core.dll 的四道过滤（P1）

core 判「这个节点有没有几何」**从来不看元素，只看它 noun 的字典位**——
`DB_Noun::getInt(fieldId)` 是一次内存表查找。而 noun 与 owner 恰好就是 L1 已经装好的两样。

core 的四道过滤（取证 `docs/2026-09-04_model-cascade-update-inventory.md` §2.1–§2.3、
`docs/evidence/2026-09-04-ida-core3d-partial-update-recheck.md` §3–§4）：

1. **库级**：只吃 `DB_DB::type ∈ {1,6}` = DESI + ISOD，CATA 根本不进重画路。
2. **noun 级**：`重画 el ⟺ el.type ∉ {WORL,MNUM} ∧ ( gb(el) ∉ {1,2} ∨ ( gb(el)==1 ∧ gb(owner) ∉ {1,2} ) )`
3. **祖先抢占**：结果集里 owner 也在集合中的元素不发事件，只发最顶那几个。
4. **新建只建顶**：`isElementTopLevelCreate`。

我方 `generation_roots_in_subtree` 与之对照，三处可换：

| 环节 | 今天 | 改后 |
|---|---|---|
| 祖先链上卷取 `TYPE` | 每级抽整条记录 + 转属性表 | 骨架 `noun_hash` → 字典位，零抽取 |
| 子树 DFS 判根 | 每节点读一张属性表 | 先查位；**只有真出根的才读 `NAME`**（`NAME` 若进 L1 则连这次也省了） |
| 剪枝 | 无，全树走到底 | `gb==2` 只穿过、`gb==1` 整棵不进（109 + 98 个 noun） |

两条不能弄错：

- **`gb==1` 的降级只看属主一层。** 上溯多层那条是 `DES_DrawList::isGraphicsIgnoredBetween`，
  作用在绘制清单环节，**两条并存，不许合成一条**。
- **几何粒度位是 `significant` 不是 `toplevel`。** TOPF 那 211 个管的是绘制清单成员与显示
  属性归属，19 个调用方里 13 个是 `get/setPrimitiveOrTOPF{Colour,…}`，**一个几何重算消费者都没有**。
  我方用 `noun_is_significant` 是对的，且有正面证据（`ExistsCPS` → `SignificantOwner`）。

成员表骨架里没有（头扫描不解析它），所以 DFS 仍要走 `direct_store` 拿成员原序——
但上面三处都不依赖成员表。

### 2.3 L3 · 库退到关键路径之外，当异步备份（P3–P4，**未拍板**）

**这一节按 2026-09-05 批注重写过。** 原来写的是「整份数据进内存、内存为真、库是镜像」；
批注否掉了前半。改后的形状是：

```
              ┌─ L1 关键信息（noun/owner/归属[/NAME]）── 服务自己判断用
   e3d-io ────┤
   （文件）    ├─ direct_store 按需属性 ─────────────── 生成 / 树 / 接口用
              │
              └─ ElementRows 渲染 ──→ 异步写 SurrealDB ── 备份 + 遗留读者用
```

**内存不是库的数据源，文件才是。** 库那一份继续由现成的 `ele_ops::ElementRows` 渲染
（基线与增量共用同一份行渲染），真正要动的只有两件：**把它从启动关键路径挪走**，
**让它的滞后可观测**。这比原方案省掉整个「内存 → 库」的同步语义。

## 5. 新不变量

- **N1 骨架只装关键信息。** 属性一旦悄悄进来，19.8 MiB 变 1.29 GiB，而涨的那一天没有任何
  东西会说话。已有护栏 `the_skeleton_holds_no_attributes` 钉住 `ElementRow` 大小；
  Q1c 若给 `NAME` 放行，护栏的上限跟着改一次，**并且只改这一次**。
- **N2 骨架与 `DirectStore` 钉同一个会话。** 两边一起旧，不许一半新一半旧。
- **N3 属主只有一个真值。** 骨架走记录头、`direct_store` 走属性表，两者必须逐元素相等
  （`--tier owner-parity`，本轮 611,345 零分歧）。
- **N4 选根判据只有一份。** L2 改造不得在 `direct_tree.rs` 里养第二段 DFS；
  已有源码钉护栏 `direct_tree_root_enumeration_is_the_shared_traversal`。
- **N5 备份滞后必须说得出来。** L3 之后 `pe` 是滞后视图，读它的接口要么改口、要么标注。
- **N6 库不是内存的镜像，两者各自从文件来。** 少了这一条，下一个人会去写「内存 → 库」的
  同步器，而那正是 §2.3 改写掉的东西。

## 6. 风险与不做

- **最大的风险不是内存，是 Q2。** 不解决就上 L3，症状是「库里查得到但不是最新」，
  而且没有任何东西会报出来。
- **L2 的剪枝改的是「走不走」不是「判不判」。** 逐根对拍不通过就整条回退，
  不许「差几个根应该没关系」。
- **不做**：**全属性常驻**（Q1b 已否决）；不动 ADR-058 D3 的基线（L3 定案前）；
  不碰 `toplevel` 那一侧的选根口径（§2.2 已证它管的是显示属性归属）；本计划不碰 plant-ui。
