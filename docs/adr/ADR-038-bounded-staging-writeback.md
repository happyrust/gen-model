# ADR-038：暂存写回必须多维分块并有单查询停滞边界

## 状态

已接受（2026-08-19）。补充 ADR-017；引用 ADR-001、ADR-011、ADR-025、ADR-034。

## 背景

`dbnum=8000 / sesno=239` 的复制保存产生 167 条 journal、约 119 KiB SQL、预计
869 行。旧实现只按 500 条语句分块，因而把整个 journal 包成一个事务。SurrealDB
持续单核计算且查询 future 超过十分钟不返回；控制台虽每十秒报告等待，但没有块级
进展或查询停滞边界，水位停在 238，任务永久保持 `running/commit`。

## 决策

1. 普通 journal 同时受语句数、SQL 字节数和预计写入行数约束；任一上限命中即切块。
2. 已显式声明事务的 journal 条目保持原子，不拆开，但独占一个写回块。
3. 每块执行前打印序号、尺寸、预计行、事务类型和非敏感指纹；成功后刷新任务的
   `stage_last_progress_at` 与事件数。
4. 单个持久层查询连续 120 秒不返回即使本窗口失败。超时不是可无限重试的传输错误；
   水位不推进，窗口按 ADR-017 丢弃，后续由权威文件区间幂等重放。
5. 尾事务仍最后执行，分块成功不代表水位承诺；只有尾事务成功才完成窗口。

## 后果

- 大复制保存不再形成按“语句数看很小、按行数实际很大”的单事务。
- 若显式事务本身卡住，日志能唯一定位其块与指纹，并在有界时间内形成失败回执。
- 分块可能在尾事务前留下已提交的幂等中间写；水位保持旧值，整窗口重放收敛。
