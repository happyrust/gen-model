# ADR-017：稳态增量窗口在 kv-mem 暂存、整窗口写回 RocksDB

> 2026-08-19 补充：写回分块不能只按 journal 条数计算；多维上限、块级进展和
> 单查询停滞边界由 ADR-038 规定。

状态：Accepted（2026-08-05）
关联：ADR-001（水位）、ADR-010（房间归属）、ADR-011（数据批次队列）、ADR-012（合批重生成，不受影响）、ADR-013（生成结果与 pending 分离）、ADR-014（BRAN 原子替换，被本 ADR 部分取代）；CONTEXT.md「暂存与写回」章节；开发方案 `docs/plans/2026-08-05-staged-increment-kvmem-write-back-plan.md`

## 背景

今天的稳态增量窗口不是原子的：`persist_latest_main_data` 按 `TX_CHUNK=500` 分块提交，模型生成按 BRAN 级事务落库（ADR-014），房间按任务级事务落库。正确性由「幂等重放 + 失败不推水位」保证（ADR-001），但共享 SurrealDB 服务器上的其他读者（viewer / 材料表 / plant-ui）在分钟级的执行窗口内会读到半批属性、新旧混合的模型；失败或崩溃后的半写数据在重放收敛前一直可见。业主裁定这类中间态为「数据污染」，要求：**一个稳态增量窗口在全部计算（解析、全部生成根、房间）完成并确认之前，持久层零落盘**。这触发了 ADR-014 预留的 revisit 条款（「若观看端将来明确要求整根快照一致，再以该需求为依据升级原子边界」），且把原子边界一次升到了整窗口。

## 决策

1. **提交单元与"不落盘"不变量**。稳态增量窗口（dbnum × 会话区间）的解析数据及其全部生成根的模型产物构成一个提交单元；写回成功之前持久层（rocksdb 后端的 SurrealDB 服务器）看不到其中任何一笔写入。房间归属是提交后的派生数据：尾事务只原子登记其 durable pending，不把房间结果放进 kv-mem 提交单元。数据可见性与模型生成成败绑定是本 ADR 的自觉选择：任何一个生成根重试穷尽仍失败 → **窗口阻断**（水位不动、持久层零痕迹、告警常驻），唯一解除方式是修复源数据后重存，新会话按冻结吸收并入同一窗口重算。**不提供自动或人工的降级提交**。

2. **暂存介质**。进程内常驻一个嵌入式 SurrealDB 内存实例（`Surreal<Any>` 指向 `mem://`，fork SDK 开 `kv-mem` feature；与 `SUL_DB` 并列的新静态句柄）。每个提交单元一个独立 staging database（`staging_{dbnum}_{window_id}`，window_id 进程内单调分配；窗口的逻辑会话区间记在元数据里，冻结吸收扩窗**不改名**）。同一批次内失败根可在原暂存工作集重试；跨批次或进程崩溃后重新构造完整窗口。提交或废弃后整库 DROP，窗口终态按进程内登记表清扫残留。暂存资源（行数 + 字节 + journal 字节）受三级状态机治理：告警阈值只告警、更高阈值拒绝吸收扩窗、极限阈值废弃暂存并转入资源阻断告警——不允许走到 OOM。

3. **读路由四则**（窗口计算期间）：
   - ① 设计 / 目录基础数据：**不从持久层复制**，按需部分解析文件进暂存库——生成根闭包 = 根子树 + 祖先链 + CATA 引用闭包，索引优先定位；miss → 惰性兜底定点解析后重试原查询。
   - ② 既有模型产物：按工作项预载进暂存库（根的 `inst_relate/inst_info/geo_relate/inst_geo/world_trans/aabb` 与隐含直管段旧行点查拷入）；本单元新产物直接写暂存库。生成链路「读自己写的」SQL（保存实例 → 深层可见集 → 包围盒刷新）因此零查询改动成立。
   - ③ 全局扫描 / 修补语句：标记为 **commit-time-only**，按读写集分类审计——纯终态扫描直接标注；写集与暂存读集相交的必须同时以工作集范围在暂存库执行；依赖唯一性补洞或删除后状态的必须显式定义执行顺序。写回时按其在 journal 中的原始位置对持久层执行，终态与现行为逐字一致。
   - ④ 控制面（水位、attempts、queue_control、按需与房间的 durable pending）：永不进暂存，持久层直读直写。**唯一例外是窗口前的 `dbnum_watermark` 行**：暂存读绝不回落持久层（这是规则①②的地基），窗口内任何一次读水位都会 miss，所以开窗时把它只读拷入一次（`preload_dbnum_state`，StagingOnly、不进 journal）；水位的**写**仍然只发生在持久层的尾事务里。

4. **写回协议（phase-1）**。暂存期间按执行顺序累积语句日志；写回 = TX_CHUNK 分块事务重放 + 尾事务收口（datacenter 状态、水位推进、attempt 记录清除、pending 的 revision 条件收口在持久层判真）。任何一块失败 → 水位不推、暂存保留、写回可重试；进程崩溃 → 按窗口重算。**单个巨事务不采用**：整窗口单事务撑爆 ws 通道是已记录在案的事故（`increment_pipeline.rs` TX_CHUNK 注释）。原子性口径 = 水位门控：以水位为准的读者把「半个写回」视为不存在；不经水位的读者可见秒级的写回窗口——这是 phase-1 的自觉残余，其消除见第 10 条。
   journal 语句必须满足 **ReplaySafe 规范**：record id 显式固定、不依赖随机值、不以执行时刻的全库查询结果选择写入目标（`time::now()` 只允许出现在信息性字段）；StagedExecutor 以 validator 拒绝不合规语句。恢复路径由构造互斥、无选择歧义：写回失败且进程存活 → 用内存中的 journal 重试重放；进程崩溃 → journal 随进程消失 → 唯一路径是整窗口重算，重算的 regen 删除集覆盖先前半提交行、幂等收敛（与今日崩溃重放同一纪律）。

5. **房间后置计算**。模型生成造成的 AABB 变化仍在窗口内归并为精确的 durable pending，pending 与空间意图、水位在同一尾事务提交。提交成功后执行顺序固定为：空间树收敛 → DROP kv-mem 窗口 → 本任务 scoped room drain。scoped drain 面板优先、元素按 256 条分页，只读取本任务 record id；成功按 revision 条件删除，失败保留 pending 并把任务记为 `partial`。ADR-011 §8 的全局空闲轮保留，用于崩溃恢复和历史积压。房间拓扑、关系与几何不再复制进 kv-mem；Rust 只持有当前分页与一轮复用的持久层几何索引。

6. **豁免**。基线 / 冷启动 / 全量生成路径不走暂存：新库无读者可污染、无旧模型可保护、全量产物体量超出内存预算；`finalize_baseline` 语义不变。SYS / CATA 元数据窗口没有生成环节，天然是纯解析提交单元。**「数据与模型同一提交单元」另有一档更宽的让位口径，见 2026-08-19 修订第 3 条。**

7. **CATA 按需解析产物随窗口提交**，不再直写持久层；跨重试由常驻 staging database 保证不重复解析。

8. **pending 与 attempts 重划**。窗口内工作清单活在进程内（崩溃后由窗口重放重建）；按 `(dbnum, root)` 的 attempts / 死信记录写持久层控制面（扩展 `increment_update_attempt` 恢复记录），窗口成功提交时清除该 dbnum 的全部 attempts——这个粒度是正当的：A 语义下窗口能提交**当且仅当**其全部根成功，不存在「历史失败根的记录被误清」；跨窗口派生工作的重试计数在 durable pending 自身的 attempts 字段上，互不相干。**冻结吸收扩窗时重置受影响根的 attempts**：新数据是全新的重算理由，也是「窗口阻断」的解除机制（修复源数据重存 → 新会话吸收进同一窗口 → attempts 归零 → 重算）。durable pending 保留三类使命：按需生成保护（ADR-013 判定顺序不变）、跨窗口派生工作（目录反向传播、延迟级联恢复）、房间任务积压。

9. **库外副作用纪律**。mesh 文件内容寻址、可照旧提前写（孤儿无害，重生成同哈希覆盖；长期阻断窗口反复重试可能累积孤儿 mesh，列为独立 GC 后续项，不阻塞本方案）。空间刷新/删除意图必须与水位写入同一尾事务；提交后先应用内存空间树并原子持久化项目空间树文件，成功后才能结算该意图。失败时跨重启持续重试并阻止下一数据批次出队，即使队列被人工暂停也继续完成已提交数据的收敛。MQTT 模型变更通告仍推迟到写回成功之后；进程内缓存以提交 / 废弃为失效边界。

10. **phase-2 方向（只定方向，不开工）**。fork 服务器端「暂存会话 / 长事务」：连接声明 BEGIN STAGING 后，该会话所有写进服务器内存 overlay、读 = base + overlay、其他连接只见 base，COMMIT 一次 rocksdb 原子落地。单写者（除 gen-model 外全是读者，已确认）下无提交冲突；读路由、语句日志、commit-time-only 全部被引擎吸收，应用层回到「当作普通库用」。phase-1 的语句日志接口按可被它替换的方式设计。立项前必须先压测两件事：长时间暂存会话对 rocksdb 快照钉住 / compaction 延迟 / SST 保留的影响；overlay 内存与 phase-1 暂存同量级，不因搬进服务器而消失。

## Considered Options

- **分相提交**（解析窗口 / 生成轮 / 房间轮各自为提交单元）：隔离收益相同、既有水位与重试语义零推翻，但业主明确裁定「新属性 + 旧模型」的中间可见态不可接受，拒绝。
- **死信自动 / 人工降级提交**：拒绝，保持「整批才落盘」语义纯粹；代价（一个坏元素挡住一个库直到修复）被明确接受。
- **常驻全库镜像**（SUL_DB 永久指向内存、rocksdb 只作提交目标）：拒绝，整库常驻内存 + 全部写路径收口 + 带外写者漂移风险，与需求不成比例。
- **同服务器 staging 表 / 库**：拒绝，「读要看见自己未提交的写」的合并问题不减，且暂存写本身就是双倍 rocksdb 写放大。

## 结果 / 约束

- 一个坏元素能挡住整个 dbnum 的数据可见性直到源数据修复。这是自觉选择；监控必须把「窗口阻断」当一级告警，任务面板要能看到阻断原因与坏根。
- 长窗口（冻结吸收放大区间）会推高暂存内存峰值；staging database 需要行数 / 字节观测与上限告警。规模前提：目标项目 .rdb < 5GB、内存预算 2–3 倍体积（第 1 轮确认）。
- 写回失败的重试与「写回一半时读者可见秒级窗口」是 phase-1 残余，消除依赖 phase-2 暂存会话。
- on-demand 生成与窗口并发：窗口在任何模型修改前，对 RegenRoot、Transform 覆盖的根及 DeleteCleanup 覆盖的旧根统一排序持锁，直到写回及提交后空间收敛完成，避免旧数据生成结果在窗口提交后落库覆盖。**on-demand 命中这些根时立即拒绝，不排队等待**：`model/ensure` 用 `try_lock`，拿不到锁就回 409 conflict（`ModelGenerationInProgress`），由调用方稍后重试，而不是把一个 HTTP 请求挂住整个窗口的时长。代价是拒绝面积不小——它等于「本窗口触碰的全部生成根」×「解析 + 生成 + 提交 + 空间收敛的总时长」，而不再是从前的单根、单次生成。模型浏览端必须把这个 409 当作「稍后重试」而非错误。
- 本 ADR 经外部对抗式审核（GPT-5.5 Pro，2026-08-05，session `kvmem-staged-increment-review`）；采纳与驳回记录见 `docs/2026-08-05_kvmem-staged-increment-oracle-review.md`。
- phase-1 落地口径（2026-08-06 实现审核后）：§2 的同窗吸收扩窗未启用——冻结点重扫并窗 + 失败窗口废弃重建替代之，「重试只重跑失败根」只在批内成立，跨批按窗口重算；§8 的 attempts 重置按「新会话触及的根」判定。窗口内 fresh 根恢复 ADR-012 合批，批失败逐根回退；成功根不得再次进入 durable pending。2026-08-09 起房间工作集预载退役，增量重算在提交后从 RocksDB 同时维护 `room_relate` 与 `room_panel_relate`。
- **（2026-08-12 补记）§5 的本任务 scoped room drain 与 journal 写回、水位尾事务、空间收敛同处 `STAGED_COMMIT_SERIAL` 临界段**（锁持到批次执行函数返回，派发门共锁）。房间重算读 mesh 做逐点判定，其时长直接顶住下一窗口的写回与派发——ADR-010 第 1 条「不进水位事务」挡掉的秒级拖累在锁维度回来了一半，容器搬迁牵出上百分支重生成时元素目标可上千、临界段分钟级拉长。这是自觉权衡：锁内跑在「空间收敛刚完成、无第二窗口并发动树/动库」的世界里，整间分支读树、元素分支读库的基线才不混层（房间是非水位读者，phase-1「写回一半可见」的残余靠锁没有伤到它）。观测：批次日志 `room_duration_ms` 与阶段耗时行。若成瓶颈，第一杠杆是给 inline scope 加时间/条数预算、余量原样留 durable pending 交空闲房间轮（语义现成），而不是先解锁；解锁所需的三道等价闸门与收益边界见 `docs/2026-08-12_room-scoped-drain-commit-lock-assessment.md`。

## 2026-08-06 实现审核修订

本次修订把提交后空间状态从“进程内回调”提升为与水位同事务登记的 durable intent，并把它定义为下一批次的准入门；同时扩大生成根锁域、恢复窗口内合批、补齐房间双表与预载失败闭锁。上述内容修正实现约束，不改变“数据与模型整窗口提交、房间失败尽力而为”的原决策。

唯一对外可见的行为变化来自扩大后的锁域：`model/ensure` 的 409 拒绝面积随之扩大（口径见结果 / 约束）。接口形状与既有字段不变。

# 2026-08-19 修订：phase-1 审计的四处收口

审计对象是 phase-1 的落地实现（不改 phase-2 方向）。四条都是「文档口径与代码实际不一致」
或「失败路径没有终态」，逐条收口如下。

1. **写回的确定性失败有了终态出口**。原实现无条件走 `retry_until_recovered`——它返回
   `(T, u32)` 而不是 `Result`，4 次快重试之后每 30 秒重放同一份 journal，**没有出口**；
   而这一整段持 `STAGED_COMMIT_SERIAL`，于是一条被持久层确定性拒绝的语句会把
   `fast_delete`、提交后空间收敛与其余 dbnum 一起停摆。§4 的恢复语义只讲了「写回失败可
   重试」，默认失败都是瞬时的，这个默认不成立。现在按 `staged_writeback_failure_is_transient`
   分流：断连与写冲突照旧无限等（它们必然自愈），其余判死——记 `window_block`（reason 带
   原始错误）、DROP 窗口、放锁、批次转 Failed。水位没动、持久层零痕迹，journal 随窗口一起
   丢，恢复路径与崩溃同一条（§4：journal 消失 ⇒ 整窗口重算）。journal **入口**早有
   `ReplayUnsafeRejection` 判死确定性拒绝，这是它在写回端的对偶物。

2. **开窗前先验持久层事件版本**。§2 没写「暂存 schema 与持久 schema 可以不一致」，实现里
   却有一处有意的不对称：暂存库不装 `update_dbnum_event`。这道不对称制造了一类「暂存全绿、
   写回逐条被拒」的语句——pe 上一旦生效的是那版对数组形制 record id 用 `array::at` 的旧
   实现，整窗口写不回去，而发现它的时刻是最贵的那一刻。`create_window` 现在进程内一次性
   读回事件定义验指纹（好版含 `string::split`），坏版直接拒绝开窗；读不到按瞬时故障放行。
   只缓存成功，排毒后下一次开窗自动放行。

3. **「数据与模型同一提交单元」的实际让位口径比 §6 宽**。ADR-025 之后闸门是
   `defer_model_phase = job.epoch_id > 0 || initialization_defers_model_phase(...)`，而重扫
   （启动、阶段转换前、范围变更后）排出来的**全部**候选都带 `epoch_id`，稳态 DESI 也在内。
   这批走的是：暂存窗口只提交数据 + 水位 + durable 模型意图，模型留给窗口外的
   `drain_data_phases` 逐根直写持久层。也就是说决策 1 的不变量、以及业主当初裁定为污染的
   「新属性 + 旧模型」中间态，在这条路径上按 ADR-025 §7 的裁量被交换掉了，模型侧的可见粒度
   也退回逐根。§6 写的「基线 / 冷启动 / 全量」只是其中一部分。这里不改行为（ADR-025 更晚且
   Accepted），只把口径写进正文，避免继续按「稳态一定整窗口原子」读这份 ADR。

4. **资源废弃档位有了可执行的阻断记录**。§2 说极限阈值「废弃暂存并转入资源阻断告警」，实现
   里 `Abandon` 只在语句入口 bail，冒泡上来与普通失败无从区分；而这类失败重算不会好——同一
   会话区间必然再次触顶，且窗口只被吸收扩大，没有按 sesno 拆窗的机制。现在按档位单独记一笔
   `window_block`，reason 带测得的字节 / 行数与生效上限，并点名 `AIOS_STAGING_ABANDON_BYTES`
   / `AIOS_STAGING_ABANDON_ROWS`。~~**仍未解决**：拆窗机制不存在~~（同日晚间的拆窗修订已
   补上，见下一节）；计量口径仍是 SQL 文本字节这个摄入代理，不是 mem 引擎实际堆占用，
   `estimate_write_rows` 对带 WHERE 的集合写按 1 行计——两处低报仍留在台账上。

顺带退役：`sweep_orphan_staging_databases_on`（「清扫不在册的孤儿库」）。生产窗口各占一个
独立 `mem://` 实例、实例随句柄回收，跨窗口孤儿库不存在，该函数生产侧无调用方，留着只会让人
以为还有一层兜底回收。

# 2026-08-19 修订（二）：暂存窗口按 sesno 拆窗

方案见 `docs/plans/2026-08-19-staged-window-sesno-splitting-plan.md`，采纳形态 C
（预算式定窗 + 触顶收窄兜底）。要点与已定的开放问题：

1. **不变量**：切点只落在**真实会话边界**（一个 sesno = 一次 SAVEWORK），绝不把一次用户保存
   劈成两半。会话号是稀疏的，右端取「窗口内第 N 个真实会话」而不是按号算术
   （`SesnoRangeResolver::budget_end` 纯函数，切点测试钉着）。
2. **第一层（预算定窗）**：`AIOS_STAGING_WINDOW_MAX_SESSIONS`（缺省 / 0 = 不收窄）。预算只在
   **执行侧**生效——`resolve` 多一个 `max_sessions` 参数，预览与看门狗（`resolve_with_header`）
   必须看见整段待应用窗口：收窄是执行策略，不是事实。Q1 按「不预估、按固定会话数定窗」落地，
   精度让给第二层；Q3 的预算单位就是会话数，元素数标定不做了。
3. **第二层（触顶收窄）**：资源废弃档位不再只记阻断——把该 dbnum 的会话预算收窄一档
   （减半、无预算从 1 起步、地板 1 个会话）再交还批次。预算 1 仍触顶 = 「一次保存大过内存
   预算」，那才是真阻断，出路只有调高上限或应急直写。收窄记录只活在进程内，**追平
   `file_latest` 时清除**——追平前保持，否则每追一段就恢复满窗、下一段又触顶。
4. **上界不改写观察值**：`SesnoUpdatePlan.file_latest_sesno` 保持文件 header 的真实值（它要进
   水位表与身份异常分类），收窄的只是 `range` 的右端（源码钉守着）。
5. **余量立即重排**：截断窗口提交成功后 worker 直接按「applied = 刚提交的水位」重新入队，
   不等下一轮重扫；`file_latest_sesno` 与 `previous_observed_sesno`（并入基线）沿用冻结批次
   那份——余量不是一次新的观察。回执带警告「本批只应用到 sesno k，余量已排回队列继续」。
6. **相位纪元豁免（Q2）**：`epoch_id > 0` 的批次一律不收窄。它们本来就让位模型相位（窗口里
   只有解析数据），不是触顶的那一类；且 ADR-025 的 phase totals 按批次记账，截断批次算不算
   「相位完成」未厘清，在那之前拆窗不碰相位链路。对这类批次，触顶仍然只是一条可执行的阻断
   记录。
7. **原子单元变小（Q4，待业主签字）**：读者能看见子窗口之间的中间态，但每一个都对应源模型
   真实存在过的某个保存点；同一个根在多个子窗口被触及时会被生成多次（结果正确、代价重复）。
   每段子窗口仍是全成才落盘，「降级提交」不存在。

提交侧一行未改：`applied_sesno` 的部分推进与 `align_end_sesno` 本来就容纳更窄的右端。
