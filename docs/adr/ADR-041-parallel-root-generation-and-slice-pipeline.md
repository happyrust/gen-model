# ADR-041：基线初始化按生成根并行，按切片流水线

## 状态

提议（2026-08-21）。实质修订 ADR-017、ADR-021、ADR-025、ADR-038；引用 ADR-010、
ADR-011、ADR-012、ADR-018、ADR-029。

落地拆为两个规格：`specs/023-parallel-root-generation-pipeline/`（并行与收口提速，
不改依赖仓、不引入 ZONE）与后一轮的 `specs/024-*`（ZONE 分片、冻结源与内存有界）。

## 背景

启动自动初始化本身**已经成立**，不是本轮要解决的问题：`lib.rs` 的启动序是
数据 → `wait_for_model_ready` → `build_room_relations`；
`docs/2026-08-17_initialization-increment-audit.md` 是这条链的专项审核，四项发现当轮
全部收口；live 台账的 `live_startup_sweep_routes_a_new_db_to_baseline_beside_an_applied_one`
（2026-08-18）钉住了「新库自动走基线、同目录存量库水位不动」。

本轮要解决的是**跑得太慢**。7999 真靶 56 MB / 120 会话，基线以分钟计；单是
`test_cal_rooms` 的房间全量收敛就 227 秒（从库指针重建 42343 条，214 间房 / 229 块面板，
写 41370 条成员边）。

现状的并行形态是「根内并行、根间串行」：`gen_model.rs` 22 处 spawn/join，
`manifold_bool.rs:76` 把布尔输入固定切 16 块并发，`occ_generate.rs` 6 处、
`pdms_inst.rs` 4 处同类。这层代码写的时候假设自己独占进程——宽度写死、不看核数、
不知道旁边还有没有别的根在跑。

同时有三条硬边界不会因为加线程而消失：

1. `STAGED_COMMIT_SERIAL`（`batch_worker.rs:290`）是进程级互斥，锁序
   `STAGED_COMMIT_SERIAL → SPATIAL_STATE_SERIAL → GLOBAL_AABB_TREE`。journal 写回、
   水位尾事务、空间收敛、房间全部一次一个。
2. 写回走 `protocol-ws` 打 fork 服务器（本仓只开 `kv-mem`，`kv-rocksdb` 是注释掉的）。
   ADR-038 的背景段记录过那边「持续单核计算」的现场。
3. `executor.rs:83` 的 `journal: Vec<JournalEntry>` 是有序追加，写回按顺序切块
   （`TX_CHUNK` 32 / `TX_MAX_BYTES` 64 KiB / `TX_MAX_WRITE_ROWS` 250），块序号与指纹是
   ADR-038 唯一的定位手段。

所以「加线程 = 变快」在这条链上不成立。并行单位、并发额度、提交顺序、失败语义要一次定清楚。

## 决策

### 1. 并行单位是生成根，ZONE 只是内存分片单位

ZONE 决定「一次把多少数据拉进来」，不决定「几件事同时做」。

生成根之间本来就有 per-根锁这一现成粒度，天然可并；按 ZONE 并行则要整片等最慢的根，
长尾直接吃掉加速比，还把跨片依赖变成常态。

### 2. 一片一个 `mem://` 实例，片内的根共享本片实例

`staging/lifecycle.rs` 已经是这个形状：生产窗口各占一个独立 `mem://` 实例，因为
`Surreal<Any>` 的克隆共享会话，并发窗口若只按 database 隔离，任一 `use_db` 都会把另一个
窗口的现场切走。片内的根从本片 kv-mem 读数据，不再新建连接层抽象。

### 3. 一个全局几何并发闸，根级与根内 fan-out 共用同一份额度

额度默认 = 物理核数。`manifold_bool.rs` 写死的 16 改为从额度派生，`occ_generate.rs`、
`pdms_inst.rs` 的同类 fan-out 一并接入。

两层各限各的会得到一个没人算得清的乘积（8 个根 × 16 路 = 128 个 task 同抢 CPU 且全砸同一个
kv-mem 实例），调参时无法归因。共用一个额度，行为可预测，而且它同时就是对 fork 服务器和
kv-mem 的限流阀门。

### 4. journal 改为每根本地 buffer，封本时按稳定序合并

每个根在自己的 buffer 里追加，根结束时整段并入窗口 journal；整片封本时按
（根 ID → 表 → record id）排定。排序的最小单位是**条目组**——ADR-038 第 2 条的显式事务
条目保持原子、不拆开、独占一块，排序不得把它们打散。

这一条同时解决三件事：重复运行的 `journal_digest` 确定；ADR-038 的块边界与块指纹确定
（否则「卡住时能唯一定位到哪一块」这个能力在并行下直接消失）；
`Arc<Mutex<StagedExecutor>>` 的锁争用从「每条一次」降到「每根一次」。

### 5. 空间树与房间保留全量重建语义，只把内部循环并行化

收口阶段仍是 dbnum 级全量重建：输入是已落库的全量数据，输出是同一棵树、同一批成员边。
改的只是中间的循环，并复用第 3 条的闸。房间之间相互独立（逐点判定），空间树的分页读本来
就在锁外，只有换树 / 发布段需要持 `SPATIAL_STATE_SERIAL`。

**不动「N 次增量 ≡ 一次全量」那个口子。** 那是 ADR-010 房间增量模型最难的部分
（`specs/018-room-invalidation-closure` 才刚收完口），不在一次以提速为目的的改造里顺手打开。

### 6. 单根失败记死信，不毁整片

并行下一个根失败，该片其余根照常封本提交。整片作废重来会让必现失败的坏根把整个 baseline
永久卡死——而这类构件是存在的，`52ae62a5 fix(model): persist primitive failures and surface
dead letters` 处理的就是它。

### 7. 发布闸门分两级

- **硬闸**：数据完整、空间树发布、房间收敛。缺一不可，缺了就是真的不能开放。
- **不挡**：模型死信。挂在 `model_update_pending` 等重试，在 `/health` 暴露计数。

这不是新语义，是既有语义的延续：ADR-025 后果段明写「`applied_sesno` 仍只承诺数据已落库，
不承诺模型已生成」，§9 定 `model_update_pending` 是重启可恢复的唯一工作真值。把模型绑进
发布闸门，反而是在基线路径上造了一套与增量路径不同的发布语义。

房间硬闸相应定义为「对**已有 mesh 的元素**全部定论」：死信根名下的元素暂时不归属任何房间，
等模型补齐后由增量房间队列收敛——这正是增量路径今天的行为。

### 8. 生产 / 消费分层，channel 深度 1，一条 = 一整本切片 journal

生产端（解析 + 生成）与消费端（有界写回 + 尾事务 receipt）分层，中间一条深度 1 的**有界**
channel。

**目标是重叠，不是消除阻塞。** 消费端硬串行（第 1、2 条边界），channel 不会让写回变快，
只能把阻塞点从「生产者直接等写回」挪到「生产者等 channel 有空位」；开成无界确实不阻塞，
代价是内存无界，与整条链的约束直接冲突。收益按 `(P+C)×N → max(P,C)×N` 计。

切片依旧是原子提交单元：一条 channel 元素 = 一整本 journal，receipt / commit_token /
尾事务三分支对账不变。channel 里的东西是进程内易失的，所以**生产端不得在消费端 receipt
确认前 DROP 该片 kv-mem**——解耦不省内存，它把 kv-mem 的寿命从「生成完」延到「写回确认完」，
峰值内存 = 2 × 单片预算。

### 9. 生产端禁止回读本次 baseline 的产物（NON-NEGOTIABLE）

生产端只能从三个地方读：

- FrozenSource + 拓扑索引；
- 自己当前的 kv-mem；
- 前置阶段固定 epoch 的产物（CATA / SYST / DICT，本次 baseline 不会动它们）。

**本次 baseline 自己写出去的任何东西，一律不许从 RocksDB 回读。**

没有这一条，跨片依赖的根就得等前一片的 receipt，深度 1 的重叠收益会被这些根吃回去——
而一根管穿两个 ZONE、CREF/TREF 指到别片，在工厂模型里都是常态。有了这一条：流水线深度与
正确性彻底解耦（以后想开到 3 不必重新论证）；不存在读自己未落盘写入的危险；同一个生成根
不论跑在哪一片、跑第几次，看到的输入都一样，第 4 条的确定性才真正站得住。

## 与既有决策的关系

- **ADR-017 §6 作废**：「基线 / 冷启动 / 全量生成路径不走暂存」的理由是「全量产物体量超出
  内存预算」。切片化之后这个前提不成立。`finalize_baseline` 语义另行对齐。
- **ADR-021 的基线衔接条款作废**：2026-08-13 补充的「暂存窗口只属于真正的增量重放」
  「基线不走窗口协议，开了窗口也等不来 finalize plan」连同源码钉
  `batch_worker::batch_reroutes_to_initial_load` 一并修订。**这一条在原始重构计划的修订
  清单里被漏掉了**（清单只列了 ADR-011/017/025/038），必须补上，否则实现与 ADR 正面冲突。
- **ADR-025 §5 需要显式例外**：「阶段状态不另建数据库表……避免出现第二份与水位竞争的完成
  真值」。第二半要引入 `baseline_run` / `baseline_shard` / `baseline_root` 三张持久表，正是
  它拒绝的形态。例外的边界是：这三张表只记录**本次 run 内部的进度**，不参与水位判定、不作为
  增量恢复的真值来源，run 终结时其结论并入水位与 `baseline_visibility`。
- **ADR-025 §7 的模型后置强制分支取消**：模型生成进入切片后不再统一延迟到数据队列清空之后。
- **ADR-011 不变，宪法「并发模型」段无需修订**：第 8 条的 channel 是一次 run 内部的两段流水线，
  不是第二条数据批次消费路径；仍然是一条队列、一个派发器、同 dbnum 串行。
- **ADR-038 保留并被加强**：块边界与块指纹在第 4 条落地之后才第一次真正确定。

## 后果

- 加速比上限由 `STAGED_COMMIT_SERIAL` 之后那一段决定。第 5 条能不能把尾巴并行起来，直接
  决定天花板抬不抬得动。
- 全局闸额度是唯一的性能旋钮，也是回滚开关：调回 1 即退化为今天的行为。
- `manifold_bool.rs` 等处的固定 fan-out 宽度不再是局部实现细节，改动要过闸。
- 第二半的三张持久表是 ADR-025 §5 的显式例外，必须限定在 run 内部，不得成为第二份水位真值。
- 「模型死信不挡 published」意味着 published 的库可能带着可见的模型缺口；这与增量路径一致，
  但要求 `/health` 的死信计数成为发布后的常规观测项。

## 否决方案

- **按 ZONE 并行**：整片等最慢的根，跨片依赖变常态，长尾吃掉加速比。
- **两层各设各的并发上限**：乘积不可控，调参无法归因。
- **`journal_digest` 改成顺序无关的集合哈希**：只能让两次跑算出同一个数，不能让两次跑逐块
  对拍；出事时要的是后者，而且它救不回 ADR-038 的块指纹。
- **把空间树与房间纳入流水线做增量更新**：要重新论证「N 次增量 ≡ 一次全量」，风险与本轮
  目标不对价。
- **无界 channel**：真不阻塞，代价是内存无界。
- **模型死信挡住 published**：一个坏构件把整库锁在 building，正式读取入口持续 409。
