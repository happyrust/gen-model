# ADR-062：房间增量按数据库文件完成后发布

日期：2026-09-05

关联：ADR-040（房间失效正确性）、ADR-056（直写增量）、ADR-057（模型与副作用分离）。

## 背景

原流程在每个模型根或 AABB 块提交后立即同步内存空间树，房间任务则主要依赖全局空闲轮消费。拆窗或单根失败时，同一数据库文件会同时暴露旧模型、新空间指针和未完成拓扑；房间算法又读取实时模型表，因此仅调整刷新调用位置不能形成一致输入。

## 决策

每个数据库文件建立持久更新轮次并冻结源终点 `T`。同一轮的拆窗和重试复用冻结令牌。模型、AABB、删除和房间失效先合并为 `collecting` 候选意图，不切换空间树、不清房间边、不让全局房间消费者认领。

当数据窗口追平 `T`、模型与补刷任务都有成功回执后，依次执行：

1. 将该文件空间意图提升为可重放状态；
2. 按变更集收敛空间树并发布快照；
3. 执行延迟清边；
4. 提升该轮关联的房间目标并立即定向消费。

房间目标仍按 `(action, target)` 全局去重，并额外保存文件轮次关联与要求的空间发布版本。计算先在内存形成候选，提交时把房间边替换、`room_target_version` 实际计算版本落款和任务销账放进同一事务，并以 revision 条件包住全部写入。共享目标的新修订可以覆盖较早轮次，旧修订不能改边、删除新任务或推进其计算版本；更高计算版本可以满足较早轮次的要求。

跨文件采用独立发布：A 未完成而 B 完成时，空间与房间的发布口径是 A 的上次成功版本加 B 的新版本。启动发现 `collecting` 文件轮次时复用最后成功空间快照，不从实时模型指针重建。

发布事务同时更新 `published_file_input:<dbnum>`。该行保存文件身份、精确会话的冻结令牌和空间发布版本；房间拓扑以全部文件令牌的规范摘要为版本键，按设计文件持久保存房间、名称和面板组。消费只按当前清单摘要读取完整分片，不再在计算时重开源文件、枚举实时文件会话或读取正在写入的 `pe` 层级。首次稳态增量在创建 `collecting` 轮次前建立基线，其中当前文件钉到本轮左端之前的已应用会话。首次导入没有旧版本，当前文件不进入基线，等发布成功后再加入。

房间几何另存为版本化 `room_published_inst` 行，内联来源 refno、AABB、世界变换和不可变 mesh 引用。文件的所有模型根与延迟动作完成后，先用本轮冻结令牌完整写入该文件候选，并为“A 旧版＋本文件新版”的组合建立 `room_published_topology` 候选；空间发布锁内会按实际待发布清单再次核对分片集合，缺失时补建，随后空间发布确认事务才把令牌切入 `published_file_input`。房间增量查询只读取当前令牌对应的几何和当前清单摘要对应的完整拓扑，逐点兜底从内容寻址 mesh 取顶点，不再跟随实时 `inst_relate`、`inst_info`、`geo_relate` 或源文件。候选已经持久化的重启可以直接复用；根级落库过程中以及候选写入后、清单切换前的崩溃窗口都继续使用旧版完整输入。

空清单一律视为首次升级边界，与初始化 epoch 无关：在空间状态可消费且持有发布串行锁时冻结全部当前设计文件，并在同一事务建立房间几何基线，任一文件无法冻结则不创建 `collecting` 轮次。已有空间清单但尚无房间基线的升级也会先补齐版本化行；若此时存在 `collecting`、`pending` 或 `failed` 文件发布则失败关闭，禁止从可能半发布的实时行补基线。启动存在遗留房间任务且尚无新数据窗口时，房间消费入口也会先建立同一基线。当前实现没有生产 mesh 可达性 GC；内容寻址的共享 mesh 在模型删除与历史快照删除时均保留，因此活动轮次和已发布版本不会被清理器误删。未来引入 GC 时必须把已发布清单、活动轮次和在飞房间任务一并作为可达根。

空间树使用 V3 单文件快照，头部同时记录逻辑空间发布版本、已发布文件数及冻结输入清单 SHA-256。快照在任务确认前写入候选清单；确认事务按同一任务顺序递增版本并切换文件行，因此确认零条、部分或全部完成后都能验证同一快照。启动只接受“当前清单加待重放任务的某个有序前缀”产生的摘要；摘要损坏或错配时进入空间门禁并报告错误，不从实时指针扫描半成品兜底。文件发布即使 AABB 内容未变也重写快照头。

一次房间消费从加载清单、模型几何和空间树，到写入房间边并按 revision 结算任务，全程持有空间发布串行锁。文件发布使用同一把锁，因此计算不会跨越两个发布版本；期间到达的新任务保留更高 revision，当前结算不能删除它，释放锁后按新版本重算。

## 失败与恢复

- 数据或模型失败：文件轮次保持 `collecting`，继续提供旧发布版。
- 空间发布失败：空间意图保留为 pending/failed，房间目标不提升。
- 空间成功而房间失败：房间目标保持 pending，由空闲补偿轮继续处理。
- 进程重启：从持久轮次取回冻结令牌和终点，不把新保存扩大进旧轮次。
- 冻结源确认不可恢复：旧轮次必须显式标记被替代，并以最新冻结点完整重建该文件候选；不得从旧轮次的部分结果继续。
- 替代事务清空新轮次的模型根、空间变更、延迟动作和房间清边候选，再把 `Reinitialize` 控制意图排在当前失败任务之后；旧任务以失败结束，不充当替代轮次的成功回执。

## 后果

正常房间触发由文件发布直接驱动，全局空闲轮只补偿遗留任务。读透和异步镜像模式不承诺此文件级发布语义。首次启用必须在空间写入暂停且存量输入可验证时建立发布基线；输入损坏时停止相关派生服务，不能回退读取实时半成品。

`e3d.room.lookup` 与 `model.spatial.bounds` 在空间发布串行锁内读取结果和版本。响应携带 `published_version`、`stale` 与 `publication_status`；文件轮次构建中返回 `updating`，房间查询还按元素及其当前面板的目标待办定向判 stale。空间状态本身不可消费时返回 `UPDATING`，不返回无可信版本的结果。读透内存模型明确返回 `publication_status = unsupported`，不伪造发布版本。
