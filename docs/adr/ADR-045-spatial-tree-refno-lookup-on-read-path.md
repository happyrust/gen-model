# ADR-045：按 refno 问空间树，读路径与写路径共用同一份索引

## 状态

已接受（2026-08-23）。引用 ADR-010、ADR-012、ADR-041；落地规格
`specs/026-spatial-tree-refno-lookup/`。不修订任何既有决策。

编号取 045 而非 043：同日已有未入库的 `ADR-043-insts-flat-invalidation-protocol.md` 与
`ADR-044-libgm-facet-caliber-and-unit-mesh-identity.md` 占位。

## 背景

`GLOBAL_AABB_TREE` 是一棵 `rstar::RTree`，按**空间位置**建索引。它擅长回答「哪些盒子跟这块
区域相交」——房间归属、射线拾取都靠它——但它不认识 `refno`。

而增量链路上有一类查询问的恰恰是 refno：

- **变更判定**（`update_inst_relate_aabbs_by_refnos_mode`）：这批 refno 在树上现存的旧包围盒
  是什么？拿来跟新算出来的比，决定要不要 bump spatial epoch、要不要排房间重算。
- **删除探测**（`delete_room_membership`）：这几个 refno 在不在树上？决定这次删边算不算改变了
  「树应有内容」。
- **删旧插新**（`sync_refnos`）与**摘除**（`remove_by_refnos`）：`rstar` 的 `remove` 按整值相等
  匹配，调用方得先拿到那条**旧的**盒子对象才删得掉，而它手里只有 refno。

后两个（写路径）早就有解：`AccelerationTree` 内部维护了一张
`refno_index: HashMap<RefU64, SmallVec<[RStarBoundingBox; 1]>>`，是纯内存派生数据
（`#[serde(skip)]`，不进 `accel_tree.bin`，加载后重建），新鲜度由 `indexed_tree_len` 看守。
同文件里还有 `sync_refnos_cost_is_not_proportional_to_tree_size` 钉着「单 refno 操作不得扫整树」。

**前两个（读路径）没有解**，因为 `refno_index` 是私有字段、没有对外读接口。于是两处调用点都
退回了 `tree.iter()` 全量遍历——`AccelerationTree` 实现了 `Deref<Target = rstar::RTree<_>>`，
这句话编得过、读起来也自然，这是它活了这么久没被发现的原因。

代价在初始化时暴露。按需基线（新库进目录、ADR-021 回退重建）把整库排成 N 个生成根逐根跑，
每根在布尔前后各刷一次 AABB，也就是**每根扫两遍整棵树**。而树是边生成边长大的：第 k 个根扫的
是前 k−1 个根的产物。总代价对库规模是平方级——这就是「越往后越慢」。AMS 现场树有 105651 条。

ADR-041 / `specs/023` 已经在治「慢」，但治的是常数因子（把写死的 fan-out 宽度收归统一并发闸）。
它第 5 条是「空间树与房间保留全量重建语义，只把内部循环并行化」——**并行化一个平方级循环，
结果仍是平方级，只是除以核数**。两条线不冲突，但顺序有讲究：不先把平方项摘掉，并行度买回来的
收益会被库规模重新吃掉。

## 决策

**「按 refno 问空间树」只有一份实现，读路径与写路径共用 `AccelerationTree` 的 `refno_index`。**

具体到四点：

### 1. 能力开在拥有索引的类型上，不在调用方复制

`AccelerationTree` 新增 `&self` 只读接口：取一批 refno 在树上现存的全部条目，以及判断一批
refno 是否至少有一条在树上。第二个不是第一个的糖——删除路径只要一个 bool，不该为此物化
`HashMap`。

**明确拒绝在 `gen-model` 侧自建一份 refno → 包围盒 的映射。** 那会造出第二份「树上现在有什么」
的真值，需要自己盯住删除清理、指针重建、启动加载三条路径去同步。漂移的后果不是变慢，是房间
归属把一个已经不在那儿的构件算进某间房——而这类错误没有任何东西会报出来。这正是原则 II 要挡的。

### 2. 接口是 `&self`，不是 `&mut self`

`update_inst_relate_aabbs_by_refnos_mode` 的两条分支持的锁不同：直写分支持
`GLOBAL_AABB_TREE.write()`，**暂存分支只持 `.read()`**（窗口内本来就不动树）。做成 `&mut self`
就得把暂存分支升级成写锁，而它并不持空间串行锁——那会直接破坏锁序
`SPATIAL_STATE_SERIAL → GLOBAL_AABB_TREE`，仓内有源码顺序断言钉着这一条。

代价是 `&self` 拿不到 `ensure_refno_index` 那条重建路径，于是有了第 3 条。

### 3. 索引与树不同步时：答案仍然正确，但必须可见

回退到全树扫描（正确性优先），同时**计数并打日志**。

`tree` 字段今天是 `pub` 且有 `Deref`，静态上无法保证索引永远新鲜。但已逐处核对：`gen-model`
里所有动树的调用都经过维护索引的 API（`sync_refnos` / `remove_by_refnos` /
`AccelerationTree::load` / 整棵树赋值），没有一处绕过。**所以这条日志一旦响，就说明有人新写了
一处绕过 API 的树修改——那是缺陷本身，不只是变慢。** 它既是安全网也是警报。

否决「静默回退」：一个悄无声息退回 O(N) 的快路径，正是原则 III 说的「它跳过的东西谁会发现」
答不上来的分支。否决「不新鲜就返回 `Err`」：那把扫描兜底留在每一个调用方，而删掉这个扫描
恰恰是本决策的目的。

### 4. 不收窄 `tree` 的可见性、不移除 `Deref`

那是让索引「永远新鲜」的根治办法，但会波及依赖仓的其它下游。用第 3 条的可见回退兜住，留待
真正需要时再做。

## 与既有决策的关系

- **ADR-041 / `specs/023` 不变，本决策是它的前置。** 023 处理常数因子，本决策处理平方项，
  两者相乘才有意义。023 的 20 条任务无一需要改动。
- **ADR-010 不变。** 房间目标集合（`chunk_changes`）逐元素不变，`tree_box_changed` 的输入与
  结论不变，不触及「N 次增量 ≡ 一次全量」那个口子（`specs/018` 才刚收完口）。
- **ADR-012 的收益因此才兑现得出来。** 多根合批省掉的是 N−1 次启动与落盘，但每根仍各自扫两遍
  整棵树；平方项摘掉之前，合批的账算不清。
- **不改水位、队列、批次终态语义**，因此与 ADR-001 / ADR-011 / ADR-021 / ADR-025 无交集。

## 后果

- 变更判定与删除探测的耗时不再随空间树总条目数增长，只随被问的 refno 数量增长。初始化的
  平方项消失。
- `accel_tree.bin` 格式不变（索引本就是 `#[serde(skip)]`），旧快照直接可用。
- 依赖仓 `../vendor/old-aios-core` 需要一次改动与一次 rev 升级。落地规格把发布拆成独立步骤：
  先用仓库既有的 `[patch]` 在本地验证与量数，确认收益后再升 rev。
- 新增一条「索引不同步」的观测项。它平时恒为 0；不为 0 就是有人绕过了 API。
- `src/data_interface/helper.rs` 里那条按 `tree.iter().any(` 找位置的源码顺序断言必须同批更新，
  否则它会从「守着次序」静默退化成「找不到即 panic」。

## 否决方案

- **在 `gen-model` 侧自建 refno 索引**：第二份真值，漂移后果是房间归属算错。见决策第 1 条。
- **接口做成 `&mut self`**：破坏锁序。见决策第 2 条。
- **索引不新鲜时静默回退**：违反原则 III。见决策第 3 条。
- **索引不新鲜时返回 `Err`**：把要删的扫描留在每个调用方。见决策第 3 条。
- **把 `tree` 改私有、移除 `Deref`**：根治但波及依赖仓其它下游，与本轮目标不对价。见第 4 条。
- **等 `specs/023` 做完再说**：023 并行化的是一个平方级循环，除以核数之后仍是平方级；库一大
  就回来了。顺序反了。
