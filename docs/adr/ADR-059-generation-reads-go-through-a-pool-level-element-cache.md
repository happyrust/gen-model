# ADR-059：生成期的读取走池级元素缓存——瓶颈是重复解析，不是几何

状态：**已接受**（2026-09-04，实测坐实）
日期：2026-09-04
关联：ADR-053（direct 模式：生成期读取直走 pdms-io / e3d-io 解析）、ADR-057（e3d-model 是纯模型面）、
`vendor/e3d-model/docs/2026-09-04-generation-algorithm.md` §3.1、`vendor/e3d-model/docs/2026-09-04-step1-in-memory-plan.md` W6 / W7-1；
实现在 `vendor/e3d-io/src/db_element.rs`、`vendor/e3d-io/src/read_stats.rs`。

## 背景

给 e3d-model 的第一步计划做 W6「分段计时」时，第一次跑就把猜测全推翻了。ams8000（6088 个设计元素、
会话 264、五个目录库）：

```
总 6861ms | 循环 6840ms = 生成 6752ms + 三角化 18ms + 写OBJ 16ms + 其它 53ms
读取（含在生成里）: 记录解析 881,145 次 2322ms | 描述符抽取 793,389 次 3633ms
每元素真读 144.73 遍（visited 6088）
```

**读取 5955ms / 生成 6752ms = 88%**。之前担心的 manifold CSG 布尔与三角化，加起来不到 1%。

重复不在遍历上——遍历本身是一次 DFS。`DbSet::element` 每次都造一个新句柄、`parsed`/`extraction` 两个
`OnceLock` 都是空的，于是**跨句柄**的重复全额付费：

- `transform::world_matrix` 逐元素上溯 owner 链，同一批祖先被 n 次重新查索引、重新解析；
- 目录链走查（`SPRE→SPCO→CATR→SCOM→GMRE`）让每只 FTUB / BEND 都把同一批目录件重走一遍——145 这个
  倍率远超树深 7，多出来的就是这一截。

句柄级 `OnceLock` 只挡下 24%（hit 286k vs miss 881k）。

对照 core.dll：它有 2KB 分页 + LRU 页缓存兜底 I/O（ADR-053 已记），而且变换是**自顶向下累乘**
（`SGDRAW` 的 `MAT16`/`CONCAT` → `GLSMAT`），祖先链一步都不回走。我们两条都没有。

## 决策

1. **池级元素缓存做进 e3d-io，但默认关**，由消费方 `DbSet::with_element_cache()` 打开。
   格式库仍然不替消费方决定内存形状——但它必须**提供这个位置**：重复发生在 `owner()` / `get_element()`
   内部，消费方够不着那里，自己补不上。这一条推翻了 `DbElement` 原注释里「池级无界缓存是消费方的取舍，
   格式库不做」的前提。
2. **键是 `RefNo`**（自带 dbno，全局唯一）；`ParsedElement` 与 `ElementExtraction` **两张表分开**——
   只导航（owner / members / 类型）的路径不为描述符抽取买单。
3. **换库即失效**：`add_db` 按 dbno 清掉对应条目。换库就是换时点，留着旧解析等于一直喂上一个会话的树，
   而且两边都不报错。缓存的正确性前提是**会话钉死**。
4. **一次生成打开它，长驻全库读不打开**。一棵子树是有界的；长驻进程按库全量读不是——那种场景另建
   一个短命 `DbSet`。
5. **计量先行**：`read_stats` 把句柄命中 / 池级命中 / 真读分三档记，只给真读计时；`gen_ams` 打印分档计时。
   任何性能改动**先量后改**，且**必须逐字节对拍产物**才算数。

## 考虑过的选项

| 选项 | 结论 |
|---|---|
| **A 自顶向下带世界矩阵**（DFS 把父的世界矩阵带下来，`model_element` 收 `parent_world`） | **仍然该做，但不是先做。** 它结构上正确、与 core.dll 同形，可是只消掉 owner 链那一半；目录链那一半（145 里的大头）它管不着。而且改 API 会正面撞上并行会话在飞的 SCTN 接线。 |
| **B 池级缓存**（本决策） | 一处改动同时消掉两截重复，零 API 变化，零行为变化。**先 B 后 A。** |
| C 只给 `world_matrix` 加记忆化 | 只解决一处，目录链不管，还多一份与 e3d-io 平行的缓存语义。 |
| D 有界 LRU | 淘汰策略是政策，一次生成里无界本来就是有界的。出现长驻场景再单开一条。 |

## 后果

- **6861ms → 523ms（13.1×）**；读取 5955ms → 116ms（51×）；每元素真读 145 → 1.91 遍
  （11651 次 miss ≈ 6088 设计 + 约 5500 目录/引用元素，即每个**不同**元素读一遍，已经到底）。
- `model.obj` / `elements.json` / `report.json` 三份 SHA-256 **逐字节一致**；账照旧平
  （visited 6088 + consumed 517 = 索引 6605）。改的是读几遍，不是读什么。
- 内存：本库约 1.2 万条 parsed + 0.8 万条 extraction，不淘汰。
- 生成期的优化重心因此**从几何移到读取**。`vendor/e3d-model/docs/2026-09-04-step1-in-memory-plan.md`
  的 W7-1 从「待拍板」升为已落地的一半（B），另一半（A，自顶向下变换）仍挂账。

## 风险

- **R1 无界增长**：长驻进程按库全量读会一直涨。缓解＝默认关 + 文档写死代价 + 生产侧单独评估。
- **R2 时点错配**：`add_db` 换库已清；但前提仍是「同一次生成里会话钉死」。绕开 `add_db` 换文件的路径
  （resolver 首次解析后冻结）不在此保护内。
- **R3 并行争用**：目前是单个 `RwLock` 罩两张表。按根并行（计划里的另一刀）之后它可能成为新瓶颈，
  届时分片，不要在没量之前先分。
- **R4 13× 不是常数**：ams8000 是管道库、目录链重。结构库（ams1112 那片板）倍率会低不少，
  **别把它当全局常数用**。待补：ams1112 / ams7997 复跑。
- **R5 生产路径尚未开**：`gen-model/src/fast_model/e3d_model_service.rs` 是长驻服务、按根生成，
  缓存生命周期该绑在一次生成上还是进程上要单独定，本决策不替它拍。
