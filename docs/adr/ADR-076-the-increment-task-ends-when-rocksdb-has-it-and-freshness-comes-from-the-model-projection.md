## 背景

### 现状有一段真空

持久档下 `data_interface/batch_worker.rs` 把整库模型水位当成 FIFO 栅栏交给 write-behind worker，任务自己置
`stage = durable_pending` 就返回了。源码注释把理由写得很清楚：后台作业只拥有 durable 模型水位，**这样下一次增量不必等**。
代价是存在一段「任务说完了、RocksDB 里还没有」的真空：任务完成信号、模型水位、盘上的行三者不同时到位，崩溃语义因此分叉。

### 用户要的是及时性，不是异步本身

「初始化可以等，增量要及时响应」。及时性的载体是**进程内模型投影**（`fast_model/model_memory_store.rs` 的 `ModelMemoryStore`）：
生成完只写这张结构体表就算发布，读路由 `model_record_reader::records_of_root` 先看投影、没有才查库。它与「异步落盘」是两件事——
投影让结果**立刻可读**，落盘什么时候完成不影响这一点。

### 实测：介质不是瓶颈，串行也不贵（2026-09-14，本机，AMS，16 物理核）

同机、同库、同一个二进制，只换 surreal 的后端：

| 跑什么 | memory 后端 | rocksdb 后端 | 差 |
| --- | --- | --- | --- |
| 7997 整库模型生成全程 | 30.0 s | 30.9 s | 3% |
| 其中落库尾巴 | 17.71 s | 18.92 s | **1.2 s / 6%** |
| surreal 自身 CPU | 21.1 s | 22.0 s | 4% |
| 8000 解析基线（含 SYS） | 36.3 s | 36.1 s | 基本相等 |

两边 `READBACK` 六项逐字相同。**把 RocksDB 移出关键路径最多值 6%**：贵的是 SurrealDB 的事务 / 索引 / 逐行写值，换介质不动它分毫。
推论：在前面摆一台 kv-mem SurrealDB 给外部读，那 17.71 s 一秒也不会少——投影之所以便宜，是因为它根本不是数据库。

增量尺度的 durable 刷盘（定向那一档 `--root`，打在已有 8000 全量数据的 RocksDB 上）：

| 根 | 元素数 | 生成 | durable 刷盘 |
| --- | --- | --- | --- |
| 24384/25586 | 15 | 647 ms | **71 ms** |
| 24384/24775 | 23 | 653 ms | **98 ms** |
| 24384/24945 | 110 | 647 ms | **124 ms** |
| 24384/22400 | 1941 | 1119 ms | **1.61 s** |

改一个构件那类增量落在头三行。**「同库下一次增量要等上一次刷完」这个代价在增量尺度上是百毫秒量级**，不值得为它保留上面那段真空。

由此还得到一个要写下来的推论：**任务既然等刷盘，投影比「直接查库」早的那一段就只有这百毫秒**。投影仍然要有——它是生成管线的
输出格式、根回执的载体、历史快照的宿主——但它**不是一个延迟装置**，不该为了延迟给它加驻留。

### 那个配置至今没有实现者

`DbOption.toml` 的 `model_cache_mode = "incremental-overlay"` 注释写着「kv-mem 只留新生成的 root overlay，冷 root 直接查
RocksDB、不回填」。**全仓没有任何地方读它**：`options::model_cache_mode()` 除了 `options.rs` 自己的单测之外零调用方。
实际行为因此是：持久档下**整库初始化生成的全部行都进投影，而且一直留着**——7997 峰值 RSS 1.5 GB 的大头就是它。

## 决策（D1–D13，对应 grill 四轮 Q1–Q13）

### D1　热路读统一走服务 API，两档同一口径

模型投影只有走 gen-model 自己那条读路（`query_service`、HTTP API）才看得见；直连 `ws://v_ip:v_port` 的消费者看不见它。
ADR-074 的 `mem` 档已经把这一条定了一半（库在进程内、没有端口，读面统一走同源服务 API）。`rocksdb` 档**跟着一样**：
热路读走服务 API，直连库降为诊断、探针与房间兼容页的用途。

两档讲两套话是最贵的：若 `rocksdb` 档保留直连读，本 ADR 想要的「增量算完即可见」在主力档位上就不成立。

### D2　任务只等自己那批根与自己那枚水位

「以落盘完成为结束标识」等的是**本任务的单元清单里那批根刷完 + 本库那枚模型水位盖上**，按 dbnum 设栅栏。
不等全局 write-behind 队列排空——隔离单元本来就是 dbnum，让一个库的任务被别的库拖累是无由的耦合。

### D3　同库严格串行，不做任务间流水线重叠

任务拖到刷完才结束，而调度器保证同库串行，于是同一个 dbnum 的下一次增量要等上一次刷完。**接受这个代价**：实测 70–130 ms。
只有单根上千元素那种重建才到秒级，那一档本来也不是「改一个件」的交互路径。真遇到连发压力再谈流水线，不预先设计。

### D4　属性写在任务内用共用写入队列重叠，收尾等队列排空

属性面沿用 e3d-io 的解析流程直接写 RocksDB（见 D10），写法接 `data_interface/sql_write_queue`：前台接着解析 / 生成，
后台单写者按批序列化，任务收尾等队列排空。那套机器（有界队列、单写者、`WRITE_WINDOW < QUEUE_CAPACITY`）已经在基线摄入上
跑着，模块头写的就是「增量那一路用同一份」，不另造一套。

**这是任务内的重叠，不是跨任务的异步**：队列没排空任务就不算完。

### D5　三枚水位由任务收尾那一笔事务同时盖

`enqueue_model_watermark_write_behind` 那条「模型水位归后台 worker」的分工取消。任务 `await` 本库栅栏返回之后，
由收尾那一笔控制面事务**同时盖三枚水位**，回到 ADR-071 D1 的形状。

一枚控制面的事实只能有一个写者；两个写者就是两套崩溃语义，而这正是现状那段真空的来源。

### D6　刷盘失败：任务内有限次退避重试，仍失败转 `Partial` 且不收写入标记

write-behind 现有的退避与死信照用，但重试预算归任务。用尽仍失败：任务转 `Partial`、**写入标记不收**，下一轮按 ADR-072
整窗重来（行幂等 + 水位在最后）。不原地无限重试——那会把一个库的队列永久堵死，而且外面看不见。

> **修订（2026-09-15，增量路计划 §8 Q1，用户拍板）：写入标记照收。** 本条写「不收」时依据的是 ADR-072 的按 sesno 回退；
> 那条路已被 ADR-073 D3 取代——今天标记停在 `writing` 的唯一处置是**整库 Reinitialize**。按字面做，一个确定性 `Blocked` 的根
> （载荷超硬顶、房间计算器缺）会变成「每次启动整库重建 → 同一根再 Blocked → 标记又不收」的跨重启活锁，正是本条自己要避免的
> 东西。落地形态：预算用尽 / 判死的根从队列摘掉（`abandon_roots`）、逐出投影（`drop_cached_root`，durable 才是真值）、单元记
> `Failed`（`message` 以 `durable flush:` 开头）、`gen_root` 留痕（`status = 'failed'`），任务 `Partial`；收尾那一笔照落、标记收成
> `finished`、`model_sesno` **不盖**、`model_dead_roots` 记判死数——走 D8「标记已收而只有模型水位没盖 → 启动核对按凭证缺口排
> `ModelOnly`」那条现成的路。收标记不掩盖任何「没写完」：数据行与 `applied_sesno` 早已同步落库、模型行按根幂等、没 ACK 的根没有
> `gen_root` 回执。预算 = 每根 `batch_worker::MAX_ATTEMPTS`（5）次 + 任务级 10 min 期限，常量不配置。

### D7　`durable_pending` 保留为任务内阶段

这个 stage 今天的意思是「任务已结束、刷盘还在飞」，本 ADR 之后那个状态不存在了。**名字留着，语义改成任务内的一个阶段**，
在任务列表与 `/health` 上照常可见。刷盘是增量里最慢的一段，把它从进度条上抹掉是自断一臂。

### D8　进程死在任务中间，不新增恢复路径

沿用现成判据：写入标记还在 → 按 ADR-073 D3 就地 `Reinitialize`；标记已收而只有模型水位没盖 → 启动核对按凭证缺口排
`ModelOnly` 恢复任务。行是幂等的、水位在最后，这两条已经把「刷了一半」盖住了，不值得为它再开一条路。

投影随进程消失这件事不需要额外处置：它本来就是缓存，真值在设计文件与库行里。

### D9　本轮落成 ADR

改的是任务边界的定义，并且是把 `batch_worker.rs` 里那句「这样下一次增量就不必等」明确翻掉。难逆、看不出缘由、有真权衡——
三条都占。不写下来，下一个人读到那行注释会把它改回去。

### D10　承认「新模型 + 旧属性」中间态

任务进行中会有这么一段：模型已从投影可见，而属性行还在被后台单写者一批批写进 RocksDB，UI 这时点那个件看到的是新几何、旧属性。

**承认它。** 理由不是「窗口短所以忍了」，而是口径本身：**属性的真值始终是 e3d-io 对设计文件的解析**，库里的属性行只是那份解析的
一次序列化，不是第二份真值。要精确属性就读解析（read-through 数据面的语义原本就是「缺行 = 还没读到，不 = 不存在」），
不是等库行。任务列表 / `/health` 把「本窗属性还在落」暴露出来即可。

不做按元素对齐的可见性闸（在投影上再加一层逐元素门控），复杂度与收益不成比例。

### D11　初始化任务的模型行直写 RocksDB，不进投影

整库初始化生成出来的行**不经过投影**，由生成侧直接序列化进 RocksDB。投影只承载增量。冷读本来就查库，这正是
`incremental-overlay` 那句注释的字面意思——只是此前没人实现它。

**这一条必须与根回执一起做。** 「这根按哪一版生成过」今天只活在投影的 `RootReceipt` 里；不进投影就必须把回执写成 durable 的
`gen_root` 行，否则初始化完一重启，启动核对会认为这个库一行模型都没生成过，把整库重排一遍。2026-09-14 实测坐实了这个缺口：
整库生成跑完，`gen_root` 是 0 行（根覆盖要显式调 `fn::sync_gen_roots` 才物化，2.4 s / 776 根，且 `status` 全空）。

### D12　增量那一份刷盘成功即逐出投影

投影只在「算完 → 落盘完成」这百毫秒里存在，之后读路自然落到库上。不留作读缓存——留就要定淘汰策略，而**没有淘汰正是今天那座
内存墓的成因**。

### D13　删掉 `model_cache_mode`

配置键、`AIOS_MODEL_CACHE_MODE`、`ModelCacheMode` 一并删除，策略由 D11 / D12 写死。只有一种策略就别假装有两种：一个没人读的
开关比没有更糟，它让读配置的人以为调得动。

## 后果

1. **任务完成 ≡ RocksDB 里有 ≡ 三枚水位到位。** 崩溃语义变成二值：要么完成且落盘，要么没完成、整窗重来。
2. **同库连发增量排队。** 实测代价 70–130 ms/次；单根上千元素时到 1.6 s。
3. **及时性与落盘解耦，但解耦点在投影，不在介质。** 任何绕过服务 API 直连库的读者都拿不到这份及时性——这是 D1 的由来。
4. **不引入第二个数据库、不做全量驻留、不做重启回灌。** ADR-074 的两档不变。
5. **常驻内存下来一截。** 初始化不再把整库在投影里过一手（D11），增量那一份刷完即走（D12）——7997 那 1.5 GB 峰值的模型投影
   部分应当基本消失。这是本轮除任务边界之外最实的收益。

- **S2**　水位所有权：撤掉 `enqueue_model_watermark_write_behind` 的水位职责，三枚水位并回 `task_end` 那一笔（D5）；

  **✅ 已落**：钉翻成 `the_task_stamps_model_sesno_only_after_its_roots_are_durable`；`settle` 整条退役、`/health` 少

  之前盖（ADR-056 D1 / ADR-025 §7，`requeue_window_remainder` 与凭证前移都读它），收尾一笔 = `model_sesno` + `finished` + Ref0。
- **S3**　失败与恢复：任务内重试预算 + `Partial` + 写入标记不收（D6）；启动侧不动（D8），补一条重启后「标记在 → 整窗重来」的
  真进程用例。
  **✅ 已落**（预算与放弃；D6 修订为**标记照收**，恢复走 D8 的 `ModelOnly`）。真进程 kill-重启用例归计划 S5，**未跑**。
- **S4**　属性写接 `sql_write_queue`，收尾排空（D4）。
- **S5**　读口径：清点 plant-ui 直连读，把热路迁到服务 API（D1）——跨仓，单独排期。
- **S6**　初始化直写：生成侧按 D11 分出「初始化直写 / 增量过投影」两条落点；同批把根回执写成 durable `gen_root` 行，

- **S7**　按 D12 在刷盘成功点逐出投影；按 D13 删掉 `model_cache_mode` 配置键、环境变量与枚举。

## 验收
