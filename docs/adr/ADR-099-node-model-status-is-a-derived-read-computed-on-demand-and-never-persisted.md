# ADR-099：节点模型状态是按需算的派生量——不建表、不进任何放行判据，新旧按「生成之后有没有改到它」判

- 状态：已接受（2026-11-10。用户在 plant3d-web 的方案
  `docs/plans/2026-11-10-model-load-speed-generate-and-freshness-plan.md` 第 6 节拍了板：生成标记**不建新表**（6.4 选 A）；
  「最新」的口径，库一级以库文件最新会话为准，SITE / ZONE 一级只有模型生成之后真有会话改到它下面的构件才算落后（6.3 选 A）；
  生成前按规模确认，阈值由后端给（6.1 选 C）。代码在工作树，写本文时未提交）
- 日期：2026-11-10
- 沿用：
  - ADR-079（生成根的成败只活在进程里，`model_sesno` 是模型面唯一的持久事实）——本文不给模型面加第二份持久事实；
  - ADR-081（版本表从会话链按需算、不落库）——「生成之后改了什么」用的是它那一族的 `node/diff-summary`；
  - ADR-086（显示按祖先查 records，没生成过是空不是 409）——「一个单元算不算已生成」与 records 读得到读不到同一套依据；
  - ADR-089（按需显示的新旧听库级承诺）——本文不改 `/model/generate` 的判据，只说清它和这里问的不是同一个问题。
- 消费方：plant3d-web 的 C2（SITE / ZONE 行的新旧状态）、B3（按规模确认、分块生成）。
- 接口：`GET /api/v1/node/model-status`，`docs/specs/web-service-api.md` §4.5.3。

## 背景

用户要「对 ZONE 和 SITE 的模型生成标记和最新 sesno 做比对和跟踪」。库里今天回答得了的只有整库一个数（`model_sesno`）。
节点一级要回答三个问题，前端此前只能拼：

1. **生成过没有**：未初始化的库只能整库枚举 `dbnums/{dbnum}/model/roots`（7997 要 21 秒，7333 要 40 秒），而且不能按
   SITE / ZONE 过滤；已初始化的库靠查 records 是不是空。
2. **是不是最新**：库一级有三枚水位；节点一级前端自己拿 `node/versions?since_sesno=<模型水位>` 去判。
3. **要生成的话有多少**：没有接口，前端沿树往下数。

最顺手的做法是给 SITE / ZONE 建一张标记表，生成时写一笔。这正是 ADR-079 退掉 `gen_root` 时拒绝的东西：逐根（何况逐节点）
的持久标记要回答重建、回退、清库、幽灵行那一整套问题，而它记的每一件事都能从水位和文件算出来。用户 6.4 选了不建表。

## 决定

### D1　节点模型状态是派生量，按需算

`GET /api/v1/node/model-status?refno=` 每次请求从四样东西现算：

| 来源 | 给出什么 | 活在哪 |
|---|---|---|
| 水位行（`DbnumState`，走镜像） | 数据水位、模型水位、库级判决、模型从哪读 | 库（唯一的持久事实） |
| 库文件 | 文件最新会话；子树里有哪些生成单元；两个会话之间这个节点下变了什么 | 工程文件 |
| 进程内投影的回执、生成根账本 | 哪些单元本进程生成过、按哪个会话；哪些失败了 | 进程内，重启即失（ADR-079） |
| 任务登记表 | 这个库此刻有没有在被写 | 进程内 |

不建表，不写任何东西。**后端没有任何一条判据读它的输出**：`/model/generate` 判不判缓存命中、增量规划器选哪些根、水位
盖不盖，都不看节点模型状态。它只给人和前端看。所以它不是第二份事实——它错了，最多是界面上一个标记不对，不会让库里
多一行或少一行。

### D2　一个单元算不算已生成：与 records 同一套依据

「生成单元」取 `/model/generate` 对同一个节点会枚举出的生成根（`DirectTreeService::generation_roots_in_subtree`，同一段
遍历）。逐个单元按顺序判：

1. 账本里它最近一次生成失败、还没重新成功 → `failed`。与 ADR-079 D6「账本里悬着失败的根一票否决」同一句话。
2. 投影里有它的回执 → `generated`，对应到回执的生成会话。
3. 库里的整库模型读得到，且它在模型水位那个会话上已经存在 → `generated`，对应到模型水位。「读得到」取
   `model_read_route` 的现成结论：路由是 `database`，或是 `memory` 而 `allows_durable_fallback()`，并且 `model_sesno > 0`。
   这一条就是 ADR-079 D3 的那句承诺：模型水位盖到 S，S 时刻每个根都已发布。回执比水位旧的单元（规划器的 `advance`
   根，回执留在它上一次真正重算的会话，ADR-089 D4）也对应到水位。
4. 其余 → `missing`。

第 3 条里「在水位那个会话上已经存在」怎么知道：水位之后才新建的单元会出现在 D3 那次差分里（单元根自己是新增行）。

### D3　落后：生成之后有没有会话改到它，按净差分

对每个已生成的单元取它对应到的会话 V。V 等于库文件最新 T 的不用比。否则做一次 V→T 的净差分，范围是请求的节点
子树——直接调 `node_diff_summary(dbnum, 节点, V, T, subtree)`，不另写一遍。落在某个单元名下、要重算几何的变化
（`mesh` / `placement` / 新增 / 删除）把那个单元记为落后。

- 这把尺子就是生成那条路自己的（`classify_operation_impact`）。登录写的记账会话、只改名字描述的修改判成 `noop`，不算。
- 用净差分而不是逐会话：模型是按 V 生成的，问的是「V 的模型和 T 的数据差不差」。先改后改回，净结果没变，不该让人去
  更新一次。`node/versions` 逐会话各记一行，那是时间线该有的样子，两者不矛盾：那张表在 V 之后没有非 `noop` 的行，
  这里一定不落后。
- 归不到单元上的几何变化（ZONE 自己挪位、不在任何交付单元下的构件变了）单列 `changes.unattributed`，节点判落后，
  但不计入 `units.lagging`。

### D4　它和 `/model/generate` 的判据不是同一个问题

ADR-089 之后 `/model/generate`（不带 `force`）跳不跳一根，看的是「库级承诺覆盖到文件最新 ∧ 进程里有没落后的回执」。
库水位落后于文件最新、或后端重启过，它都会把根重算一遍，不管中间的会话碰没碰到这根。那是按需生成在「我能不能
证明这份几何可以直接用」上的保守判据。

节点模型状态问的是另一件事：「人看到的这份模型，和库文件最新比，内容上差不差」。所以会出现这里说 `latest`、而
generate 仍会重算的情形，两边都对。接口文档里写明：不要拿 generate 去刷新；已初始化的库追到最新走数据批次
（`update/execute`），它只重算被改到的根并推进水位，跑完之后两边的答案自然一致。

### D5　生成预检的阈值与历史对比共用一个

`precheck.needs_confirm = 阈值 > 0 且 (missing + failed) > 阈值`，阈值取 `node_diff_summary::confirm_threshold_units()`
（环境变量 `MODEL_HISTORY_CONFIRM_UNITS`，缺省 20）。「多少个单元以上要先问人」是一条成本策略，不该生成一套、
历史对比一套。

### D6　缓存只缓存由文件决定的东西

进程内缓存两类中间结果：子树的生成单元清单、一段会话之间的净差分。键里带库文件指纹（路径 + 长度 + 修改时刻），
各最多 256 项，满了整体清空，重启即失。水位、回执、账本、任务每次现读——它们是会变的事实，缓存它们就是在进程里
养一份可能过期的副本。

### D7　范围 generate 的回执带上逐根的生成会话

`/model/generate` 的回执多一格 `generation_root_sesnos`，与 `generation_roots` 逐项对应：每根的回执生成会话，没有回执为
`null`。前端的「已加载节点表」拿它记「装的时候是哪一版」，与 D2 第 2 条读的是同一个字段，不另造来源。

## 为什么不是别的做法

1. **建 SITE / ZONE 标记表**。见背景。用户已否（6.4）。
2. **用增量规划器整库预演一遍**（`WindowRootSources::collect` + `plan_window_roots`，问「从水位追到最新会重算哪些根」）。
   它是最准的那把尺子，级联和上级挪位都算得进去。但它是整库的：两端各枚举一遍全库的根，大库要十几秒到几十秒，
   放不进一次点击；而它的答案在下一次数据批次跑完时就过期了。留作以后的可选项：整库算一次、按库缓存、各节点取交集。
3. **逐会话判（`node/versions?since_sesno=`）**。前端过渡期就是这么判的。它冷算要走整条会话链（三个基线 SITE
   1.0–1.6 秒），而这里只需要水位之后那一段；它也给不出「哪几个单元」。净差分一次窗口就够。
4. **把 generate 的缓存判据放宽成这里的判据**。那是改 ADR-089，要先证明「没改到就可以直接用旧几何」在回执缺席、
   目录库前移这些情形下都成立。不在这一轮。

## 后果

- 前端一发拿全：三枚水位、生成过多少、落后多少、要不要确认。未初始化的库也答得出，不再整库枚举。
- 后端重启后，未初始化的库的节点回到「未生成」——它们的模型本来就只在进程内存里（ADR-079）。已初始化的库不受影响。
- 库文件比模型水位新、但没改到这个节点时，节点是 `latest`，库一级仍如实显示「有 N 个新会话未更新」。两句话都对。

## 已知的限度

- 尺子只看节点子树里的记录。上级节点挪了位置（查 ZONE 时 SITE 动了）、跨节点的级联（结构连接对端、电缆端点、
  设计引用）看不到，要等下一次数据批次。`node/versions` 与 `node/diff-summary` 同样如此。
- 目录库换了版本、生成器换了版本（ADR-093）不在这把尺子里：那是整库的事，由目录版本核对和启动时的整库重排处理，
  期间库一级会显示在更新。
- 不属于交付单元的生成根（STRU 之类靠「显著」兜底成根的）内部变了，归不到它头上，记在 `unattributed`。
- 「清理模型」清掉的子树在已初始化的库里仍按水位算已生成：水位不因清理而退。这与
  `dbnums/{dbnum}/model/roots` 的 `durable_ready` 是同一个既有口径，不是本文引入的。
- 范围强制重生成做到一半时不单列「更新中」，按当时读到的计数回。
