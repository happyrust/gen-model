# ADR-021：水位必须有数据支撑，回退默认整库重建

状态：已接受（2026-08-13 评审决议）  
日期：2026-08-13（同日修订：回退处置从「档位 opt-in 对齐」改为「默认整库重建」，档位与单库对齐端点随之移除）

引用的既有决策：ADR-001（DBNUM 状态记录是唯一水位来源）、ADR-011（手动与自动共用一条队列、一个派发器——2026-08-09 修订后默认单在飞批次、可配至 8——同一份谓词）、ADR-017（暂存窗口收口）。本 ADR **修订 ADR-001**：给「水位是承诺不是进度」补上它的对偶面，并**取代** ADR-001 的 2026-08-12 修订（watermark_realign 档位）。

## 背景

ADR-001 把 `applied_sesno` 定义成「数据确实落库了」的承诺，并且规定失败不得推进水位。这条纪律管住了**写**的一侧：没写成功就不许往上推。

但**读**的一侧有两个洞。

### 洞一：水位非零、库里零行 → 静默走增量

决定「这一批走全量基线还是走增量重放」的谓词只问水位，不问库里到底有没有数据：

```rust
// src/data_interface/manual_update.rs
fn needs_initial_load(applied_sesno: i32, file_latest_sesno: i32) -> bool {
    applied_sesno == 0 && file_latest_sesno > 0
}
```

真正会看数据的那个判据（`baseline_needs_full_parse`，`pe_count == 0 || applied_sesno == 0`）在 `initialize_dbnum_baseline` **内部**，必须先被上面那个谓词路由进来才轮得到。两者分工错位：**看得见数据的够不着路由，做路由的看不见数据。**

于是「水位非零，库里零行」这一格被判成正常增量：从 `applied + 1` 起重放，把 `1..applied` 那段当成已经在库里。该段永远不会被解析，而且不阻断、不告警、不留痕。

这一格不是假想出来的：

- **播种会造出它。** ADR-001「初始状态」一节规定：没有专属水位行但 `dbnum_info_table` 有历史统计时，以该 dbnum 的最大统计 `sesno` 回填。那张表是按 `ref_0` 的元素统计，可能来自另一段历史、也可能来自一次中断的解析。
- **现场实测。** 2026-08-13，AvevaMarineSample（8009）：dbnum 7350 / 7353 / 7741 的 `applied_sesno` 分别是 208 / 101 / 94，而 `pe` 表里这三个库**一行都没有**。证据见 `.scratch/realign-20260813-114321`。

### 洞二：文件回退的处置停在「阻断等人」，而阻断会静默消失

回退（`file_latest_sesno < applied_sesno`，文件被还原/替换）在默认档位下只阻断该 dbnum、打 F6 日志。问题有三：

1. **阻断会自己消失，而且是静默的。** 只要有人存盘把 `file_latest` 涨回 `applied` 之上，F6 不再报，增量从 `applied + 1` 接着走——回卷后重新长出来的同号会话内容已经不同，中间那段差异永远错过。2026-08-13 现场的 7350 距离这一幕只差 1 次存盘。
2. **等人，但人没有决策空间。** 回退意味着磁盘上已经没有那段被丢弃的历史，「等文件涨回去」不是一个选项（见上）；正确处置只有一种——按当前文件重建。一个只有唯一正解的状态不应该停机等人。
3. 2026-08-12 引入的 `watermark_realign` 档位（off/check/rebaseline）与单库对齐端点把重建做成了 **opt-in**，并且用的是「只删高于文件水位的残留 + INSERT IGNORE 补洞」的缝合式对齐——依赖「幸存行与新文件同史」的假设，靠基线完整性校验兜底。假设不成立时（文件被换成另一段历史）它响亮失败，库停在半修状态。

## 决策

### 1. 水位承诺的对偶

`applied_sesno > 0` **必须有数据支撑**。该 dbnum 在 `pe` 里一行都没有时，唯一正确的处置是**按首次导入重建基线**，而不是从水位往后接增量。

判据用**存在性**而不是计数（`dbnum_has_any_pe_row`：`SELECT … FROM pe WHERE dbnum = N LIMIT 1`）：问的是「有没有一行」，不是「有多少行」。计数在百万行级的 `pe` 上要秒级（2026-08-13 实测 1–9 秒），存在性判定语义上也更准确。查询只在 `applied_sesno > 0` 时才需要（`applied == 0` 本来就走基线），每个批次一次，不进会话循环。

存在性查询**失败必须上浮**：不得吞成「没有数据」（会把一个正常的大库整库重建），也不得吞成「有数据」（缺口继续静默）。与 `classify_scan` 同一条纪律。

### 2. 回退默认整库重建，不再阻断、不再有档位

检测到回退时，默认且唯一的处置是：**整库清空该 dbnum 的数据，按首次导入重新解析当前文件**。不进增量，不等人。

- 清库粒度是**整库**而不是「只删高于文件水位的残留」：缝合式对齐依赖同史假设，换成另一段历史时留下半修库；整库重建之后 DB 就是当前文件的函数，完整性校验（`pe_count - root == parsed_count`）天然自洽，「两段历史缝合」问题从根上消失。代价（大库小回退也付全量重建）是接受的——回退本身就是异常事件，正确性优先于代价。
- `watermark_realign` 档位（off/check/rebaseline）、`AIOS_WATERMARK_REALIGN` 环境变量、`POST /api/v1/dbnums/{dbnum}/realign` 端点与 Python 绑定 `aios_db.sync.realign` **全部移除**。回退的处置没有第二种正确答案，不需要档位；手工兜底保留现有 `DELETE /api/v1/dbnums/{dbnum}/data`（整库快删）与 `DELETE /api/v1/dbnums/{dbnum}/data/above/{watermark}`（残留清理）两个运维端点。

### 3. 清库动作在 worker 执行体里做，不在扫描时做

扫描（启动重扫 / 周期对账 / 文件事件 / 手动入队）检测到回退时**只分类 + 入队**一条带显式 `Reinitialize` 意图的重建批次，不动任何数据。`Reinitialize` 不受普通 `applied + 1..=file_latest` 数值覆盖门支配：文件最新会话为 0 时用 `0..=0` 控制窗口，非零时显示 `1..=file_latest`；它到达已有排队行时占优，到达同 dbnum 运行中行时必须留下后继行。普通 `ApplyWindow` 在 `applied == file_latest == 0` 时仍不入队。worker 出队后在冻结点**重新裁决**（`execute_one_dbnum` 现成的执行侧复核），仍判回退才调用 `wipe_dbnum_for_reinit` 清库，然后落进现成的 `needs_initial_load` → `initialize_dbnum_baseline`；清库后当前文件没有任何会话时直接以 Applied 收口并保持水位 0，不进入基线或增量收集。

理由：破坏性动作必须受 `startup_autorun` 与队列暂停约束。`startup_autorun = false` 的契约是「起来先什么都不执行」——若扫描时清库，一次重启就能在队列还挂着的时候删掉 42 万行。清库放进 worker，暂停/挂起对它就是真闸门，与本仓所有数据变更端点「先暂停队列」同一条纪律。

入队与执行之间文件可能被换掉，所以 wipe 必须以冻结点的**新鲜裁决**为前提（源码顺序测试钉住）。

与 ADR-017 的衔接（2026-08-13 live 首跑实测补充）：**暂存窗口只属于真正的增量重放**。按增量形状（`start_sesno > 1`）入队的批次，若冻结点的权威状态已经是「会改走首次导入」（applied 归零 / 回退 / 幽灵水位），必须**不开** kv-mem 暂存窗口、直接走执行体——基线不走窗口协议，开了窗口也等不来 finalize plan，只会以「暂存窗口缺少 finalize plan」失败收场。该预判（`batch_worker::batch_reroutes_to_initial_load`）与执行体路由共用同一个数据支撑探针；预判读不出来时按入队形状开窗，由执行体复核给出响亮终态。

### 4. `wipe_dbnum_for_reinit` 的口径

复用 `fast_delete` 的 Ref0 区间快删机器（关系边 → 区间行 → 元数据三阶段，自持 `STAGED_COMMIT_SERIAL` 与 `DBNUM_STATE_WRITE_GATE` 两把写闸），与整库快删端点唯一的差别在元数据阶段：

- `dbnum_watermark:{dbnum}` **清值不删行**（`applied_sesno = 0, sesno = 0, applied_sesno_time = NONE`，登记身份保留）——删行的话启动播种会从 `dbnum_info_table` 把水位回填成旧值（2026-08-04 播种审计第 5 条），且下一轮 classify 会把这个库误判成首次登记；
- 该 dbnum 的 `dbnum_info_table` 统计、`model_update_pending`、`increment_update_attempt`、`incr_side_effect_pending` 全部清空；
- 同一元数据阶段**递增 spatial epoch**：清库删掉了 `room_relate` / `inst_relate` 行却不 bump，崩溃重启会按指纹相等复用一棵还留着被删构件包围盒的树（ADR-010 D4 的幽灵形态）。
- 元数据阶段（统计与持久队列清理、spatial epoch、水位清零）必须包在一个显式 SurrealDB 事务中，且水位更新位于事务末尾；任一语句失败时整组回滚。关系删除与大区间删除继续作为前置的独立幂等阶段，失败后由下一轮重放。
- **（2026-08-13 补记，逆向核实确认漏删后修复）** Ref0 区间表清单补入 `room_panel_relate`，与 `room_relate` 成对清理：其 id 形态 `room_panel_relate:{room_refno}_{panel}`（`room_model.rs:698/724`）可按 Ref0 区间寻址；房间重算只对现存实体先清后写、从不整表清空，整库重建后的孤儿边无人回收，属 ADR-010 D4 幽灵同类。修复落点 `fast_delete.rs:25`（`RANGE_TABLES` 增表），回归测试 `the_wipe_deletes_room_panel_relate_alongside_room_relate` 钉住；跨 dbnum 边界与 `room_relate` 对称，未扩大也未缩小。

### 5. 只有回退这一种异常转重建

`TypeChanged` / `Duplicate` / `Missing` / `ForeignProject` 照旧阻断——它们是「这个 dbnum 对应哪个文件」的身份歧义，自动清库等于替人挑文件。`FileAnomaly::auto_realignable` 更名为 `requires_reinit`，覆盖集不变（仅 Rollback），它是「哪些异常转重建」的唯一裁决。

「库里没有数据」（洞一）**不进** `FileAnomaly`：文件本身好好的，判据两端也没有冲突，它走 `needs_initial_load` 这条路由线，且不删任何东西（没东西可删）。

### 6. 检出必须发声

- 回退重建：扫描日志点名「已按整库重建入队」，worker 清库时打出删除规模，批次回执写明「检测到回退，已整库清空并按首次导入重建」。
- 幽灵水位：判定为「水位非零而库里零行」时，日志与批次回执都要明说「水位与数据不一致，已按首次导入重建」。
- 只有 `println!` 而调用方回执里看不见的报告，视同没有报告（宪法：静默失效）。

### 7. 判据落在路由上，不落在入队门上

`needs_initial_load` 的数据支撑维度只加进「基线还是增量」的**路由**决策，**不得**加进 `discover_batch` 的入队门。

理由是「空库是合法状态」：`baseline_parse_confirmed_empty` 承认一个真的解析不出元素的库。这种库基线完成后 `applied == file_latest` 而 `pe` 仍为零行，若入队门也问「有没有数据」，它每一轮对账重扫都会被重新全量解析——无限循环。今天靠 `discover_batch` 的 `file_latest <= applied` 早退挡着，这条边界由源码顺序测试钉住。

## 结果

### 正面

- 「文件回退」与「水位说应用过、库里却什么都没有」都从**静默错误 / 停机等人**变成**会自愈并且会喊出来**的状态；「阻断静默消失、差异永久丢失」的时间窗随之关闭。
- 重建后 DB 严格是当前文件的函数，不存在缝合两段历史的可能。
- 手动与自动同一份判定（ADR-011），配置面净减一个档位、一个环境变量、一个端点。

### 代价

- 回退重建是全量代价：整库删除 + 全量解析 + 该库全部生成根的几何重生成（2026-08-13 实测 7350 一个库约 2 小时）。**升级即触发存量重建**：现网任何「水位超前文件」的库会在首次重扫排出重建批次（`startup_autorun = false` 下 held，放行才跑）。
- 每条数据批次在路由前多一次存在性查询（仅 `applied > 0` 时）。
- 预览的 `initialization_required` 语义扩大：回退与「登记过但数据没了」也标真。界面文案要能与「全新的库」区分。

### 约束与已知边界

- 清库只出现在 worker 执行体；扫描路径只分类入队（源码顺序测试钉住）。
- 数据支撑判据不得下沉到入队门（守护测试钉住）。
- **服务停机窗口内文件回退又长回去**（回退从未被任何一轮扫描观察到）无法靠会话号检出；`applied_sesno_time` 与文件同号会话时刻的交叉核验是后续项，本期不做。
- 在水位行上记录「这条水位是怎么来的」（基线收口 / 增量收口 / 播种回填）仍是值得做的后续项：它能把幽灵水位在扫描阶段就查出来，也能正面区分「基线过的空库」与「从没基线过的库」。要动 schema 与启动播种路径，单独一轮做。

## 未采用方案

### 保留 watermark_realign 档位、默认值改 rebaseline

拒绝。回退的正确处置唯一（见决策 2），档位剩下的价值只有「先看看」，而这层保护已由 `startup_autorun` / 队列暂停承担（清库在 worker 里，见决策 3）——同一件事不需要两道闸门，多一个配置项就多一种「装置状态与预期不符」的现场。

### 缝合式对齐（只删高于文件水位的残留 + INSERT IGNORE 补洞）作为默认

拒绝。它依赖「幸存行与新文件同一段历史」的假设；假设不成立时基线完整性校验响亮失败，库停在「删了一半、建不起来」的状态等人。作为 2026-08-12 的档位实现它服役过一天，被本决议取代。

### 用 `dbnum_info_table` 的行数代替 `pe` 存在性判定

拒绝。那张表是观察值不是权威值，而且它**正是**伪造水位的来源之一——拿它去证明水位有数据支撑，等于让嫌疑人给自己作证。

### 把「无数据」并进 `FileAnomaly`

拒绝。它不是文件异常（文件好好的），也不该改变 `requires_reinit` 的覆盖集语义——那个谓词回答的是「哪种**文件异常**要重建」，库侧状态由路由谓词回答。

### 取消 `dbnum_info_table` 播种

拒绝。播种是历史库免于全量重解析的唯一通道。真正的问题是播种出来的水位没有数据支撑时会被增量路径当真，本 ADR 修的正是这一点。

### 启动时对全部 dbnum 做一次「水位 vs 数据」体检

拒绝（本期）。全表扫描在生产库上是分钟级；它能发现的问题，路由判据在该库真正要跑批次时同样能发现，且只付一个库的代价。
