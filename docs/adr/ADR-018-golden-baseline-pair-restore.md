# ADR-018：L3 实机套件以「金基线成对恢复」管理测试数据生命周期

状态：Accepted（2026-08-06）
关联：ADR-001（水位与文件异常裁决）、ADR-016（监控目录与项目数据域）；CONTEXT.md「实机端到端测试」章节；执行剧本 `docs/2026-08-06_e3d-l3-automation-test-plan.md` §4

## 背景

E3D 的 SAVEWORK 永久追加会话、refno 永不复用，所以实机测试的「改完还原」没有天然手段。
更要命的是 gen-model 的文件异常裁决把**会话回退列为阻断性异常**：如果只把 .db 文件恢复到旧备份
而 Surreal 侧水位不动，`file_latest_sesno < applied_sesno`，该库直接被阻断——单边恢复不是还原，
是自杀。历史上属性场景用 apply/restore 宏对凑合（库只长不缩），删除场景靠手工同时处理文件备份
与 Surreal 侧，无法交给无人值守套件。

## 决策

L3+V 自动化套件的每一轮运行，都从**金基线对**整体恢复起跑：E3D 项目副本与 Surreal 数据快照
是一个不可拆的版本化整体，恢复必须两边一起、恢复后校验「三库文件 latest sesno 与库侧水位
等于金基线记录值」，**不成对即拒跑**。轮内属性类场景照用场景宏对（restore 顺带验证反向增量），
删除/新增类场景排在轮尾，由下一轮的整体恢复兜底。空间树文件不入金基线，恢复时删除、
启动后从库指针重建。

## Considered Options

- **活库模式**（不做整体恢复，全靠 apply/restore 宏对）：零恢复成本，但删除/新增的回滚仍要
  单边文件恢复（阻断坑还在），且任何一次 restore 失败都会永久污染基线，漂移不可审计。拒绝。
- **每场景整体恢复**（最彻底的隔离）：场景间零串扰，但每场景多一次恢复加整栈重启，套件时长
  膨胀数倍，还丢掉 restore 宏顺带的反向增量覆盖。拒绝。

## Consequences

- 金基线是版本化资产：场景需要新库基线或 E3D 项目升级时铸新版本，台账记录 `(file_latest_sesno,
  applied_sesno)` 对；
- 恢复要求整套栈（E3D / 服务 / Surreal）全停，套件天然单机串行、不进无人 CI；
- 轮内场景相互可见（同一持续演进的会话流），场景表的顺序是语义的一部分——删除/新增必须排轮尾。
