# CATA 依赖闭包缓存：实测（plan `docs/plans/2026-09-15-cata-dependency-closure-cache-dev-plan.md`）

## 基线（S0 取证，2026-09-15，缓存尚未落地）

**怎么量**：`resolve()` 里加拆项账（`ClosureAccount`：open / parse / expand 耗时、`parse_element` 请求数 / 成功数 /
本进程首见数、会话数），`resolve_dependency_rows` 加 identity / 装行耗时并打一行 `[cata_closure] …`；基线路与三条落库路的
回执（`DependencySummary` / `CataDependencyReport`）加 render 耗时与 SQL 字节。**只加账，不改行为**（`cargo test --lib` 不退步）。

**跑什么**：`initialize_ams_dbnums --with-model <dbnum…>`，release，每轮全新 rocksdb（`surreal.exe` 拉在 **8011** 端口——8009 被另一
会话的 `rocks-full` 店占着，没碰它），`DB_OPTION_FILE` 指一份只改 `watch_dbnums` / `v_port` 的 DbOption 副本。
harness：`%TEMP%\cata-cache-eval\run-init-cata.ps1`（ADR-077 那套 + `-Port` / `-Dbnums`）。工作树 `codex/model-projection-cache@917e85893` + S0 账。

### 读数

1. **解析本身很便宜**：7997 整份闭包 resolve 777 ms（open 300 + parse 459），占初始化 162 s 的 0.5 %；8000 527 ms / 21 s = 2.5 %。
   PLAN「减少重复打开与解析」在初始化这条路上省的是**亚秒级**。
2. **贵的是渲染与字节**：7997 render 5.2 s、SQL 17.6 MB；8000 render 1.7 s、SQL 10.3 MB。属性 lane 吞吐 ≈ 0.8 MB/s（7997 131.6 MB / 162 s，
   8000 16.8 MB / 21 s），所以 CATA 块在 lane 上要 **7997 ≈ 22 s（13 %）、8000 ≈ 13 s（62 %）**——小设计库的初始化墙钟一大半是目录行。
   要省这一截只有「不发」（plan D6）；解析缓存对它一个字节都省不了。
3. **轮内重复请求**：`parse_element` 请求数 > 成功数 + 缺失数——7997 **21,592 vs 15,500（6,088 次 = 28 % 白解）**，8000 15,489 vs 14,021（9.5 %）。
   机制：上一轮 `next` 里同一个 refno 被多个父元素指到、`frontier.push` 不去重，本轮 `to_parse` 只滤 visited 不滤自身重复，
   `parse_refnos_with_session` 逐条解、`HashMap` 收敛时才合。**一行去重就能拿回的 28 %，与缓存无关，单独一片（S1a）先落。**
4. **跨库复用很少**：1112 → 8000 → 7997 同一进程顺序初始化，8000 首见 14,020 / 14,021（与 1112 重叠 1），7997 首见 **14,801 / 15,500（与
   1112 + 8000 重叠 699 = 4.5 %）**。三库闭包的并集 ≈ 29,000 个目录元素。PLAN「1112 / 7997 / 8000 复用预热」在初始化上只值 4.5 %；
   缓存真正的用处在**初始化之后**——每个增量窗口、每个模型根发布重解的都是同一批目录元素（本轮没量到，见下）。
5. **会话 open 占 resolve 39 %**（7997：300 / 777 ms；每会话 ≈ 30 ms）。plan Q4 的 10 % 门过了 → D5 会话保活**做**（S2b）；
   但缓存全命中时根本不开会话，所以它只对部分命中的窗口有用，别指望它单独换来什么。
6. **闭包宽度（另议，不在本计划）**：8000 设计库 6,637 个元素，闭包却 14,021 行、其中 5052 一库 13,280 行；7997 170,085 个元素闭包 15,500 行。
   「闭包比实读宽是允许的」（ADR-064 D5），但小库上目录行比设计行多一倍，对 lane 字节的影响比任何缓存都大——值得单独量一次
   `catalogue_visited` 与 `closure` 的差集在哪些 noun 上。

### 单位成本（供窗口路估算，缓存落地后对照）

| 项 | 单位成本 |
| --- | --- |
| `OnDemandDbSession::open` | ≈ 25–30 ms / 库（7 库 178 ms，10 库 300 ms） |
| `parse_element` | ≈ 0.02 ms / 次（7997：459 ms / 21,592 次） |
| render（`ElementRows::render` + 装事务） | ≈ 0.12–0.33 ms / 行（8000 1,733 ms / 14,021；7997 5,188 ms / 15,500） |
| SQL | ≈ 0.74–1.14 KB / 行（8000 10,340 KB / 14,021；7997 17,605 KB / 15,500） |
| 属性 lane | ≈ 0.8 MB/s |

一个碰到 10 个目录库、闭包 2,000 行的增量窗口，今天的 CATA 块估 ≈ open 0.3 s + parse 0.05 s + render 0.4 s + 2 MB SQL（lane ≈ 2.5 s）——
缓存全命中时前两项归零、D6 命中时后两项归零。**这一估算 S5 要用真窗口对一次。**

### 没量到的

- **窗口路 / 模型根路**：需要 E3D TTY + 隔离 AMS 工程 + live 服务的 `scripts/increment_matrix` family 流程（README：不得并发 TTY），
  本轮没跑；S5 A/B 时一并量。上面「单位成本」是它的替身。
- **三库同进程的总墙钟**：`1112 8000 7997` 那一轮在 7997 属性 lane 写到 cata=7002 时 rocksdb 报 `No space left on device`
  （C: 只剩 3.9 GB，三库一店装不下），任务按纪律清库、`Error: 1 dbnum baseline(s) failed`；闭包账在失败前已打完，读数 4 用的就是它。
  要重跑得把数据目录放到别的盘。

## S1a 轮内去重（2026-09-15）

`resolve()` 的本轮解析名单改经 `round_parse_list(refs, &visited)`：滤 visited + 去掉本轮自身重复，保持首次出现顺序；
单测 `a_round_parses_each_refno_once_even_when_several_parents_point_at_it` + 源码钉。7997 同一 harness 复测：

| | S0（去重前） | S1a（去重后） |
| --- | --- | --- |
| `parse_element` 请求 / 成功 | 21,592 / 15,500 | **15,502 / 15,500**（多出的 2 = 7000 库里 not found 的那两个；另 2 个缺失是 no dbnum mapping，到不了解析） |
| parse | 459 ms | 427 ms（重复解析吃的是热页，省得不多——省下的主要是 6,090 次调用与日志 / 留痕） |
| resolve / open | 777 / 300 ms | 755 / 304 ms |
| 闭包 | 15,500 行 / 10 库 / 7 轮 / 缺失 4 | **同** |
| `COUNTS` / 水位 / `gen_root` / `pe.dependency` 行数 | — | **与 S0 逐字相同**（pe=187396 … gen_root=6772；184/184；15,500） |
| 初始化总墙钟 | 162.7 s | 154.6 s（机器噪声量级，不归功于去重） |

读数：白解的 28 % 次数拿回来了，**时间只省 30 ms**——重复请求命中的是刚读过的页，`parse_element` 本身就便宜。
它的价值在窗口路上更大一点（每窗都要重来），但仍是次要项；真正的钱在字节（D6）。`cargo test --lib` 2066 passed / 0 failed。

### 结论 → 对计划的修正

- 加一片 **S1a 轮内去重**（`to_parse` 去重，行为不变），先于缓存单独量一次：7997 预期 `parse_element` 21,592 → 15,504。
- D5 会话保活：做（S2b）。
- D8 默认上限：三库闭包并集 ≈ 29,000 个元素、SQL ≈ 1 KB/行，属性表本身应在同一量级 → 200,000 条 / 256 MiB 是「整份 AMS 目录 × 6」，够；不改。
- 性能门（plan §5.3）按本表填「关」列；「初始化总耗时不回退」这条对解析缓存本身几乎没有区分度（省 < 1 s），改看
  **窗口路的闭包耗时与 CATA 块字节**（S5 真窗口）。

## S2 接进 `resolve()`（2026-09-15）

缓存接线只在 `CataClosureResolver::resolve()` 一处：每库先取身份（文件指纹 + 目录会话号）→ 查缓存 →
命中的直接扩边落 manifest、**连库会话都不开** → 没命中的过本库那把闸、重查一次、再解析 → 解析成功的写回。
扩边抽成 `expand_into()`，命中路与解析路共用（源码钉）。S0 的临时首见表 `SEEN_PARSED` 删除，账改由缓存的
`cache_hits / cache_misses` 出；`ClosureAccount` 另加 `identity_ms`（取身份是新增的那一笔文件头读）。

### 真库 A/B：ams8000 同一批 seeds 连解两次（`live_a_second_resolve_of_the_same_seeds_comes_from_the_closure_cache`）

| | 冷（第一次） | 热（第二次） |
| --- | --- | --- |
| 缓存 | 0 命中 / 13,998 未命中 | **13,995 命中 / 3 未命中** |
| `parse_element` 请求 / 成功 | 13,998 / 13,995 | **3 / 0** |
| 打开的库会话 | 6 | **1** |
| resolve | 456 ms（open 174 + parse 242） | **57 ms（open 21 + parse 0）** |
| 闭包 | 13,995 行 / 6 库 / 8 轮 / 缺失 4 | **逐位相同** |

重来的那 3 个是 `13244_271598 / 271629 / 271645`——请求得到、**库里根本没有**（`Ok(None)`）。按设计不进缓存：
记下来就是把「此刻查不到」写成「永远没有」。它们连带把 5052 那一库的会话又开了一次（21 ms），所以热跑的
open 不是 0。第 4 个缺失是 `no dbnum mapping`，到不了解析这一层。

### 对拍 oracle 在热缓存下重跑

`live_ams8000_catalogue_reads_are_covered_by_the_dependency_closure` 与上面那条同进程连跑（第二条跑时缓存已满）：
`visited 6117 · catalogue_visited 5009 · closure 13995 · missing 4 · unexplained 0`——与冷跑逐字相同。
**缓存喂出来的闭包与文件解出来的闭包是同一个**，这是 S2 最要紧的一条。

### 读数

1. **省的是 open + parse 这 416 ms 里的 399 ms**（456 → 57）。8000 的闭包 resolve 本来就只占初始化的 0.5 %，
   所以这一片对**初始化总墙钟**仍然没有区分度；它的钱在**窗口路**——每个窗口都要重来一次这 456 ms，
   而窗口的目录闭包与上一窗高度重叠。
2. **open 从 6 次降到 1 次**：D5 会话保活（S2b）的收益被这一片吃掉了一大半——全命中的库根本不开会话。
   S2b 要不要做，等 S5 用真窗口量完再定（那时剩下的 open 只发生在部分命中的库上）。
3. **字节一个没省**：热跑照样渲 13,995 行、照样发同样的 SQL。这正是 D6（S3 已落库去重）要解决的那一半。

### 顺手改掉的一处浪费

`parse_refnos_with_session` 原先给 `attmap_sink` 的是 `merged.clone()`——属性表交出去之后本函数不再用它
（`noun_name` 挪到 clone 之前取即可）。改成搬走：每个元素省一次 `NamedAttrMap` 深拷贝。加上缓存写入那一次，
`retain_attmaps` 开着时的拷贝次数与改动前持平（1 次），关着时是 0 次。

### 缺陷在哪

`FIXING` 的 owner 链是 `WALL → JLDATU → PLDATU → FIXING`，而 **`JLDATU` 与 `PLDATU` 两级都没有
POS/ORI**——它们的标架是**隐式**的：

- JLDATU 的位置由 `ZDIS` 沿宿主 WALL 的 spine 弧长定出来；
- PLDATU 的 `POSL=OBOW` 是 E3D 的隐式墙 pline（PLAX=-X），配 YDIR=+Z 得到列 (-Y, +Z, -X)。

`transform::world_matrix` 逐级乘 `local_matrix`，在这两级上乘的**是单位阵**。
墙上开孔的那把刀（`elmodl::fixing_world_cutter`）早就把这两级算对了，而 **FIXING 自己那一件实例**
走的是 `catalogue::model_catalogue_member` 里的 `world_matrix(member)`——**两处各算各的**，
于是刀切对了位置、件却落在别处。

### 改法：两处共用一个标架

抽出 `elmodl::fixing_host_frame(wall, fixing)`（= `world_matrix(wall) × joint × pldatum`）与
`elmodl::fixing_host_wall(fixing)`（按 noun 上溯找宿主墙——`collect_host_fixings` 是从 WALL 递归
**下来**的、层数不固定，反过来不能数层数）。开孔刀与
`catalogue::catalogue_member_world` 现在都走它。**同一条规则只有一处实现**，
这正是「命中路与解析路共用一处扩边」那条纪律的同型。

### 一、GWALL 13 多出来的不是一块料，是一根贯穿全高的针

`17496/116569` 的生成物有**两个连通片**：

| --- | --- | --- |
| 主片 | 2,786,812,305.7 mm³ | 874.4 × 2,394.6 × 3,620 mm |
| **第二片** | **294.9 mm³** | **1.254 × 20.717 × 3,620 mm** |

第二片斜长 20.76 mm、**等效平均厚度 0.0039 mm**、从 z=−20 站到 3,600。占整墙体积 **1.06e-7**。
它的位置正是报告里那 5 个「最远 gen 点」（局部 x∈[613.42, 614.67]、y∈[2399.72, 2420.44]），
两端就是接缝刀 NXTR `17496/116928` 的原点 A=(614.985, 2394.569) 与它环上的顶点
B=(613.428, 2420.440)——主片的 y 上界恰好停在 A，针贴着 A→B 这条边站着。
`17496/116894`（2160 以上那把）的一条边与 A→B **同向**（局部方向 (−0.0601, 0.9982)），
所以上下两段都留同一根。

**E3D 侧同一处也有这个退化，只是塌成了零厚度**：RVM 在那儿只有两个 xy 点（相距 0.009 mm）、
z=2,160 与 3,600 的四个顶点——一张没有体积的面片；**2,160 以下什么都没有**。
我们那根针比它多出 2,160 以下的一段，2,010 mm 的 Hausdorff 就是针的下端到最近一张真表面的距离。

旁证三条：

- **体积**：gen 2,786,812,601 mm³ vs RVM 面片实算（散度定理）2,786,819,721 mm³，
  差 **−7,120 mm³** = 2.6e-6，是 RVM f32 坐标的噪声量级；针的 295 mm³ 比这个噪声还小 24 倍，
  体积这把尺根本量不到它。
- **AABB** 差 0.0018 mm、**p95** 0.0014 mm、**`rvm→gen` Hausdorff 0.0028 mm**：
  除了这根针，两边逐点重合。
- 全墙只有它一个多连通片（20 只 GWALL + 4 只 WALL 里独一份）。

所以这不是「该切的洞没切」，是共壁布尔在接缝边上留的毛刺——`solid.rs` 模块文档记的同型
（「差完留下一根 0.01mm 厚、贯穿全高的针」，当年是世界系 AABB 缩放那一版）。
`MANIFOLD_NUDGE_MM` 不能再加：0.01 在**这只墙**上实测过切 25.88 mm。
该做的是**布尔之后按 libgm 的面级容差 `RES_TOL_MM = 0.051 mm` 丢掉薄于它的连通片**：
这根针 0.0039 mm，比容差薄 13 倍，丢它不会碰到任何真几何。

### 改了什么（`vendor/e3d-model`，+112/−18）

- `elmodl.rs` 的正体臂在负体之后多一档宿主刀：`noun == "GWALL"` 时 `collect_host_sleeves`

  `DESP.len() >= SBFI_DESP_MIN` 门），逐根调 `sleeve_world_cutter`；建不出来的照 FIXING 那条
  记进 `negatives_skipped`，不静默。
- 洞 = `sbfitting_bore_from_desp`：与套管本体**同一份 DESP、同一组顶点、同一处平移**
  （抽出 `SBFI_SEGMENTS = 8` 与 `sbfitting_ring`，环换成 `OD` 实心柱，`(x, y, z−LEN)`）。
  依据是逐点实测：RVM 里洞的内壁是**内接**于 `OD/2` 的八边形（采样点径向落在边心距
  `62·cos22.5°=57.3` 与顶点 `62` 之间；OD 186 的那些落在 86.1~93.5，同样是八边形而不是十二边形）。
- 标架抽成 `sbfitting_world = world_matrix × sbfitting_catalogue_alignment`，
  **套管实例与开孔刀共用这一处**——`FIXING` 在同一天刚栽过「两处各算一遍」的跤。
- 新增单测 `a_sleeve_bores_its_own_outer_octagon_through_the_host`：洞是实心八棱柱
  （体积 = 内接八边形面积 × 长）、包围盒与套管本体逐轴相同、短 DESP 同样建不出洞。
