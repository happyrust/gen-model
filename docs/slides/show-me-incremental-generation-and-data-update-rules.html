两类更新：属性更新 ≠ 模型更新 每一次 SAVEWORK 都是属性更新，但只有一部分会变成模型更新

E3D 里任何一次改动（新增 / 修改 / 删除 / 搬迁）落到库文件里都是属性记录的变化——数据面照单全收、每个元素一条净变化。模型是从属性算出来的派生物：只有当变化会改变几何或位姿时，才值得重算；而且重算的单位不是「这个元素」，而是它所属的生成根。

属性更新（数据面）

「库里的数据是不是最新的」
  • 触发：库文件会话号前进（file_latest_sesno > applied_sesno），无条件。
  • 范围：这一窗 S→T 里每个被改过的元素，各一条净变化 Add / Modified / Deleted。改了 NAME 也算、只改了描述也算。
  • 做什么：把 T 时刻的属性记录整行替换进库；删掉的元素留墓碑。
  • 凭证：applied_sesno —— 数据追平到哪个会话。
例
设计员把 /P-101-B1 这条 BRAN 的 DESC 从「主蒸汽」改成「主蒸汽 A 线」并 SAVEWORK。→ 属性面板下一秒就能看到新描述；模型一个三角面都没动。

模型更新（模型面）

「已生成的三维模型还对不对」
  • 触发：只在变化被判为 Regen 或 TransformOnly 时；Skip 的变化模型不动。
  • 范围：变化元素上卷到它的生成根（默认 BRAN / HANG / SUPPO / EQUI 这类交付单元），整根重算或整根刚体移动。
  • 做什么：直接按 T 时刻的库文件重新求几何（模型面是纯函数，不依赖库里的属性行）。
  • 凭证：model_sesno —— 模型追平到哪一版数据；永不超过 applied_sesno。
例
同一条 BRAN，设计员把一个弯头 ELBO 换成另一个规格（SPRE 变）。→ 属性照常更新；同时整条 BRAN 的几何按新文件重新生成，不是只重画那个弯头。
所以同一个 SAVEWORK 之后，可能出现「新属性 + 旧模型」的短暂中间态——这是被承认并可观测的设计（两枚水位分别表达），不是数据污染。两枚水位相等时，数据与模型一致。

什么时候会触发模型重新生成 一次变化对模型只有三种意义：Skip · TransformOnly · Regen

判定原则是宁多勿漏：新增、删除、成员变化、看不清改了什么 —— 一律重生成。想「少算」必须拿到证据：只动位姿才能走 TransformOnly；字典说它不影响图形（DCHC = 0）∧ 生成器根本不读它，两票齐才算 Skip。

原理判据从哪来

impact(一次元素操作):
  if 新增 or 删除 or 成员/顺序变 or 看不清改了什么
    return Regen
  for 每个变化的属性 a:
    if 字典DCHC(a) == 0 and 生成器不读(a)   # 两票
      记 Skip                                # 少算要证据
    elif a ∈ {POS, ORI} and 元素不是几何容器
      记 TransformOnly
    else
      记 Regen                               # 默认方向
  return 最重的一档                        # Regen > TransformOnly > Skip
  • 与 E3D 自己一致：core 交互路按属性字典的 DCHC 类别决定「不动 / 只改矩阵 / 整件重画」，我们的三态就是它的映射；但 core 在跨会话 GETWORK 上是任何记录重写都整件重画——我们比它更省，所以「少算」的两档才要两票。
  • 预览（改动前问「会影响模型吗」）与真正执行用同一个判据，不会一边说不影响、一边又重算。
一句话
属性面板关心「值变了没」；模型只关心「形状或位置变了没」。

重算的单位是「生成根」，不是被改的那个元素 变化元素向上归一到恰好一个根；一根一窗只算一次

属性更新的粒度是元素（一个 refno 一行）；模型更新的粒度是生成根——一个具备独立成败与独立交付语义的模型单元。这样做的原因：几何是整体求出来的（管段随弯头走、面板随顶点走），部件级重画既不安全也不省。

规则变化元素怎么找到它的根

root_of(e):
  # 1. 最近的「最小交付单元」祖先（含自身）
  #    默认 BRAN / HANG / SUPPO / EQUI，可按项目配置
  if e 或其祖先 ∈ MDU: return 最近的那个        # 交付单元根
  # 2. 没有 MDU 祖先：跨过 LOOP/PLOO/VERT/PAVE 这类
  #    几何容器，上溯到最近的非 SITE/ZONE 属主
  if 找到: return 它                             # 正常颗粒根
  # 3. 自己就是 SITE / ZONE / WORL：不生成
  return 不整区重算
  • FTUB（隐含管段）永远不是根，继续往上找 BRAN。
  • 「父模型输入」型子元素（GENSEC 的 SPINE/POINSP、PANE 的顶点）自身不出模型，变化归到父级根。
  • 几何数据容器（graphicsBehaviour = 1，如 LOOP）不独立成件；层级容器（= 2，如 ZONE）永不单独重画。
  • 桥架：把 CWBRAN 配成交付单元后，托盘 CTRAY / 直段 CTSTRA / 路径点 POINTR 全部归到 CWBRAN；默认集下托盘只归到直接属主 CTSTRA。
  • 同一根一窗只生成一次：一条 BRAN 里改了 5 个件，仍只重算 1 次。

搬迁的例子
把 TEE 从 /P-101-B1 挂到 /P-101-B2：这一窗两条 BRAN 都重算——旧根少了一件（管段要重连），新根多了一件。
不重算的例子
新建一个空 ZONE、给 SITE 改名：属性更新照做；模型侧没有任何根被触到。

一次保存会波及多远 本窗触到的根 · 不再是根的 · 没被碰到的 · 别人变了却牵连到我的（联动）

把窗口 S→T 两端的根集合并起来看，每个候选根只有一种去向。没被碰到的根什么都不做——这是增量比全量省的全部来源；「被碰到」除了自己子树里有变化，还包括联动：别处的变化改变了我的形状或位置。

去向一个根在这一窗的五种结局

去向条件例子
regenT 端是根，且子树里有 Regen 级变化（或被联动点名）BRAN 换了弯头
transform已发布根，子树里本窗只有位姿变化EQUI 整体挪了 2 m
deleteS 端是根、T 端不再是根删掉整个 EQUI；或 BRAN 被挂到别的 MDU 之下
advance两端都是根、没被碰到这次 SAVEWORK 只改了别的 ZONE；这份几何到 T 仍有效，零成本
lazyT 端新出现的根、从没生成过、也没被碰到刚导入一个库但没人看它 → 等第一次被打开时按需生成
典型的一次 SAVEWORK
一个 900 根的库，设计员改了 3 条 BRAN、挪了 1 台 EQUI、把 2 个 SITE 改了名：属性侧写入这一窗的全部变化行；模型侧 3 regen + 1 transform + 896 advance，896 根一个三角面都不碰。

安全阀：若这一窗变化太大（候选超过索引的 30%）或依赖关系解析不全，就不再相信「没被碰到」的判断，把两端都在的根全部重算——宁可多算，不留陈旧几何。

联动别人变了，为什么我要重算

变化发生在牵连到
容器（ZONE / SITE）的 POS / ORI子树里每个根：整体换矩阵（不重网格）
删除一个容器它下面全部子孙的根：清掉几何；被搬走的后代按搬迁算，不按删除
改挂（OWNER 变）旧根 + 新根都重算
元件库（CATA：SCOM / GMSET / 截面 / 规格）改了引用它的所有设计根都过期 → 按目录版本核对整库排重算
隐含管段的邻居只动了位姿管段要重连 → 便宜路径改判整根重算
房间定义（PANE / FRMW / SBFR / CWALL / CFLOOR）变了该库全部构件的房间归属重算；几何本身不重生成
结构连接：SCTN-A 端头连在 SCTN-B 上（A 的 CREF → B，B 的 JOIS/JOIE 回指 A）；B 挪位或换截面A 的端头是贴着 B 定位 / 切割的 → 对端 A 的根也重算（E3D EVALAT 同此；本系统同库版已接线，开关默认关）
电缆端点：EQUI / ELCONN 挪位或接线变；CWBRAN 桥架分支变接在它上面的 CABLE（STAREF/ENDREF 反向查）、路过这条桥架的电缆都要重画；电缆几何尚未按路由落地，几何上暂无表现
管道连接（HREF / TREF）不需要额外联动：E3D 把接头位置回写进 BRAN 自己的 HPOS/TPOS，变的是 BRAN 自己
UDA 定义依赖、XRPNTR 交叉引用明确不做（不参与几何）
元件库的例子
规格员把 /SPEC-A/ELBO-90-100 这个 SCOM 的几何集改了一个参数：设计库里没有任何一行属性变化，但所有用了它的 BRAN 形状都变了——所以模型侧记「这个设计库照的是哪一版目录」，目录版本一变，整库引用它的根重算。

对照 · 5 / 5

属性更新 vs 模型更新：差别一览 触发 · 粒度 · 版本 · 失败 · 一致性

两者共用同一份「S→T 谁变了」的文件差分，从那一刻起分道：数据面追求每一版都到，模型面追求只算该算的。

属性更新（数据面）模型更新（模型面）
什么时候发生库文件每前进一个会话就发生，无条件只在变化被判为 Regen / TransformOnly、或被联动点名时
更新的单位元素（refno）：一行一条净变化生成根：整根重算 / 整根刚体移动 / 整根删除
输入库文件 S→T 两端记录的差分库文件 T 时刻本身（纯函数，不看库里的属性行）
结果长什么样属性行整行替换；删除留墓碑几何记录 + 世界变换 + 房间归属边；未变根原样保留
版本凭证applied_sesno：数据追平到哪个会话model_sesno：模型追平到哪一版数据；≤ applied_sesno
失败了会怎样整窗不推进水位，下次按同一区间重放（幂等）只这一根留痕、不阻断数据水位；下一窗碰到 / 按需打开 / 启动补算时再算
用户看到什么属性面板 / 搜索立刻是新值模型稍后追平；期间「新属性 + 旧模型」是被承认的中间态
什么叫「一致」applied_sesno > 0 ∧ model_sesno == applied_sesno ∧ 没有还在算的根 → 数据与模型一致；落后是常态不是告警

推论「模型版本」比「属性版本」稀疏

一个交付单元的模型版本表只列它被碰到过的会话，每条带一档影响：delivery（单元出现）/ tombstone（被删）/ mesh（形状变）/ placement（只挪位）/ noop（碰到了但全是 Skip）。

例：BRAN /P-101-B1 的一生
sesno 12 建成 → delivery
sesno 15 改 DESC → noop（属性版本 +1，模型版本不变）
sesno 18 换弯头 → mesh
sesno 21 整条挪位 → placement
sesno 30 被删 → tombstone
属性历史有 5 个版本，模型对比只需要看 12 / 18 / 21 / 30 四个；版本对比时 15 那一版不必重新生成几何。
  • 模型版本是从会话链按需算出来的派生量，不落库；判据与生成路是同一把尺子，两边不会各说一套。
  • 历史投影（看某一版的几何）也按需算、不进库、不进水位。
