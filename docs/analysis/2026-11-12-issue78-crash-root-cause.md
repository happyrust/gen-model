# #78 发布包范围生成中段 `0xC0000409` 同偏移连崩：根因与取证（2026-11-12）

## 结论

- 这几次崩溃是**内存分配失败**：整台机器的可提交内存（物理内存 + 页面文件）被用到上限，后端申请一两兆内存时被系统拒绝，Rust 标准库随即 abort。不是栈溢出，也不是某一段生成代码的确定性缺陷。
- 占着内存的主要不是后端。崩溃发生在开发与验收共用的那台机器上，同一时刻并行着多个编译器、浏览器和 IDE 代理进程；后端自己最多占 5.8 GB，有两次崩的是几乎空闲的进程。同一时段数据库服务也以同样的方式退出。
- 「每次同一个偏移」不指向任何一段业务代码：在同一个构建里，**不管在分配什么，分配失败都死在同一条指令上**（见第 5 节的演示）。
- 没能做到的：当时那两个构建的二进制与符号文件都已不在，偏移解不到函数名和行号；也没有在正式进程上复现（那要把整机内存耗尽）。

## 证据

### 1. 系统事件日志：哪几次、哪个构建、什么偏移

应用崩溃事件（Application Error，事件 1000）里，release 构建的后端共 9 次 `0xC0000409`：

| 时间（本地） | 构建（PE 时间戳） | 出错偏移 | 当时在做什么 |
|---|---|---|---|
| 10-16 08:47:38 | 发布包 A（`6ad0169e`） | `+0x414a811` | 运行了 8 个多小时 |
| 10-16 10:07:17 | 发布包 B（`6ad155a6`） | `+0x41b9e11` | 这一轮的日志没留下 |
| 10-16 11:21:28 | 发布包 A | `+0x414a811` | 起来 5 分钟，只生成过 4 个根 |
| 10-16 11:41:44 | 发布包 A | `+0x414a811` | 空闲，只有 30 秒一轮的增量检测 |
| 10-19 12:27:37 | 发布包 B | `+0x41b9e11` | 范围生成中（这一轮已有 445 次「几何生成开始」） |
| 10-19 12:34:44 | 发布包 B | `+0x41b9e11` | 范围生成中（90 次） |
| 10-19 12:41:31 | 发布包 B | `+0x41b9e11` | 范围生成中（18 次） |
| 10-19 13:17:54 | 发布包 B | `+0x41b9e11` | 范围生成中（14 次） |
| 10-28 12:16:55 | 本地 release 构建（`6ae08b6a`） | `+0x435a021` | 日志没留下 |

票面说的「同偏移连续崩」就是发布包 B 在 10-19 的四次。同一个构建偏移相同，换一个构建偏移就变。

### 2. 进程自己的 stderr：七次都以分配失败结尾

留着 stderr 的七轮（上表除 10-16 10:07 与 10-28 两次），最后两行都是同一个样子：

```
memory allocation of 1671856 bytes failed
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

七次的大小依次是 1671856、1764888、1743728、3784704、2097152、1909248、1638416 字节。这是标准库默认的分配失败处理打的两行（没有 `thread … panicked at`，所以不是 panic），打完就 abort。

### 3. 系统自己的诊断：每一次崩溃的同时，整机虚拟内存不足

Windows 的资源耗尽检测器（系统日志，事件 2004）在整机提交量逼近上限时记一条「虚拟内存不足」的诊断，带当时的提交量、上限和提交量最大的三个进程。九次崩溃**每一次**的前后 3 分钟内都有这样一条：

| 崩溃 | 最近一条诊断 | 整机提交量 / 上限 | 当时占用最多的三个进程 |
|---|---|---|---|
| 10-16 08:47:38 | 后 124 秒 | 87.5 / 87.6 GB | 浏览器 7.2、云桌面客户端 6.1、编译器 5.6 GB |
| 10-16 10:07:17 | 前 50 秒 | 87.3 / 87.6 GB | 编译器 6.8、云桌面客户端 6.2、浏览器 4.3 GB |
| 10-16 11:21:28 | 前 4 秒 | 87.3 / 87.6 GB | 云桌面客户端 6.2、浏览器 4.3、构建工具 3.3 GB |
| 10-16 11:41:44 | 前 59 秒 | 87.3 / 87.6 GB | 云桌面客户端 6.3、浏览器 4.3、编译器 3.0 GB |
| 10-19 12:27:37 | 前 7 秒 | 87.3 / 87.6 GB | **后端 5.8**、IDE 代理进程 3.6、3.6 GB |
| 10-19 12:34:44 | 前 175 秒 | 87.3 / 87.6 GB | IDE 代理进程 3.6、3.6、数据库服务 2.9 GB |
| 10-19 12:41:31 | 前 1 秒 | 87.3 / 87.6 GB | IDE 代理进程 3.9、3.7、2.5 GB |
| 10-19 13:17:54 | 后 63 秒 | 87.3 / 87.6 GB | IDE 代理进程 5.8、5.0、2.6 GB |
| 10-28 12:16:55 | 前 5 秒 | 87.5 / 87.6 GB | 代理进程 4.2、编译器 3.2、后端 2.9 GB |

读法：

- 提交量离上限只剩 0.1–0.3 GB，这时任何进程再申请一两兆都可能被拒绝。
- 前三名加起来只有十几到二十 GB，其余六七十 GB 分散在同一台机器的几百个进程里（并行的编译、多个 IDE 与代理、浏览器）。后端只在 10-19 第一次崩溃时排第一（5.8 GB，范围生成进行中；当天更早的几条诊断里它从 3.6 GB 升到 5.7 GB 之后不再涨），其余几次不在前三名里。
- 这台机器经常这样：187 天里这种诊断有 516 条，分布在 69 天；10-16 一天 28 条，10-19 一天 14 条。

### 4. 数据库服务同一时段同样的死法

10-19 12:42 与 12:54 数据库服务的 stderr 结尾同样是 `memory allocation of 1572864 bytes failed`；10-16 上午它在事件日志里也有两次崩溃，与后端的崩溃相隔几分钟。两个互不相干的程序在同一时刻同样地死，原因在它们共同的环境里。

### 5. 「同一个偏移」是什么

Windows 上进程自己 abort 都是一条 `__fastfail` 指令，退出码一律 `0xC0000409`。出错偏移是这条指令的位置，它只分得出是哪一种 abort。`process_diagnostics` 里有两条手动跑的演示测试，在同一个构建里各弄死几个子进程：`each_way_of_aborting_looks_the_same_from_outside`（四种 abort）和 `a_stack_overflow_does_not_look_like_an_abort`（对照：栈溢出）。本机跑的一次，事件日志里记下的是（偏移的数值每个构建不同）：

| 死法 | 退出码 | 出错模块与偏移 | 崩溃笔记 |
|---|---|---|---|
| `Vec::with_capacity` 分配失败 | `0xC0000409` | 程序自身 `+0x65ad071` | `alloc_failed` |
| 另一处、另一个大小的分配失败 | `0xC0000409` | 程序自身 `+0x65ad071`（**同一个**） | `alloc_failed` |
| 直接 `std::process::abort()` | `0xC0000409` | 程序自身 `+0x287aa75` | 没有 |
| 展开途中再 panic | `0xC0000409` | `ucrtbase.dll+0xa527e` | `abort` |
| 栈溢出（对照） | `0xC00000FD` | 程序自身 `+0x1d59567`（把栈用完的那个函数里） | `stack_overflow` |

所以一个构建里「每次同一个偏移」正是分配失败的样子，与当时在生成哪个根、在分配什么无关。把偏移解到符号，得到的也只是标准库里 abort 的那一条指令，不是出事时在跑的代码。栈溢出是另一回事：退出码就不一样，偏移落在出事的函数里——本票的崩溃不是它。

（顺带：事件日志里 08-09 与 09-06 各有一次模块是 `ucrtbase.dll`、偏移同为 `+0xa527e` 的崩溃，与上表第四行是同一个位置——那是 C 运行库的 `abort()`，另一类问题，不属于本票。）

## 不属于本票的几类

- 调试构建与单测程序的 `0xC0000409`：11-02、11-05、11-06（三次）与 10-27 的六次，前后 5 分钟内同样有「虚拟内存不足」的诊断，是同一个原因；10-22、10-23（四次）、11-08（两次）附近没有这样的诊断，原因没有查。
- 7–8 月事件日志里的 `0xC00000FD` 是栈溢出，出在调试 / 测试构建上，后来几何池和主线程池改用 64 MB 栈缓解的是这一类。它与本票的崩溃异常码不同、机理不同。
- 11-07 的两条崩溃笔记（`alloc_failed`，后端提交量 7.6 GB 与 2.5 GB）前后一分钟内同样有「虚拟内存不足」的诊断。其中 03:21 那一次后端自己占了 7.6 GB、数据库服务 12.3 GB，两者合起来是当时占用最多的——这一次后端自己的占用是成因的一部分。

## 取证时发现的两件事

- **事件日志里没有不等于没崩。** 从 IDE 或代理的终端里起的进程继承了「崩了不上报」的错误模式，崩了系统既不记应用崩溃事件，也不留转储；11-07 的两次就只在崩溃笔记里。要事件和转储，后端得从普通控制台或服务管理器起。
- 留痕上线（11-07）之前的崩溃没有笔记，只能靠 stderr 与系统的诊断对时间；10-16 10:07 那一次连 stderr 都没留下，归到同一个原因靠的是偏移相同（发布包 B）加上同一分钟的诊断。

## 这次补的留痕

- 崩溃笔记（`logs/crash-notes.log`，同时写 stderr）多三格：`sys_commit_free_mb`（整机还能提交多少）、`sys_commit_limit_mb`（整机提交上限）、`sys_phys_free_mb`（空闲物理内存）。原先只有本进程的 `working_set_mb` / `commit_mb`，要判断「是不是被别人挤死的」得另翻系统日志。
- 笔记写满时照样收行（原先写满了没有换行，下一条会接在后面）。
- `scripts/Get-CrashEvidence.ps1`（只读）把上面几样东西按时间对到一起。

## 下次再崩怎么查

1. 在后端所在的机器上跑（PowerShell 7）：

   ```powershell
   pwsh -NoProfile -File scripts\Get-CrashEvidence.ps1 -LogsDir <后端的 logs 目录> -Days 7
   ```

   它列出每一次崩溃的构建、异常码、偏移，同一时刻有没有「虚拟内存不足」的诊断（当时整机提交量与占用最多的进程），`crash-notes.log` 里的笔记，以及那一轮 stderr 的最后两行。

2. 看崩溃笔记那一行：

   | 笔记 | 意思 | 该做什么 |
   |---|---|---|
   | `kind=alloc_failed`，`sys_commit_free_mb` 很小，`commit_mb` 不大 | 整机内存被别的进程用尽，后端被牵连 | 腾内存（停掉并行的编译、关掉不用的程序）或调大页面文件；不是代码问题 |
   | `kind=alloc_failed`，`sys_commit_free_mb` 很小，`commit_mb` 是全机最大的 | 后端自己占得多 | 看 `root=`、`last_stage=` 当时在生成什么；范围生成时 5–6 GB 是见过的水位 |
   | `kind=alloc_failed`，`sys_commit_free_mb` 还很宽裕 | 一次离谱的申请（大小在同一行） | 是算大小的代码有问题，按 `thread=`、`last_stage=` 找 |
   | `kind=stack_overflow` | 栈溢出 | 看 `thread=`；确认 `RUST_MIN_STACK` 与线程池的栈大小 |
   | `kind=abort` | C 运行库的 `abort()`：本机 C/C++ 代码，或 Rust 展开途中再 panic | 看同一时刻 `logs/process-events.jsonl` 里有没有 `"stage":"panic"` |
   | 没有笔记，事件日志里是程序自身的偏移 | 显式 `abort()`，或不能展开的 panic | 同上，看 `"stage":"panic"` |

3. 需要调用栈时：发布脚本按构建号归档了符号文件，启动脚本有打开崩溃转储的开关；转储加符号文件可以还原崩溃线程的栈。对分配失败这一类，栈只说明「最后是谁申请失败的」，不说明内存被谁占着，帮助有限。

## 这台机器上能做的（要人定）

- 验收与长时间的范围生成不要和并行编译放在同一台机器的同一时段；编译已经改成经编译锁一次一个，是同一个方向。
- 调大页面文件可以抬高提交上限（现在是 63 GB 物理内存 + 24 GB 页面文件）。
- 后端在开始一批生成前检查整机余量、不够就不开工——没有做：它拦不住生成中途被别的进程挤占，只是把崩溃换成拒绝。
