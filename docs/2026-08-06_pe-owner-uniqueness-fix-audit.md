## 一句话

## 背景：一条边两个身份

```
DEFINE INDEX unique_pe_owner ON pe_owner FIELDS in, out UNIQUE
```

- 记录 id：`pe_owner:[<owner>, <槽位>]`，槽位是成员在属主成员表里的**序号**；
- 唯一索引键：`(in, out)` = （成员，属主）。

同一条边有两套身份。成员表增删一项，后面所有成员集体换槽 → 同一个 `(in, out)`
以**新 id** 重插 → 撞唯一索引。这就是 7997@95 的直接死因：

```
persist CATA ownership: [staging_7997_3] 暂存执行语句失败:
Database index `unique_pe_owner` already contains [pe:24381_34109, pe:16189_0],
with record `pe_owner:[pe:16189_0, 2]`
```

真库对过：属主 `pe:16189_0`（WORL）名下 15 条边、槽位 0..14 连续无重复，成员
`pe:24381_34109`（SITE `/1RX-ARCHHB`）只有一条边、就在槽位 2。**库里的数据是干净的，
是写法撞了索引，不是数据脏。**

## 确认修对了的部分

### 1. 两刀预删确实堵住了换槽冲突

```rust
DELETE pe_owner:[{op}, {slot}];                        // 槽位被别的成员占了
DELETE pe_owner WHERE in = {cp} AND out = {op};        // 这个成员换了槽位
```

### 2. 跨分块也收敛（这条是复核时特意验的）

`(in, out)` 那刀是按**成员**键的，永远和该成员的新槽位落在同一个分块里。所以
「成员从槽 600 挪到槽 3」和「从槽 3 挪到槽 600」都能过：前者在 chunk 0 里先删掉它
在 600 的旧行再插到 3；后者在 chunk 0 被 id 刀删掉，chunk 1 再插。

分块真正影响的是**崩溃一致性**，不是唯一性。

### 3. 预删走索引，不是扫全表（实测，不是推断）

```
WHERE in = X AND out = Y   EXPLAIN → Iterate Index  unique_pe_owner  operator "="
                           实测耗时 → 0.65 ms
WHERE out = Y              EXPLAIN → Iterate Table
                           实测耗时 → 3.83 s
```

修复用的是前一种形式：778,925 行的表上每刀不到 1 ms，不是性能陷阱。
（`out` 单键那种形式扫全表——本文其它地方的全表统计每次 25~40 秒就是这么来的。
`(in, out)` 索引的前缀是 `in`，所以只给 `out` 用不上它。）

## 仍然开着的四个口子

### P0-1　成员表变短时，旧边没人删

预删只按**新**成员表渲染槽位 `0..n-1`。属主从 15 个成员变成 10 个，槽位 10..14 的
五条边活下来，`<-pe_owner.in` 的子树遍历照样走进去 → 模型树上多挂已经不属于它的
子节点。

**不会抛异常**，所以不会进死信、不会有告警，只会在某天变成「这个属主底下怎么多了
个东西」。比撞索引难查得多。

**真库现状：还没造成损害。** 幽灵边的指纹是「成员存在，但它自己的 `pe.owner` 与边的
`out` 不一致」，全表扫下来 1,852 条，**全部**是 SYST（8191）里 noun=`DB` 的行——那是
MDB → DB 清单的合法多父引用，不是幽灵边。设计库（DESI）一条都没有。

所以这一条是「代码里真实存在、数据上尚未发作」。

### P0-2　成员表里出现重复成员会照样抛

同一批 insert 里两条载荷撞同一个 `(in, out)`，唯一索引照样拒绝，照样进死信。
抛出来本身不算错（宁可响，别静默），但应该在**解析阶段**就带着 refno 报出来，
而不是在落库时以一条索引错误的形式出现——后者读不出是哪个属主的成员表坏了。

### P1　delete 与 insert 不在一个事务里

两次独立的 `execute_model_write` 往返，中间没有事务；成员超过 500 的属主还会被切开。

- 暂存窗口内：两条语句都进 journal、按序重放，崩溃后重放收敛 ✅
- 窗口外直写持久层：崩在中间 → 该属主的边缺一截，**不自愈**，要等下次解析同一个
  元素才补得回来 ❌

### P2　身份模型本身才是根因

边 id 用序号、唯一索引用 `(in, out)`——一条边两个身份，这是「成员表改一下，后面
所有成员的 id 全变」的来源。把 id 改成 `pe_owner:[owner, child]`、序号退化成普通
字段（`ordinal`），这一整类 bug 就不存在了：成员移动只是 `UPDATE ordinal`。

代价要算清楚：778,925 条边的迁移，加上排查所有依赖 id 形状或依赖 id 顺序
（`ORDER BY id` 之类）的地方。不是这次该做的事，但值得记一笔。

## 另外扫到的一件事（未查到底，只是标出来）

45,966 条边指向**不存在**的 `pe` 行，其中 10,292 条连属主那头也不存在。

最可能的解释是 CATA 按需解析的设计使然：它写每个已解析元素的**整块**成员表，却只为
闭包内的元素插 `pe` 行，于是闭包外的成员天然只有边、没有行。**我没有把这一类查到底，
不下断言**——如果它不是设计使然，那就是另一类损害。

## 建议的优先级

| 优先级 | 事项 |
|---|---|
| P0 | 成员表变短的旧边清理：按 owner **整块**删（`DELETE pe_owner WHERE out = <owner>`）再整块重插，或显式删掉 `槽位 >= 新长度` 的边 |
| P0 | 解析阶段加重复成员断言，带上属主 refno 报出来 |
| P1 | 把一个 owner 的删 + 插包进事务；分块按 **owner** 切，别把一个属主切两半 |
| P1 | 顺手确认那 45,966 条悬空边是不是设计使然 |
| P2 | 长期：`pe_owner:[owner, child]` + `ordinal` 字段 |

注意 P0 第一条如果用「整块删再整块重插」，`DELETE ... WHERE out = <owner>` 是扫全表的
形式（实测 3.8 s / 次），属主一多就不能这么写；按「槽位 >= 新长度」逐条按 id 删更稳。
