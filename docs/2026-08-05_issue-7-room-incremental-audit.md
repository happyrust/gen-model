## 2. 这个症状能怎么静默产生

### 2.1 两条重算分支对空间树的依赖方向相反（主嫌）

- 全量重建 `cal_room_refnos`：拿**面板自己**的包围盒在树上捞成员，再排除面板集合。
  面板在不在树上都算得出来。
- 元素分支 `recalc_element_membership`：反过来，在树上按 `noun == "PANE"` 找候选，
  再与在册面板取交集。

于是「启动时的全量重建算得出房间号，而增量元素分支一条边都写不出」在结构上完全成立，
且**全程静默**：任务算成功、队列行删除、日志一行没有，库里只剩那条 DELETE。这与 issue
描述的「删掉边 → 改模型 → 还是没有」逐字吻合。

树里可能没有在册面板的几条来路：库只生成过管路、结构库从未生成；`accel_tree.bin` 来自
那一次生成；`sync_aabb_tree_with_db` 的数量快路径（`tree_count >= stored_count`）放行；
以及 `sync_aabb_tree_with_db` **只在 `run_app` 里调**，直接进 `run_cli` 的入口不做这次
对账。

### 2.2 其余三处静默

- `enqueue_room_recalc` 在 `gen_spatial_tree` 关闭时直接返回 `Ok(())`：不入队、不记录。
  那条路上队列里从此不会有任何 `room_recalc` 行，房间轮每轮早退，泳道空着。
- 元素查不到几何实例、世界包围盒不可用：都按空集收敛（这与全量一致，是对的），但此前
  没有任何日志。而元素任务的入队条件就是「包围盒确实变了」，走到这两条路本身就是信号。

合成夹具上；ADR 自己记着真实项目的对拍卡在「结构库从未生成、`inst_relate WHERE
in.noun = 'PANE'` 为 0」。

## 4. 本轮改动

分两笔：先让故障可见（`b2509914`），再把 §2.1 那个依赖直接拆掉。

**`b2509914`（可观测性）**：元素分支的三处静默出口补上日志；`enqueue_room_recalc` 在
`gen_spatial_tree` 关闭且确实有变更时按进程告警一次；空候选集在树里没有在册面板时改为
上抛、保留任务重试，不再静默清边。

**根治（本轮第二笔）**：不是给那个依赖加门禁，而是把它拆掉。在册面板只有百来块（本项目
124 间房 / 147 块），一次 `query_insts` 就能整轮复用——新增 `PanelIndex`，一轮 drain 加载
一次在册面板的库内几何，元素分支的候选改为在这些**库里的**面板包围盒上做相交筛选。相交
口径与整间分支逐字一致：rstar 的 `locate_in_envelope_intersecting` 与 parry 的
`Aabb::intersects` 同样是闭区间。于是「树里得有 PANE」这个隐含前提整个消失，空候选集由
构造而可信，覆盖率门禁随之取消。代价是候选筛选从 R 树的 O(log n) 变成面板数的线性扫描，
在这个量级上是噪音；顺带省掉了原来每个元素任务各发一次的候选面板 `query_insts`。

**反方向的同一条纪律**：整间分支仍然用树（少量面板 × 大量构件，这是树的正当用途），
但它也是先清后写——树空着时每块面板都算出 0 个成员，一次启动就能把整库房间归属抹平。
`build_room_relations` 因此加了空树拒跑，上抛交给 `lib.rs` 已有的降级告警，启动不受影响。

回退即红的测试：相交口径（含贴面与跨界）、元素分支源码里不许再出现 `GLOBAL_AABB_TREE` /
`load_aabb_tree`、全量重建的空树判定必须排在任何一次重算与写入之前、`gen_spatial_tree`
关闭必须留下痕迹。`cargo test --lib --features http_api` 343 通过 / 0 失败。

## 5. 复现环境上的五步定位清单

第一条就能把问题劈成两半：

1. `SELECT * FROM model_update_pending WHERE action = 'room_recalc_element';`
   有 `room_recalc_element_24383_66460` → 触发端正常，问题在消费端；没有 → 触发端。
2. `GET /health` 的 `gen_spatial_tree` —— 关着的话触发端立即结案。
3. `SELECT count() FROM inst_relate WHERE in.noun = 'PANE' AND aabb != none GROUP ALL;`
   外加 cwd 下 `accel_tree.bin` 与 `accel_tree_{project}.bin` 的大小与时间戳。
4. `SELECT count() FROM room_relate GROUP ALL;` —— 若整库房间边在这次增量后大面积减少，
   就是元素分支在静默清边，而不只是这一个构件没算出来。
5. 任务泳道里最近一条 `room_recalc` 的 detail 与 dead_letters。

§4 那两笔之后，③ 已经不再是成因（元素分支不看空间树了），①②④ 会各自在日志或任务
失败原因里直接说出来。
