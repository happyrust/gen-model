## 0. 结论

**链路结构上是收敛的，未提交改动审读未发现正确性回归，编译通过。**
未提交的四文件改动是一套**元素分支性能优化**（见 §2），语义等价性有两道防线钉住：
两相谓词与单发谓词的逐例对拍测试、元素分支的三条源码断言。吸收封闭性输入的取样时点
从「整间分支跑完后」前移到「轮初」，方向是保守安全的（推导见 §3）。

遗留暴露面没有变化：凹形房盲区（记录在案的口径）、整间分支对空间树「非空但不完整」
无检测、真实项目的 ADR-010 §9 对拍验收仍欠着（§4）。

## 1. 链路现状（触发 → 收敛 → 落盘）

1. **触发**：AABB 变更集是唯一触发源（基线取空间树上旧值，`AabbChange`），按 noun 分流：
   PANE → 整间分支、其余 → 元素分支（`enqueue_room_recalc`）。判定顺序钉死「开关在前」：
   `gen_spatial_tree` 关闭时按进程告警一次并零入队（变更集在该配置下恒为空，顺序反了就
   永远无话可说）。非几何触发（D12：房间改名、PANE 的 OWNER 搬迁）另有入口。
2. **队列**：行 id `{action}_{target}` 不带 dbnum，同目标天然去重；房间任务死信**无条件复活**
   （跨库 sesno 不可比，每次入队都是全新重算理由）；`attempts >= MAX_ATTEMPTS` 进死信隔离。
3. **调度**（`batch_worker`）：常规出口是空闲轮收口（数据积压清空才收房间轮，ADR-011 §8）；
   持续入库时按 `ROOM_ROUND_FLOOR = 600s` 强收一轮；数据阶段失败的轮**不收**（退避）。
   元素侧分页 `ROOM_DRAIN_PAGE_SIZE = 256`，剩货立即唤醒下一轮，防止积压按 30s/页爬。
4. **一轮 drain**（`drain_rooms`）：整间任务先行（无分页上界=面板数）→ 记 `claimed_panels` /
   `claimed_members` → 吸收判定 → 元素任务。失败逐个记录、轮末聚合上抛，单任务失败不
   中断本轮其余任务。
5. **整间分支**（`recalc_panel_membership`）：成员候选从空间树捞（面板自己的盒在树上查交）；
   **空树拒跑**（先清后写下，空树会把整间清空——上抛保留任务）；面板已不在册时清边（这
   与树无关，边本来就该清）；先删该面板全部出边、再整批写回，单事务。
6. **元素分支**（`recalc_element_membership`）：候选面板从**库内** `PanelIndex` 相交筛选（与
   空间树彻底解耦，issue #7 的根治）；两轮判定（八顶点全进/全出短路，跨界才取实际几何点）；
   任一候选面板网格判不了 → 整任务上抛保留重试（防「判不了当不在里面」静默清边）；先删该
   构件全部入边、再写回，单事务。
7. **判定统一**：两条分支共用 `room_predicate` 同一份规则（八顶点计数 → 结论 → 逐点兜底），
   共用边 id `{panel}_{element}`，两边写入都排序渲染保证可重放、可对拍。
8. **落盘**：空间树脏标记后每个空闲轮至多写一次 `accel_tree.bin`，失败保留脏标记重试。

## 2. 未提交改动是什么（性能优化包）

四处改动同属一个主题：**把元素分支「每任务重复劳动」抽成「每轮一次」**。

- **面板网格整轮缓存**：`PanelEntry` 挂 `OnceLock<PanelMeshes>`，同一块面板的 `.mesh`
  反序列化 + 三角化一轮只做一次。此前一页 256 个元素任务挤在同一间房时，同一块墙板
  网格被现做上百遍——这是一轮房间收敛里最大的一笔开销且不产生新信息。惰性构建：
  只有真被候选到的面板才读盘；`mesh_dir` 随索引定下来，缓存随 `PanelIndex` 生命周期
  （一轮）释放。
- **整页归属快照 `ElementRoomHistory`**：轮初一条 `SELECT ... WHERE out IN [整页元素]`
  查回全部现存 `room_relate` 入边，同时服务两个此前各自发查询的读者——归属变化日志
  （旧房间号）与同轮吸收的封闭性检查（旧归属面板）。N+1 消除，且两份可能分叉的读法归一。
  加载失败的处置是**本轮零吸收**（空快照会让「旧边 ⊆ 已重算面板」凭空成立、错吸收留下
  永久陈旧边），日志侧只降级为「旧房间显示成无房间」。
- **两轮判定拆分 + 推迟取点**：新谓词 `membership_by_aabb` 一次给出（结论, 八顶点计数），
  计数直接作 `inside_count` 排序键（此前判定完再重数一遍，同一面板八次 BVH 点包含跑两遍）；
  实际几何点（一次 `query_geom_pts` 库往返）只在确实有跨界候选时才取（此前无条件先取，
  全进/全出的绝大多数构件白付一次查询）；「判不了整块面板」的 bail 提前到取点之前。
- **回退即红**：两相形式与单发谓词逐例对拍（`the_two_phase_form_agrees_...`）；元素分支
  源码断言 ×3（不得碰空间树、不得自建网格、取点必须在待办守卫之后）；快照缺项读空集有
  单测钉住。

## 3. 吸收快照时点前移的等价性

旧实现：封闭性输入（元素的现存归属边）在**整间分支全部跑完之后**查询。
新实现：**轮初**一次快照。差异只在「本轮整间分支自己造成的边变化」是否可见。逐情形推：

| 情形 | 轮初快照给出的旧边 | 对子集判定的影响 |
|---|---|---|
| 整间分支删了 E→P 的旧边（P 本轮跑过） | 仍含 P | P ∈ claimed，子集判定不变 |
| 整间分支新写了 E→P 的边（P 本轮跑过） | 不含 P | 左侧变小，子集只会更容易成立；而该边指向 claimed 面板，吸收后不会遗留 |
| E 的旧边指向本轮**没跑**的面板 Q | 含 Q | Q ∉ claimed → 不吸收 → 元素任务照跑、清掉 Q 边。与旧实现同判 |
| E 无任何旧边 | 空集 | 与旧实现同判（缺项=空集，且有单测） |

结论：新时点在所有情形下与旧时点**同判或更保守**，不会产生「该跑而被吸收」的方向性错误。
变化日志的「旧房间」口径从「任务执行时刻」变为「轮初」，纯日志差异。

## 4. 发现的问题与遗留暴露面

按影响排序，本轮改动引入的**正确性**问题：无。

1. **（小，浪费）`execute_item` 对整间任务也加载 `PanelIndex`**：单任务路径
   （`model_update_pending.rs::execute_item`）对 `RoomRecalcPanel` 同样跑一次
   `load_panel_index`（147 块面板的 `query_insts`），而整间分支根本不消费它——注释只把
   `ElementRoomHistory` 摘出去了，`PanelIndex` 没摘。一行条件可省。
2. **（既有，非回归）同步 IO 在 async 上下文内**：`PanelMeshes::build` 是同步读盘 + 三角化，
   在 tokio worker 上直接执行会阻塞该线程。整间分支 `cal_room_refnos` 同样是既有模式；
   本轮缓存把次数摊薄了几个数量级，单次构建（大面板多网格）仍可能百毫秒级。如后续要动，
   用 `spawn_blocking` 包 `PanelMeshes::build` 即可，非必须。
3. **（既有口径）凹形房盲区**：八顶点全在外 = `Outside`，横穿凹形房间的长管漏归属。
   `room_predicate.rs` 注释已声明「与全量路径逐字一致，改口径须另立决策」。本轮未动。
4. **（既有暴露面）整间分支对空间树是硬依赖**：空树有拒跑门，但「树非空而不完整」（缺某些
   构件条目）检测不了——缺谁谁被挤出该房成员。元素分支已解耦，整间分支的这条依赖是
   结构性的（少量面板 × 大量构件，树是正当用途），只能靠树的对账机制兜底，而
   `sync_aabb_tree_with_db` 目前仍只挂在 `run_app`（上轮审核的后续项，未变）。
5. **（既有欠账）真实项目的 ADR-010 §9 对拍验收仍未做**：五条 live 用例全在合成夹具上，
   前提（结构库先生成一次）仍未满足。

## 6. 与 kv-mem 暂存方案的交点（为后续方案预留的事实）

- 元素分支现在的读依赖全部是**库内现状**：`PanelIndex`（在册面板 inst 行）、
  `ElementRoomHistory`（现存 room_relate 边）、`element_world_points`（pts 查询）、
  构件世界包围盒。若增量批次的写入改道 kv-mem，这些读必须透过「基线 + 批内覆盖」的
  合并视图；而本轮改动恰好把它们收敛成了「一轮一快照」的形态——快照构建点就是未来
  overlay 的接入点，这对暂存方案是**友好**的。
- 房间写入（两条分支）都是「先删后写 + 单事务 + 确定性渲染」，天然幂等，可直接作为
  暂存写回的重放单元。
- 整间分支的成员候选来自进程内空间树（非库），暂存方案里它属于「派生全局态」，需要
  与库内暂存同步一份批内视图（或按 AABB 变更集在批内补丁），这是暂存方案要单独回答的题。
