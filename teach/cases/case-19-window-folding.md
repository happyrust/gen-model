# 案例 19 · 窗口折叠：last-writer-wins，以及它只在哪种窗口有效

<sub>族 F 性能 · 已实施 · 证据层 B（10 个单测 + 真实文件回放对拍）+ C（A/B 实测）</sub>

## 一句话

一个 refno 在窗口里被改 N 次就产生 N 组落库语句，而最后一条已经覆盖了前面所有——
折叠掉中间态让 amssys 冷启动的 persist 阶段从 ~20 s 降到 ~2.6 s，但对设计库**基本等于空转**。

## 背景与动机

本模块的契约是「**只保留最新状态，不写 sessions / element_changes 历史表**」。
既然中间态不会被任何人读到，逐会话回放它们就是纯粹的浪费：一个 refno 被改 N 次，
就产生 N 组 `UPSERT … MERGE` + `UPDATE pe`。

## 实测数据

**窗口规模**（amssys / dbnum 8191 / sesno 1..=169）：

| 指标 | 值 |
|---|---|
| 有变更的会话 | 151 |
| 操作总数 | 5214（Add 2120 / Modified 1626 / Deleted 889 / None 579） |
| 去重 refno | 2171 |
| 平均重复度 | 2.16 次/refno |
| 最热 refno | `24575/1509`，一个窗口内被写 **55 次** |

**persist A/B**（一次性内存实例，非生产库，两轮交替执行）：

| 轮次 | 未折叠 | 折叠后 | 降幅 |
|---|---|---|---|
| 第 1 轮 | 20,524 ms | 2,648 ms | **−87.1%** |
| 第 2 轮 | 19,075 ms | 2,597 ms | −86.4% |

| 形态 | 语句数 | SQL 体积 |
|---|---|---|
| 未折叠 | 4635 | 16.73 MB |
| 折叠后 | 3213 | **1.98 MB** |

关键观察：**收益来自字节数而非语句条数**——SQL 体积降 88%，语句条数只降 30.7%。
在 SYST 库里被反复修改的恰好是**带大列表的重元素**，它们占语句数不到三成、却扛了载荷的八成半。

## 但这个收益不普适

同一个探针扫过全部四个库：

| 库 | 类型 | 窗口 | 落库操作数 | Add | Modified | Deleted | 折叠收益 |
|---|---|---|---:|---:|---:|---:|---|
| 8191 amssys | SYST | 1..=169 | 4635 | 2120 | 1626 | 889 | **−30.7%** |
| 7997 | DESI | 1..=83 | 176,219 | 176,181 | 14 | 24 | −0.0% |
| 7997 | DESI | 69..=83 | 1926 | 1902 | 11 | 13 | −0.3% |
| 7999 | DESI | 1..=41 | 101,125 | 101,102 | 9 | 14 | −0.0% |
| 8000 | DESI | 16..=30 | 5088 | 5063 | 24 | 1 | −0.2% |

设计库的历史几乎全是**元素创建**，平均重复度恒为 1.00 次/refno，最热的 refno 也只被写 4~6 次。
**折叠对它们等于空转**——但也不亏，那趟扫描是 O(n) 的，相对于渲染几十万条语句可忽略。

真正吃到收益的是 amssys：项目结构库里 MDB / DB / TEAM 这类定义会被跨会话反复编辑，
而它们又恰好带大成员列表。（注：设计库的完整窗口在生产中不会自然出现——
`COLD_START_DB_TYPES` 只放行 SYST/DICT/GLB/GLOB，DESI 必须靠人为压水位才会重放到 sesno 1。）

## 三个设计决定

**一 · 只作用在 `persist_latest_main_data` 内部。** `range_eles` 本体不动，
模型计划、反向索引、缓存失效、datacenter 四个下游看到的仍是**原始数据**，爆炸半径最小。

**二 · 按 key 的 last-writer-wins，不是 union。** 这是唯一真正容易写错的地方：

```text
会话 5：删属性 X        会话 9：又加回 X
简单 union ⇒ X 同时出现在 added 和 deleted 里
而 to_modify_surql 把 deleted 放在最后处理 ⇒ 值被静默抹成 NULL
```

`fold_attr_namespace` 用单张 `HashMap<K, LastWrite<V>>` 归并，**天然保证一个 key 只落进
added / modified / deleted 三桶之一**。这一点比未折叠**更安全**：未折叠时若源解析同时给出
同 key 的 added 与 deleted，值就会被抹成 `NULL`；折叠消除了这种可能。

**三 · 合并后的语句放在 run 最后一个操作的位置**，全局语句顺序不变。安全前提是：
生成的语句里每个值都是**字面量**，**没有任何一条语句会读另一条记录**，所以丢掉中间写不可能改变
后续语句看到的东西。`Add` / `Deleted` **不参与合并**，建记录 → 立墓碑的顺序原封不动。

## 等价性怎么验证的

- **10 个单测**覆盖顺序敏感的边界：删后重加、加后再删、跨三个命名空间的 last-writer、
  `Add`/`Deleted` 打断 run、无关 refno 保序、最新子列表胜出。
- `folding_a_real_window_preserves_final_state`：在**真实 E3D 文件**上把原始序列与折叠序列
  **各自回放一遍**，逐 refno 比对末态（2171 个 refno **逐一相同**）。
  回放用的是**独立写的状态机**，不复用 `fold_window` 的 run 检测逻辑——否则就是自己证自己。
  只需文件、不连库。

round2 审核逐条核对折叠依赖的四个前提，全部成立；并额外记录一处
**「成立但依赖一条未被断言的不变量」**：三个命名空间在折叠侧是独立归并的，
而真正落库的观测面是**一个** MERGE 对象（`to_modify_surql` 把普通属性与显式属性写进同一个
`main_fields`，显式循环在后、同名 key 必然覆盖）。也就是说折叠把「后一个会话胜出」换成了
「显式命名空间恒胜」。当前构造不出实际发散（`refine` 保证两侧值恒等），
但建议加一条断言，防 `refine` 变更导致等价性**在两层测试都通过的情况下悄悄失效**。

## 规律

**先量窗口成分，再决定优化。** 折叠在 SYST 冷启动窗口上省 87%，在设计库上省 0.0%——
差别不在实现好坏，而在**窗口里到底是什么**（重复修改 vs 纯新增）。优化前先跑一个只读探针
统计 Add/Modified/Deleted 比例与重复度分布，能避免大量做了等于没做的工作。

**等价性测试不能复用被测逻辑。** 用独立写的状态机回放两遍再比对末态，这条纪律让
「折叠等价」变成了真正的证明；如果回放器复用 `fold_window` 的 run 检测，测试就只是在证明
它自己内部一致。

**「更安全」也要被识别出来。** 折叠顺手消除了 added/deleted 同 key 时值被抹成 NULL 的隐患。
优化改动带来的**行为改善**同样要写进记录，否则下次有人想回退折叠时不会知道自己在放弃什么。
