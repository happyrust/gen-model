ref_rev：回答「谁在用我」的那张索引

正向问题（这个弯头实例用的是哪个目录元件）读一次属性就有答案；反向问题（这个目录元件被哪些实例用着）在 PDMS 数据里根本没有出口。ref_rev 就是为反向问题建的索引。本课用 10 张流程图 走完它的写、查、用、坏了怎么办四条路径，配两个端到端例子，最后拿 core.dll / Core3D.dll 的实测反编译对照原生 back-ref 是怎么做的、又是谁在做。

1. 为什么需要它：正向易、反向难

先把问题摆清楚。设计实例通过 CATR/SPRE/PRTREF 这类属性指向目录元件——这条正向关系就写在元素自己的属性里，读一次就有。但增量更新真正需要的是反向：有人改了目录元件，谁的几何会跟着变？

这就是那段 TODO src/data_interface/model_refresh.rs 里有一大段注释描述这个缺口：「当被多个设计实例引用的共享 CATA 目录/规格元件本身被改动时，这里只会把该 CATA 元素归一到它自己的 CATA owner 重生成，不会反查并重生成所有引用它的设计实例」。ref_rev（ADR-003）就是来补这个洞的。

2. 一条边长什么样（方向陷阱在这）

ref_rev 是 SurrealDB 的图边表：in = 引用方，out = 被引用方，边 id 是两端拼成的复合主键。

最容易看反的地方 名字叫「反向索引」，但表里存的是正向边（实例 → 目录）。「反向」体现在查询方向上。
为什么不干脆把行反过来存？因为这样维护成本最低：清理一个元素的旧引用只需要 DELETE pe:X->ref_rev，沿元素自己的邻接表走，不用扫表、也不用建二级索引。

2.1 哪些属性会进这张索引

门槛只有一个：该属性被 model_impact::classify_attribute_effect_with_meta 判为 DependencyCascade。判定逻辑和「哪些变更要级联」是同一份定义，不会各说各话。

类别例子进索引？
目录 / 规格 / 设计表引用CATR SPRE SPREF PRTREF SPCO SCOM DESP GMREF TMPL …✅ 进
A2 兜底：schema att_type == ELEMENT 的引用属性，名字不在上面清单里项目自定义引用属性✅ 进（自动升级为 DependencyCascade）
结构属性OWNER CHILDREN❌ 不进 —— 层级关系由 owner 图负责
纯几何参数DIAM XLEN HEIG❌ 不进 —— 不是引用
业务元数据 / 位姿NAME DESC / POS ORI❌ 不进

排除 OWNER 是有意为之：把层级也塞进来，这张表就退化成「什么都有」的大杂烩，级联范围会失控。它要保持是一张纯粹的交叉引用表。

3. 流程 A · 写：增量落库时怎么维护

入口在 IncrementPipeline::apply_one 里的 maintain_reverse_index，位置在主数据落库之后、推进水位之前。

渲染出来的语句就是这个样子（build_reverse_index_statements 是纯函数，可单测）：

DELETE pe:ELBO_A->ref_rev;
INSERT RELATION INTO ref_rev [
  { id: ref_rev:[pe:ELBO_A, pe:CAT_ELBOW90], in: pe:ELBO_A, out: pe:CAT_ELBOW90 }
];
按约定非致命 apply_one 把这一步的 Err 吞成 warning。理由写在代码注释里：缺一条边最多漏一次级联，下次触及该元素时会整体重写而自愈；而如果让它阻塞水位，一次目录写失败就会卡死整个 dbnum。

4. 流程 B · 查：传递闭包 BFS

查询发生在 build_model_update_plan 里（落库前，此时索引还是变更前的状态）。它不是查一次就完事，而是逐跳扩张。

常量值为什么存在

5. 流程 C · 用：怎么变成重生成根

闭包只是「谁引用了我」的原料。build_unit_rollup 才把它变成真正要重建的交付单元（BRAN / HANG / SUPPO / EQUI）。注意这里的止步规则——它决定了级联不会无限扩散。

两种命中的区别 同一个交付单元上会分别记 direct（元素自己被改了）和 cascaded（是被引用关系带出来的）。两者都会让 will_generate = true，但计数分开，预览时能看出「这条支管是我自己改的，还是被目录改动波及的」。

7. 例子二：为什么必须多跳

规格表链是典型的间接引用：设计侧并不直接引用表项，中间隔着一层没有交付单元的目录中间体。

TABITE 是什么

Table Item，表项——目录侧「表」机制里的一行数据（TABGRO 表组 → CTABLE/TABLE 一张表 → TABITE 一行）。规格元件不把尺寸写死，而是用 PRTREF 指向表里某一行，展开几何时去读那行的值。

它自己完全不产生几何，这一点从 schema 标志位可以直接看到（noun_flags.json，noun hash 0x4F3C0B8，在 parse.rs 里的全名是 TABITEM）：primitive:false, geomset:false, extrusion:false, is_pointset_point:false, graphics_behaviour:0。所以改一个表项时，「改动位置」上没有任何东西可重建——真正变形的是隔着两层引用的设计管件。

第三个小例子 · 改引用与删元素

把 ELBO_A 的 CATR 从 /ELBOW-90-DN100 改成 /ELBOW-45-DN100：维护流程是「DELETE pe:ELBO_A->ref_rev 清掉全部旧出边，再按后态整体重写」，所以旧边不会残留，以后再改 DN100 弯头不会把 ELBO_A 误拉进来。

ELBO_A 被删除时只执行 DELETE、不再插入，它从此不出现在任何级联结果里。

8. 流程 D · 坏了怎么办

写和读的失败策略是不对称的，理由不同：写失败可以自愈，读失败会导致「静默漏刷」，必须留下痕迹。

索引为空时是 no-op build_unit_rollup 里级联那段在 ref_reversal 为空时行为与 B1 落地前完全一致。所以「先建索引、后接消费」这种分期上线是安全的。

9. 对照 core.dll：back-ref 到底是什么

gen-model 自建 ref_rev，是因为 E3D 原生本来就有这套东西——只是离线拿不到。本节结论全部来自对 core.dll 的实测（IDA 会话 core31-retrace，imagebase 0x5170000）。

9.1 那些 *BREF 确实是真属性，不是文档传说

每个名字在属性名字符串区都有一条字符串，且各自被一个 0xDB 字节的静态初始化器引用——这些初始化器是同一个模板生成的，干的事就是 new DB_Attribute("名字") 再存进一个 ATT_* 全局。

属性名字字符串静态初始化器对应全局
SPBREF0x5D7FA54sub_57675F0（0xDB）ATT_SPBREF @ 0x64203E4
SCBREF0x5D7D604sub_575D4F0（0xDB）同款模板
TABREF0x5D84578sub_577BC50（0xDB）同款模板
GOBREF0x5D82980sub_56CB910（0xDB）同款模板
HDBREF0x5D83A50sub_56D07D0（0xDB）同款模板
DBREF0x5D7EBA4同一字符串区同款模板

sub_57675F0 —— ATT_SPBREF 的静态初始化器

v1 = operator new(0x114u);              // DB_Attribute 对象 276 字节
memset(v1, 0, 0x114u);
sub_581BFE0(v4, "SPBREF");              // 构造 std::string("SPBREF")
v2 = DB_Attribute::DB_Attribute(v4, 1);
ATT_SPBREF = v2;                        // ?ATT_SPBREF@@3QBVDB_Attribute@@B
已确认 · 顺带的一条反证 正向属性 ATT_SPRE 的初始化器 sub_576D8D0 同样是 0xDB 字节的同一模板。所以 back-ref 属性和普通引用属性在「怎么被造出来」这一层毫无区别——它们就是普通属性，差别只在语义和「谁来写」。

9.2 维护挂点：那是个广播器，不是维护者

这一步常被简写成「PostSetRefListAttribute 维护 back-ref」。但反编译出来，它什么都不维护——它是条事件总线：

DB_ElementChangesPlugger::PostSetRefListAttribute @ 0x591E780

char DB_ElementChangesPlugger::PostSetRefListAttribute(
        this, a2 /* DB_Element const& 改动的元素 */,
        DB_Attribute *a3 /* 被写的引用列表属性 */,
        a4 /* vector<DB_Element> const& 新的引用目标 */)
{
  if ( !DB_Attribute::wnoevt(a3) )         // 闸门：属性若配置为「不发事件」，整段跳过
  {
    v6 = *(this + 76);  v5 = *(this + 77); // 订阅者指针数组 [begin, end)
    v8 = (v5 - v6 + 3) >> 2;
    do {
      (**v6)(*v6, a2, a3, a4);             // 虚调用：三件套原样转发给每个 handler
      ++v6;
    } while (--v8);
  }
}
这个签名值得单独看一眼 参数正好是三件套：改动的元素、被写的引用属性、新的引用目标列表——恰好就是维护一张反向索引所需的全部信息。gen-model 的 extract_reverse_ref_edges(op) 拿到的是同样三样东西（referrer、哪些属性算引用、后态目标集），挂点位置也一致：都在「写引用属性」那一刻。这不是巧合，ADR-003 就是照着这个挂点选的。

9.3 订阅者到底是谁（实测：只有两个，而且都不写 SPBREF）

这一节是本课最容易讲错的地方，所以直接把它查穿。先看一个反直觉的事实：SubscribePostSetRefListAttribute 在 core.dll 内部一个调用方都没有——它唯一的 xref 是 0x5E14028，也就是导出表数据项（IDA 标为 Exported entry 12076）。**订阅动作全部来自外部模块。**

对 E3D 安装目录下 621 个顶层 *.dll / *.exe 扫描导入名，命中除 core.dll 自身外只有三个模块：

模块订阅者它拿这条消息干什么
Core3D.dllDESDRA_SCPlugs（单例，Instance @ 0x10409440）维护连接型 back-ref——下面这条链
AfiModeling.dllElementEvents（sub_100C4AB0 @ 0x100C4AB0 一次性 new 出 14 个 handler 子对象并逐个订阅）转发成应用层事件 + 合法性校验，不写 back-ref
Aveva.Core.Database.Implementation.dll未分析（混合模式 C++/CLI）推测是 .NET 事件桥
和 gen-model 撞了同一条纪律 BAKREF 在写新边之前会**先调一次 BREAKF** 把旧的清掉，然后才建立新的反向引用。这正是 maintain_reverse_index 的「先整体 DELETE 出边、再按后态整体重写」——两边独立走到同一个结论，因为要解决的都是「改过引用后旧边不能残留」这个问题。

配对关系是查表来的：desdblib/LOOKUP，646 行

BAKREF 靠 sub_10382A60（trace 串 desdblib/LOOKUP）回答「A 型元素用属性 X 指向 B 型元素时，B 那边应该写哪个属性」。它线性扫描一张静态表 dword_10DA5EA0，646 行 × 4 列（列间距 646 个 dword，共 10 336 字节）：col0 == noun_a && (col1 == noun_b || noun_b == 0) && col2 == attr ⇒ 产出 col3。

整张表已经解码落盘在 .ida_scratch/out_conn_pairing_table.md。它的形状是：

col0 / col1 = noun 对 92 / 95 个不同值 BRAN NOZZ ELBO TEE FLAN REDU OLET GENSEC HANG AHU DAMP FILT … col2 / col3 = 属性对 只有 11 个不同值 CREF HREF TREF CRFA JOIS JOIE PFRE CFRA LNFA HPREF TPREF 表是对称的：既有 TREF → CRFA，也有 CRFA → TREF 例： BRAN | TEE | HREF | CREF BRAN 的 HREF 指向 TEE ⇒ 配对属性是 TEE 的 CREF BRAN | BRAN | TREF | HREF 两条支管首尾相接 LOAP | FITT | CREF | CREF 两侧同名
这里要更正一个说法 所以这条链维护的是**连接型 back-ref**（管道 / 暖通的首尾与连接关系），不是 9.1 那六个 SPBREF/SCBREF/TABREF/GOBREF/HDBREF/DBREF。目录 / 规格那一族 back-ref 究竟由谁写，本次没有找到——不在这两个订阅者里，很可能压根不走 plugger，而是由 dabacon 内核在写引用属性时自己维护。这与 ADR-003 早就写下的判断（「PDMS 里 back-ref 是独立引用表 / 系统维护结构」）是一致的。
对 gen-model 的直接意义 E3D 认定为双向连接的这 11 个属性里，DEPENDENCY_CASCADE_ATTR_NAMES 只显式列了 CREF/HREF/TREF。另外 8 个（CRFA JOIS JOIE PFRE CFRA LNFA HPREF TPREF）不在任何静态清单里、也不被 attribute_affects_model 命中，于是落到 Unknown，再被 A2 兜底（schema att_type == ELEMENT）升级成 DependencyCascade。
结论：ref_rev 的成员资格没有缺口，但这 8 个是靠兜底进来的而不是靠 curated 清单——这也算 A2 那条规则第一次被逆向正面验证。另外它们全都在离线 all_attr_info.json 里，和 SPBREF 家族的「离线零命中」正好形成对照：连接型 back-ref 离线读得到，目录型读不到。

9.4 wnoevt：要不要广播，字典说了算

DB_Attribute::wnoevt @ 0x58D5290

bool DB_Attribute::wnoevt(DB_Attribute *this){
  if ( !*((BYTE*)this + 8) )              // 还没从字典加载过？
    (*(*(DWORD*)this + 20))(this);        // 走 vtable 槽 +20 懒加载 schema
  return *((BYTE*)this + 184);            // 返回 this+0xB8 的布尔字段
}

「want no event」＝这个属性被写时要不要广播变更事件。注意它和课 01 的 DB_Noun::graphicsBehaviour 是同一个套路：先看 this+8 加载过没有，没有就走 vtable 懒加载，然后返回一个固定偏移的 schema 字段。也就是说「哪些属性是静默的」同样由字典数据驱动，不是二进制里写死的。

推断 · 未验证 很自然会猜：back-ref 属性自己的 wnoevt 应当为 true，否则 handler 写 SPBREF 又会触发一轮 PostSetRefListAttribute，无限递归。但这个值存在字典里而不在二进制里，静态分析读不到——要在活的 E3D 会话里查该属性的 schema 才能证实。所以目前只是推断。

9.5 名字怎么拆（提示，不是结论）

按前缀看：SP+BREF ＝ spec 反向引用、SC+BREF ＝ spec component / SCOM 反向引用、GO/HD+BREF 同理；TABREF 则少了那个 B。字面拆分并不唯一，语义要以字典定义为准。

顺手解决了一个长期麻烦：名字 ↔ hash

逆向里遇到的全是裸 hash（DB_Attribute::hashValue / DB_Noun::hashValue 的返回值），过去只能靠在字典 JSON 里搜数字。这次从本仓 all_attr_info.json 的 701 个 (name, hash) 对把函数拟合出来了——先用「只差一个字符的名字对」求每个位置的权重（恒为 27^i，首字符权重最低），再按名字长度解常数项：

hash(name) = 27^4 + Σ(i = 0 .. n-1) val(c_i) · 27^i        val('A')=1 … val('Z')=26

在 701 个属性名上 100% 命中（长度 2/3/4/5/6 全对），对 noun 同样成立：TABITE ⇒ 83 083 448，与 noun_flags.json 一致。意味着 gen-model 不需要字典就能算任意 noun / 属性的 hash，也能把逆向里的裸 hash 立刻反解成名字——上面 646 行配对表里有 8 个字典查不到的 noun，就是这么解出来的。脚本：.ida_scratch/attr_hash_solve.py。
