批量模型生成：一条 ADD 如何变成上万个段

本课回答一个你问了很久的问题：AVEVA 到底怎么"批量"生成模型？ 结论会让你意外——批量循环不在 core.dll。core.dll 是"图形/几何供应商"，真正的批量遍历在 Core3D.dll。全部结论配地址反编译导入导出表证据。

预计 20–25 分钟 · 会话：core31-retrace(core.dll) + core3d-retrace(Core3D.dll) · 工具：ida-pro-mcp

1. 先证伪：批量循环不在 core.dll

直觉上"core.dll 是内核，模型生成当然在它里面"。但四条硬证据一起否定了这点。

1.1 core.dll 里只有一个函数会建 SGL 段

FZ3SGL @ 0x5297141（fm3dcanv）

把 core.dll 对 sgl5NET 全部 32 个导入做反向 xref，只有 35 个函数调用图形引擎，而其中唯一调用建段 API（GLSVCR / GLVSEG / GLSVBO / GLSVSA / GLSVSE / GLVCRE）的就是 FZ3SGL：

GLVCRE(&v8, &v10);                        // 建 1 个视图
HPUTI1(a2, &unk_5D32024, &v8);
if (*a4 && *a5) GLVSIZ(&v8, a4, a5);
v11 = 140; v12 = 140; v13 = 1; v14 = 1;
GLSVCR(&v8, &v11, &v12, &v13, &v14);      // 建 1 组固定的段（常量 140/140/1/1）
...
GLSVSE(&v8, varC); GLSVSA(...); GLSVBO(&v8);

参数是写死的常量——它建的是"画布容器"，不是"每个元素一个段"。core.dll 里根本没有"遍历元素建段"的代码。

1.2 绘图 opcode 全部只被导出表引用

core.dll 有一套 GINO 风格的图形抽象层（下一节详述）。但对 GSTDRG(Start drawing)、GFIDRG(Finish drawing)、GOPSGI、GMASTE、CPTSGL、以及整个 MBX* 包围盒族做 xref，结果唯一引用都是 0x5e14028——导出目录。

confirmed 没有任何 core.dll 内部代码调用它们 ⇒ 它们是给别的 DLL 用的 API。

1.3 谁在用？Core3D.dll

DLL从 core 导入从 sgl5NET 导入从 libgm 导入
core.dll（自身）—32（只有视图/段管理 + GLUPDA）0
Core3D.dll4859113（含 SGL_define_primitive_d）124（gm_Create*）

数量差本身就是答案：Core3D 才是那个"每个元素都要画一遍"的模块。

2. core.dll 提供的四件"批量原料"

core.dll 的角色是供应商：它把批量生成需要的四类零件都导出，自己不跑循环。

2.1 GINO 风格图形抽象层：141 个 opcode

名字表 0x60f9f00 · 描述表 0x60fd650 起步长 0x190 · 下标→名字 helper sub_54D4308

// sub_54D4308：把 opcode 下标翻成 6 字符名字
for_cpystr(a1, a2, a2>>31, &aGopenGdfpicgst[6 * *a3 - 6], 6, 0, 0);

表里 141 项，从 GOPEN 到 GQUNWV。并排还有一张 40 字符定长的人读描述表。挑几个关键的：

opcode描述（来自二进制里的描述表）意义
GSTDRG 0x561e1a6Start drawing一次批量绘制的开括号
GFIDRG 0x561ecbdFinish drawing闭括号
GDFSEG 0x54bd158Define segment定义段
GDFPGP 0x54be5cbDefine primitive-group定义图元组
GSTSGD/GQUSGDSet/Query segment user-data as Splash element段↔元素身份绑定
GQUITV / GTHITVQuery / Highlight Item in View拾取与高亮
GRGPICRegenerate picture重生成
记住这一对 GSTDRG … GFIDRG＝"开始画/结束画"。**批量**在 AVEVA 的语义里就是：这对括号之间塞进去 N 个元素，最后一次性 GLUPDA 刷屏。

2.2 boxlib：逐图元包围盒（第一张真正的"按图元类型分派表"）

0x55f9c24 – 0x55fe2af，全部导出

MBXBOX 0x55face8  盒     MBXCIR 0x55fb004  圆     MBXDSH 0x55fb1f8  碟(dish)
MBXPOI 0x55fb7b4  点     MBXPYR 0x55fbab4  棱锥   MBXSAN 0x55fc01c  ?
MBXSLC 0x55fc5d4  斜切柱 MBXSNO 0x55fca18  锥筒   MBXSPH 0x55fcc40  球
MBXSRE 0x55fcd3c  回转体 MBXTOR 0x55fd2d8  环     MBXARC/MBXELL/MBXSEC …
MBXADD 0x55fab78  合并盒  UNVBOX/EXPBOX/LINBOX/LINVOL/LTHVOL  体积与限界

注意这一族只算盒不算几何——比建实体便宜好几个量级。批量流程会先用它做体积/限界过滤。

2.3 cpslib：CPS 图片存储

CMPTUD @ 0x5595aec

GQUSGD(&v7, v6);                       // 读段上的 user-data
HPUTI1(v6, &unk_5DAB0E8, a3);          // 改一个字段
HPUTIA(v6, &unk_5DAB0EC, a2, ...);
GSTSGD(&v7, v6);                       // 写回

整套 CM*（CMINIT/CMHEAD/CMGTPF/CMPTGP/CMDLGP/CMGTUD/CMQSGU…）是图片(picture)持久化层，"Delete picture (cps)" 就在 opcode 描述表里。

2.4 nounlib：分类谓词族

IFCOMP / IPCOMP / IHCOMP / IECOMP / INCOMP / INGCOM / IGMCOM / IG2COM / IASLCO / ICABCO / IPFCOM / LPRMTV / MEMTES。这些是课 01 讲的"数据驱动类型判定"的调用面：Core3D 的每一层分派都在调它们。

Core3D.dll 里大部分函数没有符号，但每个 FORTRAN 例程入口都有 MTRENT("模块/例程", …) 的 traceback 字符串。把这些串反向 xref 就能还原全部名字。下面是还原出来的批量主链：

confirmed 每一格的地址都由 traceback 串反查得到，调用边由 xref 与反编译核对。SGHDRW 的调用者只有 SGDRAW；SGDRAW 的调用者只有 ELMODL；ELMODL 的调用者只有 MODCMP；MODCMP 的调用者含 SEGCRE 与 SEGREP。

3.1 遍历方式：游标，不是列表

build/NXTITM @ 0x102547f5

if (*a2) { if (*a2 == -1) { v3 = 0; goto END; } }   // -1 = 遍历结束
else {
  *a2 = sub_10402210(a1);                            // 首次：取第一个成员
  if (!*a2) { v3 = 0; goto END; }
}
if (sub_10402220(a2, v4)) v3 = sub_10402250(a2);     // 推进游标
else v3 = 0;

典型的 first / next / sentinel 游标。配合 ELMODL 里的 DSAVE/DRESTO（保存/恢复 DB 当前指针）做子树深度遍历——全程不物化元素数组，所以 ADD 一个几万元素的 ZONE 不会先吃掉一大块内存。

4. 批量的关键：几何之前的两级闸门

批量要快，靠的不是几何算得快，而是大多数元素根本没走到几何。流水线里有两道闸门，都在建实体之前。

4.1 第一道：DRAWOP —— 表示法 + 层级

build/DRAWOP @ 0x10254579

v7 = IFCOMP(a2);  v8 = IPFCOM(a2);
if (IASLCO(a2) | v7 | v8)   v9 = dword_10EB4000;   // 按 noun 类选一个"表示法标志字"
else if (*a2 == 3426330)    v9 = dword_10EB4008;
else if (ICABCO(a2))        v9 = dword_10EB400C;
else if (*a2 == 710633)     v9 = dword_10EB4010;
else                        v9 = dword_10EB4004;

sub_1025BC2E(&v10, _6C);                     // = build/LEVGET 取绘图 level
if (v9 & 2) v13 = -1; else v13 = 0;  ...     // bit 1/2/4/8 = 各表示法开关

先用 noun 分类谓词选表示法标志字，再用 LEVGET 取绘图层级，最后按 bit 展开成一组布尔开关（对应 PDMS 里 obstruction / insulation / centreline 之类）。这一步只读属性，不碰几何。

4.2 第二道：GMDRAW —— 两级早退

build/GMDRAW @ 0x10254b01

if (*a4 != 621502 && *a4 != 621505 && *a4 != 312510241
                  && *a4 != 312510247 && *a4 != 312510290) {   // ① 5 个 noun 码直接跳过
  if (*a5 & 1 | ((sub_10510680(...) & 1) == 0)) {
    if (sub_10402560(a2, ...) == 1) {                            // ② 是不是 3D 可画
      v8 = GMCFST(a2);                                           //    取缓存首项
      sub_10527500(&v9, ..., a5, &v7);                           //    才真的画
      ...
    } else if (dword_10E98634[0] > 1) {
      MTRINT("GMDRAW: Skipping non-3d:", 24, a2, ...);            //    否则打点跳过
    }
  }
}
confirmed 那条 "GMDRAW: Skipping non-3d:" 字符串是硬证据：AVEVA 自己就是把"非 3D 元素"在几何之前扔掉的，而且留了 trace 级别开关（dword_10E98634[0] > 1）。

5. 批量的加速：缓存 + 登记表

5.1 cachegml：几何缓存

GTGEOM(0x10341d2e, 2106 B) 是核心，周边 GTCLEL / GTCLRF / GTCLSH / GTTUBG / GTCSPA / MBXGML，还有两个"意向位" BXWANT(要盒吗) / SLWANT(要实体吗)。GTGEOM 的调用面全是分类谓词 + CGTCT2/CSTCT2(目录读取) + GATINS：

inferred 缓存键在目录几何层（catalogue / GMSET），不是设计元素层。理由：GTGEOM 的入参路径走 CGTCT2/CSTCT2 目录读取而非设计元素属性，且 MODCMP 也调 CGTCT2。这解释了批量的主要加速来源——同型号构件复用同一份几何。尚未逐块反编译确认键的构成。

5.2 maplib：元素 ↔ 段 登记表

41 个例程：MAPINS(0x1038f5e4 插入) MAPGET MAPELE MAPREM MAPBOX MAPKEY/MAPKY2/MAPKY3 QVOLDS/SVOLPR(体积过滤) 以及一族 MU* 更新例程。

这张表是增量更新的前提：有了它，css/SEGREP(0x102334d0) 才能"只替换一个元素的段"——它同样调 MODCMP，等于对单个元素重跑一遍流水线尾段。

5.3 change：变化 → 图形

change/EVALST 0x1022e0a7   变化求值（兄弟 EVALAT EVALCD EVALNW EVALRF）
change/UPCACE / UPCACP     缓存失效
change/UPGRPH 0x1022eaee   图形更新（3959 B）
change/UPDATD 0x1022e5ac   / UPDATN / UPDATP

这与课 02 的 core.dll 侧（DB_ElementChangesPlugger → invalidate(attr)）是两层：core.dll 失效数据缓存，Core3D 失效图形缓存并重建段。

7. 修正三条旧结论

correction 1 课 01 第 5 条说"sgl5NET 只暴露视图/段管理 + GLUPDA，无逐三角 API"——这只对 core.dll 的 IAT 成立（32 个）。Core3D.dll 导入 113 个，含 SGL_define_primitive_d / SGL_import_external_geometry。而实体建模其实在第三个库 libgm。
correction 2 课 02 第 4 条说"真正的 3D 逐-noun 几何派发…待定位"——已定位：Core3D.dll build/MODCMP + build/SGDRAW + build/GMDRAW。判据是 core.dll nounlib 的 I*COMP 谓词族，不是 graphicsBehaviour 上的一个大 switch。
correction 3 速查表把 sub_5621F20 记为"图形 metafile 令牌解析器（引用 FACET 字典）"——不准确。它是 metafile/plotfile 的设备选项命令解析器（CHKEYW 关键字表 FRAME/TOKEN/ZCOORD/EUC/SHIFTJIS/APPEND/SCALE/SPLASH/FACET/UTF8…），FACET 在这里是"输出要不要含 facet"的开关，不是几何令牌流。
顺带：fm3dcanv/F3BDAD(sub_5297CCF) 不是 drawlist add，是 3D 画布边框的方位/仰角标尺（UIALBL 造 label、UIASLD 造 slider）。

8. 落到 gen-model：五条可直接抄的做法

  1. 把批量边界定在"子树"。AVEVA 一条 ADD SITE/ZONE 就是一个批；遍历用 DB 指针栈(DSAVE/DRESTO) + 游标(NXTITM)，不物化元素列表。我们的 pipeline 若先收集 Vec<Element> 再处理，在大 ZONE 上内存会吃亏。
  2. 闸门必须前移到几何之前。对齐 DRAWOP(类 + level) → GMDRAW(noun 早退 + 非 3D 早退)。现在我们容易"先建网格再按 LEVEL/CLFLA/TUFLA 丢弃"，那是纯浪费。
  3. 缓存键放在目录几何层，不是设计元素层。同型号构件复用一份几何是批量的主加速点（对应 cachegml/GTGEOM）。
  4. 建一张 元素 ↔ 产出 的登记表（对应 maplib）。ADR-003 的反向索引是"输入侧"，这里需要的是"产出侧"索引——没有它就做不到 SEGREP 式的"只换一个单元"。
  5. 包围盒走独立的便宜通道。boxlib MBX* / dbboxlib 先算盒做体积过滤，再用 BXWANT/SLWANT 决定要不要实体。适合我们的"交付单元"级裁剪。

9. 还没验证的部分（不要当成已完成）

  • ELMODL(7675 B) 只读了调用面，未逐块反编译其子树遍历与 level 分支。
  • GMDRAW 里跳过的 5 个 noun 码（621502 / 621505 / 312510241 / 312510247 / 312510290）未解码成类型名。
  • MODCMP 在多种"建模方式"间如何选（sub_102586DB / sub_1025B8B3 / sub_1038158C / sub_10651840）未展开。
  • libgm 的 gm_Create* 与 PDMS 目录图元(SCYL/SBOX/SSNO…)的精确对应表未逐一核对，目前是按名字对应的强推断。
  • CPS(cpslib) 明显服务 DRAFT/2D 出图，是否也缓存 3D 段未查。
  • 另一条批量入口 dra_model/GENMOD(0x100df724) → updview/DESUPV(0x101b7b7a) → UVIEW(0x101b2254, 12.7 KB) 是 DRAFT 出图路径，本课只确认它同样汇入 MODCMP/ELMODL，细节未展开。
