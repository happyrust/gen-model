DB_Noun：类型判定的答案
到底从哪来

1. 它是类型描述符，不是元素

先把名字对上。AVEVA 官方文档在列属性类型时，写的是一个你可能扫过去没在意的词：

官方口径 属性类型清单里有一项叫 ElementType (or Noun)。 —— Database Attributes, AVEVA E3D Design

所以 DB_Noun 不是 AVEVA 程序员随口起的名字，Noun 就是 AVEVA 对"元素类型"这一概念的正式称呼。EQUI、PIPE、ELBO 各对应一个 DB_Noun 对象，全进程共享。你数据库里一万个设备，共用同一个 DB_Noun。

DB_Element（元素实例，成千上万个） DB_Noun（类型描述符，每类型一个） ┌────────────────┐ type() ┌──────────────────────────────┐ │ /VESSEL-1 │ ─────────────► │ hashValue = <EQUI 的 hash> │ │ /VESSEL-2 │ ─────────────► │ 是不是图元？怎么画？能不能改？ │ │ /VESSEL-3 │ ─────────────► │ │ └────────────────┘ └───────────────┬──────────────┘ │ 用 (hash, 字段号) 去问 ▼ dabacon 数据字典（外部文件）

这解释了一个容易踩的坑：DB_Noun 上挂着 psOwner / psNext / psFirstMember，看着像树遍历，但它们描述的是 类型之间的 schema 层级（WORL 底下能挂 SITE、SITE 底下能挂 ZONE），不是你项目里某个具体设备的父子关系。官方文档说的正是这件事：

官方口径 "The allowed hierarchy is defined in a Database Schema. The database schema is the 'meta data'… Database Schemas cannot be modified by users." —— Hierarchical Data Model, AVEVA E3D Design

2. 一眼判断：三条取值路径

这是本课的核心技能。DB_Noun 的每个谓词，答案只可能来自三个地方之一。反编译出来一眼就能分：

路径 A：字典现查（每次都问）

BOOL DB_Noun::internalGetField(DB_Noun *this, int fieldId, bool *out)
{
  v4 = *((_DWORD *)this + 28);          // 0x70 = baseType 指针
  v8 = *(_DWORD *)(v4 + 116);          // baseType->hashValue (0x74) = 字典主键
  sub_1084F1A5(&v8, &fieldId, &a2, &v6);  // FORTRAN dabacon 查
  *out = a2 & 1;
  return v6 == 0;
}

0x10457890 · primitive / geomset / extrusion 走这条

注意主键怎么取的：不是直接读自己的 hashValue，而是先取 0x70 的 baseType 指针，再读它的 hashValue。对普通类型 baseType == this，绕一圈等于没绕；对 UDET（用户自定义类型）就分叉了——顺手也就解释了 isUDET 为什么长这样：

BOOL DB_Noun::isUDET(DB_Noun *this) { return *((_DWORD *)this + 28) != (_DWORD)this; }
//                                          baseType 不指向自己 ⇒ 是用户自定义类型

路径 B：读 ReadData 灌好的缓存

int DB_Noun::psOwner(DB_Noun *this) {
  if ( !*((_BYTE *)this + 120) )   // 0x78 dataLoaded == 0？
    DB_Noun::ReadData(this);      // 首访：一次把 ~20 个字段全灌进来
  return *((_DWORD *)this + 38);     // 0x98，之后都读这里
}

特征：函数体里有 if(!flag) ReadData() 前缀

路径 C：结构自身，不查字典

int DB_Noun::hashValue(DB_Noun *this) { return *((_DWORD *)this + 29); }  // 0x74，构造时写入

特征：光秃秃一行 return，4–9 字节的函数

练一下 graphicsBehaviour（画法）是哪条路径？
反编译是 if(!*(this+120)) ReadData(); return *((_DWORD*)this+56); → 路径 B，缓存在 0xE0，由 ReadData 用字段号 5099119 灌入。

3. 两条互不触发的懒加载链

路径 B 其实有两条，各有各的标志位和加载函数，互不触发。这点记录 0003 没覆盖：

链标志位加载函数谁在用
主链0x78 dataLoadedReadData() 0x10457D00层级指针、画法、权限位…约 20 个
DAB 链0x79 dabLoadedReadDataDab() 0x10454F50目前只见 primaryList
 
bool DB_Noun::primaryList(DB_Noun *this) {
  if ( !*((_BYTE *)this + 121) )   // 0x79，不是 0x78
    DB_Noun::ReadDataDab(this);   // 也不是 ReadData
  return *((_BYTE *)this + 164);     // 0xA4
}
为什么值得记 如果你在写"模拟 core.dll 行为"的代码，调 ReadData() 不会让 primaryList 变得可用，反过来也一样。两条链要分别处理。

4. 一个会让你全盘搞反的陷阱

BOOL DB_Noun::isValid(DB_Noun *this) { return *((_DWORD *)this + 29) == 0; }

this+29 就是 hashValue。也就是说——isValid() 在 hashValue 等于 0 的时候返回真。

按字面意思"有效则真"去用，判断会整个反掉。语义上它更接近 isNull()／"这个类型没解析出来"。旁证在 ReadData() 里——正是 hashValue == 0 这一支走向 "Unknown Element Type"：

v11 = *((_DWORD *)this + 80);
if ( !v11 )
  sub_10004A90("Unknown Element Type", 0x14u);
else if ( DB_Udtg::findUdtg(v11, &v13) )   // 兜底：查用户自定义类型字典
  ...DB_Udtg::description(v16)...

5. 版本漂移：偏移会变，字段号不变

这是本课最有实践价值的一条，而且是拿两个版本对撞才撞出来的。

把本课（2.1）和记录 0003（3.1）放一起，同一个语义字段的偏移全都对不上：

字段E3D 2.1E3D 3.1差
hashValue0x740x5C24
dataLoaded0x780x6024
visible20816444
graphicsBehaviour224 0xE0180 0xB444
modifiable26621452
（字段 13953605）30825256

差值是 24 → 44 → 52 → 56，不是常数。说明两版之间有多处增删字段，你没法靠"整体平移 N 字节"把一版的偏移换算到另一版。

但是 dabacon 字段号两版完全一致。 5099119 在 2.1 和 3.1 里都是 graphicsBehaviour， 621476 都是 modifiable，722704 都是 visible。 变的是"放在结构体第几个字节"，没变的是"在字典里叫几号"。

结论很硬：字段号是可移植的资产，偏移量是一次性的。 完整对照表见 速查表第 5 节。

6. 落到 gen-model

  • 别把偏移写进代码。 你要复刻的是"按字段号问元数据"这个机制，不是某一版的内存布局。all_attr_info.json 这类元数据快照就是对的方向——它存的是语义映射，不是字节位置。
  • 类型判定要数据驱动。 core.dll 自己都不硬编码"EQUI 是不是图元"，而是拿 (hash, 659518) 去问字典。gen-model 硬编码类型表就等于把 AVEVA 刻意做成数据的东西又焊回代码里。
  • 两级缓存的取舍可以照抄。 "首访批量灌、后续读缓存"正是解析器按 schema 一次解码元素隐含块的思路。但注意 AVEVA 分了两条独立链——说明加载代价不同的字段应该分组，不必一次全读。
  • UDET 要单独一条路。 baseType != this 就走用户自定义类型分支（DB_Udtg::findUdtg）。增量里把 UDA 属性按未知保守处理，和这个设计是一致的。
