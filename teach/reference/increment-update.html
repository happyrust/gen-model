0 · 为什么增量比全量难

全量生成只需要回答一个问题：这个元素长什么样。增量生成要回答四个，而且每一个都能独立地错：

1. 什么变了

PDMS 文件给的是会话流水，不是「当前状态」。同一个元素在一个窗口里可能被改 55 次， 其中大多数是中间态。而「OWNER 改了」在数据上表现为两个 owner 各自的成员列表变化，不是一条属性修改。

2. 谁受影响

改一个共享目录元件，可能有 72 个管件在用它。这个「谁在用我」的问题， PDMS 离线数据根本没有出口——必须自建反向索引（案例 05）。

3. 从哪重生成

改一根 SPINE 不能只重生成 SPINE——几何是在 SUPPO 这个层级成形的。 必须沿 owner 链上溯到最小交付单元，而且主路径、兜底、补偿三条路必须算出同一个答案 （案例 04）。

4. 失败了怎么办

数据落了库、模型没生成，进程挂了——重来一次会不会重复、会不会丢、会不会永远卡住？ 这决定了水位、事务边界与幂等性的全部设计（案例 11）。

贯穿全文的一条判据 增量缺陷的典型表现是「流程走完了、没报错、结果是空的或旧的」。所以本文每个阶段都标注了 「错了会看到什么」——排查时倒着用这张表，比顺着读代码快。

2 · 阶段详解

① 发现：文件身份守卫

watcher 每 30 s 轮询监控目录。它要回答的不只是「文件变了吗」，还有「这还是同一个文件吗」： 同一个 dbnum 出现两份文件（Duplicate）、被换成更旧的备份（Rollback）、 被搬到新路径（PathMigrated）、消失（Missing）。

这四类判定原本只挂在手动路径上，自动 watcher 一概不做——直到 F6 把 check_file_against_state 接进自动路径（案例 15）。 关键约束来自 ADR-001：

ADR-001 不变量 文件观察字段（file_name/file_path/file_size/file_modified_at/file_latest_sesno） 必须通过独立写入更新，该写入失败不能修改或间接影响 applied_sesno。
换句话说：「我看到了一个新文件」永远不等于「我已经处理完它了」。

② 窗口：水位决定做多少活

窗口是 (applied_sesno, file_latest_sesno]。这里有一条容易被忽略的设计后果： 事件只是「去看一眼」的触发器，真正的工作量由水位决定。所以事件通道容量为 1、 串行处理不会丢工作，最多是延迟（案例 15 · T903）。

冷启动时 COLD_START_DB_TYPES 只放行 SYST/DICT/GLB/GLOB； 设计库不会自然出现「从 sesno 1 重放」的窗口——这一点在读性能数据时很重要 （案例 19）。

③ 解析：净变化与六个变化桶

collect_changes 把会话流水折成净变化。变化桶沿用 DB_UserChanges 的布局：

变化桶含义模型侧后果
Created元素新建生成该元素所属交付单元
Deleted元素删除（软删墓碑，带 deleted = true）删除清理 + 重生成旧 owner 侧
MovedOWNER 变更 = 搬迁旧根与新根两端都要重生成
MemberChanged成员列表变化搬迁在数据上的真实形态：旧 owner 与新 owner 各一条
Reordered成员次序变化影响装配次序的类型需要重生成
Modified属性修改看属性效果分类（阶段 ⑤）
最容易写错的一条 OWNER 不是普通属性。把它当属性处理，只会刷新新 owner 一侧， 旧位置的几何原样留在三维里。ADR-009 把这条钉死：搬迁 ⇒ 两条 MemberChanged（旧 owner + 新 owner）。 详见 案例 01。

解析层的缺陷会伪装成业务缺陷。CURD/DBLS 这类跨记录块存储的长引用列表， 一旦收集逻辑遇到不认识的块就 break，整条属性丢失 ⇒ 用户看到的是「模型树是空的」 （案例 18）。凡是「整类东西都没有」的故障，先往上游查一层。

④ 落库：折叠 + 分块 + 幂等

本模块的契约是只保留最新状态，不写历史表。既然中间态没人读，逐会话回放就是浪费—— fold_window 按 key 做 last-writer-wins 折叠。amssys 冷启动窗口 SQL 体积降 88%、 persist 从 ~20 s 降到 ~2.6 s；但设计库几乎全是新建，收益 −0.0% （案例 19）。

【折叠 · last-writer-wins，不是 union】 会话 5：删属性 X 会话 9：又加回 X ───────────────────────────────────────────── 简单 union ⇒ X 同时出现在 added 和 deleted 里 to_modify_surql 把 deleted 放最后 ⇒ 值被静默抹成 NULL ✗ 单张 HashMap ⇒ 一个 key 只落进 added / modified / deleted 三桶之一 ✓ （比未折叠更安全：消除了原本就存在的抹 NULL 隐患） 安全前提（实测坐实，不是推断）： · 生成的语句里每个值都是字面量，没有任何一条语句会读另一条记录 · Add / Deleted 不参与合并 ⇒ 建记录 → 立墓碑的顺序原封不动 · 合并后的语句放在 run 最后一个操作的位置 ⇒ 全局语句顺序不变

落库按 TX_CHUNK = 500 分块提交。分块 ≠ 单事务——这意味着中途失败会留下已提交的前几块， 重放必须收敛。所以每一条写都必须幂等：pe_owner 的插入曾经不是，导致该 dbnum 反复失败、水位永远不动 （案例 14）。

⑤ 影响判定：唯一的 attr → effect 映射

这一层踩过两个坑，方向相反但根因相同——分类规则散落在多处：

  • 名单过宽：POSS/POSE/CPOS 这些名字带 POS 的属性定义的是几何本身， 却被归进「只更新 transform、不重建 mesh」的便宜路径——改型材端点，长度不跟着变 （案例 02）。
  • 顺序决定归属：五张分类名单靠 if-else 链先后判定，73 条重名被短路后永远走不到， 错写漏写都不报错。合并成唯一映射后，重名成为可检测的冲突（案例 03）。
正交性 「它是不是一条引用」（建不建 ref_rev 边）和「改了它有什么效果」是两个正交问题。 把建边资格挂在效果分类上，归在 DirectGeometry 表里的引用属性（NGMR/ORRF/VXREF） 就会一条边都不建（案例 06）。

⑥ 生成根：一个变化元素归一到恰好一个根

这里的纪律不是「算法要对」，而是「三条路必须算出同一个答案」：主路径、无索引兜底、失败补偿 如果各用一套口径，就会出现「主路径说重生成、补偿说跳过」——失败重试之后模型永远补不上 （案例 04）。 ADR-008 把统一收口点定在 generation_root。

⑦ 反向级联：ref_rev 回答「谁在用我」

PDMS 原生有存储型逆指针（SPBREF/SCBREF/TABREF 等），但离线解析取不到—— 这是 ADR-003 决定自建 ref_rev 的直接依据。 索引本身存的是正向边，反着查；边 id 是两端复合主键，所以重复写天然幂等。

这条链路上最脆的一处不在算法里，而在一行 SQL 的子句顺序：死信复活依赖 attempts = IF {end_sesno} > (source_end_sesno ?: 0) THEN 0 ELSE attempts ?: 0 END 在 source_end_sesno = … 之前求值。挪一行，所有死信任务永远失去复活能力—— 没有报错、没有告警、没有测试会红。现在靠一条断言钉住（案例 07）。

⑧ 模型生成与删除清理

四类模型工作按 (dbnum, action, target_refno) 去重入库，语义是 at-least-once： 模型失败不回滚数据与水位。这个选择的代价是每个环节都必须能安全重跑。

【删除清理的两个坑，方向相反】 坑一 · 清理集为空（案例 08） 被删元素带 deleted = true 软删墓碑 生成期却用 !deleted 过滤 ⇒ 它永远进不了删除集 ⇒ 几何原样留在库里 坑二 · 清理中途失败（案例 09） render_cascade_delete 的清理条件，读的是它自己刚删掉的那条边 DELETE inst_relate:X ; ← 已提交 IF (该边不存在) THEN 删几何 END ; ← 这里失败 重试时条件恒为假 ⇒ 清理被静默跳过，函数还返回 Ok 修法：整段包进 BEGIN TRANSACTION … COMMIT TRANSACTION 坑三 · 记录压根没建（案例 10） 普通元件：inst_info_map → 建 inst_relate 记录 → aabb / world_trans 有处可存 TUBI ：inst_tubi_map → 只收集 aabb 和 transform，从不建记录 ✗

按需生成（on-demand）这一侧的失败形态是「不报错、0 个几何」：精确 CATA 闭包的类型白名单 少一个 GMSS，WALL 的 SPRF → GSTR → GMSS 就断在最后一跳 （案例 16）。 修完还有第二层——闭包结果有缓存，规则改了旧缓存仍然宣称「依赖已解析完」， 所以必须带 CATA_CLOSURE_SCHEMA_VERSION。

结构专业还暴露了一类数据形态问题：隐含子元素（PAVE / VERT / SPINE / POINSP / CURVE）只有 noun 表记录、 没有通用 pe 行。按 pe 表查子元素的代码必须准备好回退到 noun 表 （案例 17）。

⑨ 收口：三段式水位

收口之外，这一层还有两条「别让局部失败变成全局停摆」的教训：

  • 失败隔离要真的隔离。drain 的注释承诺「单个坏任务不阻塞队列」， 但删除队列行用的是裸 ?——一次数据库抖动就让本轮后面所有任务全不跑， 而且已经生成成功的那个下轮还要重跑一遍完整几何（案例 12）。
  • 不要用 panic 表达业务失败。一句 .expect("更新模型数据失败") 把「一个元件网格生成失败」升级成「整个增量看门狗停止工作」 （案例 13）。

3 · 六条不变量

这六条是从 20 个案例里反提炼出来的。每一条都至少被一个真实缺陷违反过， 所以它们不是「最佳实践」，是止血线。

#不变量被谁违反过
I1「观察」与「应用」是两条独立的写。 文件观察字段的写入失败， 不得修改或间接影响 applied_sesno。15
I2同一个判定只能有一个定义处。 属性效果、生成根、建边资格—— 主路径 / 兜底 / 补偿必须调用同一个函数，而不是各写一份。03、04、06
I3水位只在一个原子事务里前移，且必须与模型工作登记、交付态同批。11
I4分块提交下每一条写都必须幂等，同窗口重放必须收敛到同一末态。14、19
I5局部失败只隔离到自己。 一个任务失败不得阻塞整轮； 业务失败用 Err 表达，不用 panic。12、13
I6读后写的清理必须在同一事务内。 条件读的是自己刚删掉的东西时， 中途失败会让重试恒为假、静默跳过。09
还有两条「元」纪律 规则变了，缓存必须跟着失效——闭包 / 分类 / 名单类缓存都要带规则版本号， 否则一次修复会被旧缓存完整吃掉，看起来像「修复无效」（案例 16）。
等价性测试不能复用被测逻辑——折叠等价性用独立写的状态机回放两遍对拍， 如果回放器复用 fold_window 的 run 检测，测试只是在证明它自己内部一致（案例 19）。

7 · 复现命令

release 可执行文件还需要 D:\Rust\target\debug 里那 104 个 DLL（OpenCASCADE 等）， release 目录下一个都没有，不加进 PATH 会直接 STATUS_DLL_NOT_FOUND 退出。

# 窗口成分 / 重复度分布 / 折叠收益估算（只读，不连库）

激进折叠未做末态 Deleted 只留墓碑可再降约 19 个百分点语句数， 但需先确认没有消费方依赖 deleted = true 记录。
load_base_graph 逐跳串行未做同文件的 fetch_ref_rev_edges 已是正确的分块批量写法，可照抄改成逐层 BFS。
maintain_reverse_index 无条件 DELETE未做对每个非 None 变更都发一条 DELETE {referrer}->ref_rev;， 哪怕该元素没有任何引用属性。
同文件一轮打开 3~4 次未做init_watcher → SesnoRangeResolver::resolve → resolve_with_header → collect_changes。远程共享目录上成本不低。
裸字符串拼 SQL未做全链路无参数绑定。转义靠调用点自觉——已经因此出过一次故障（案例 14）。
B3 · record_scan 早于重复判定已知重复文件两份都会写观察字段，最终留下的身份取决于文件大小。 applied_sesno 不受影响，只是状态记录被污染。
B4 · init 递归 / watch 限深不一致已知监控注册本身是 NonRecursive，不构成漏判； 但子目录里的库文件启动时会被处理、之后永远收不到事件。
折叠的命名空间断言建议三个命名空间在折叠侧独立归并，落库观测面却是一个 MERGE 对象 ⇒ 「后一个会话胜出」被换成「显式命名空间恒胜」。当前构造不出发散（refine 保证两侧值恒等）， 但建议加断言，防 refine 变更导致等价性在两层测试都通过的情况下悄悄失效。
