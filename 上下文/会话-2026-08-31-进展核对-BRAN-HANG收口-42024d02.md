### 关键发现：`RPRO` 不是属性，是「按名字查设计表」的引子

这条卡了整段的大头，也是照着字典查一辈子都查不出来的东西。

`PDIS` 里大量出现 `ATTRIB RPRO TLEN` / `ATTRIB RPRO RADI`。`RPRO`（`db1_hash` 840258）
**在 1933 个 noun 的字典里既不是 noun、也不是任何 noun 声明过的属性**，`TLEN` / `HLEN` /
`YB` / `CGC` / `LENR` / `LENL` 同样查无此名。靠数据反推出来的真相是：

> 目录件的 `DTRE` 指向一个 `DTSE`，`DTSE` 的每个 `DATA` 成员用 `DKEY` 当键、
> `PURP` 说这个键的值从哪来、`NUMB` 给下标、`PPRO` 是它自己的公式。
> `ATTRIB RPRO <键>` 就是拿 `<键>` 去查这张表。

`PURP` 四种取值实测：`DATA`→目录件 `PARA[NUMB]`，`DESP`→设计构件 `DESP[NUMB]`，
`ATTR`→设计构件上同名属性，`EXPR`→求这一行的 `PPRO`。

**这个读法是自证的**，不是我归纳出来硬套的：命中的行往往把 `PURP` + `NUMB` 指的东西
在 `PPRO` 里又写了一遍——`RADI` 行 `PURP=DESP NUMB=1` 而 `PPRO = ( ATTRIB DESP[1 ] )`，
`CTLF` 行 `DESP` / `6` 而 `( ATTRIB DESP[6 ] )`，`APAR` 行 `DATA` / `1` 而
`( ATTRIB PARA[1 ] )`。三行互相印证。所以实现上**先认 `PPRO`、`PURP` 只兜底**：
目录自己写了公式就用目录的，别用我从样本里归纳的映射。改成这个顺序后全库数字**一字未变**，
等于两条读法在 4714 个端点上完全一致。

### 实测（ams8000 全库，2612 个路由构件，5.3 s）

目录链走通 2357×2 = 4714 个端点（`PTAX` 4198 + `PTCA` 516）。定位属性全部求出的：

| | 接 `RPRO` 前 | 接 `RPRO` 后 |
|---|---:|---:|
| 端点全求出 | 3033（64.3%） | **3185（67.6%）** |
| `PDIS` 求不出 | 1653 | **1515** |
| `PX` / `PY` / `PZ` 求不出 | 28 / 28 / 14 | **0 / 0 / 14** |
| 求不出的公式**种类** | 10 | **2** |

剩下那 2 种是同一个东西：`( ATTRIB RPRO TLEN )`，1529 处，设计件清一色 `FTUB`。

**求出来的数是对的，有独立验算**：一个 `BEND` 的 `PDIS` 公式是
`( ATTRIB PARA[1 ] + 2 * ATTRIB PARA[9 ] ) / 2 * TAN ( ATTRIB ANGL / 2 )`，
求得 1.853060516503026。手算：通径 50 + 2×壁厚 1.5 = 外径 53，半径 26.5，
`ANGL=8°` → 26.5 × tan(4°) = 26.5 × 0.069926812 = 1.8530605。这正是弯头切线长的
标准式，两边独立对上。

### 有意留下的账：`TLEN` 不猜

`/ACP1000-TFVL-DTSE` 的 `TLEN` 行是 `PURP=EXPR`、`DTIT="True Length"`，而
**`PPRO` 那一格是空的**——目录没写这个键怎么算，是 E3D 自己算。两种读法都说得通、
几何却相反：

- 它的邻居 `HEIG` 行（`PURP=ATTR`，`DTIT="Tray Length"`）读得到设计件的 `HEIG`，
  实测两个样本分别是 1300 与 998，都是那根托盘自己的长度（1300 那根所在 BRAN 从
  z=1580 到 z=280，正好 1300）。若 `TLEN = HEIG`，元件铺满、隐含管身为零。
- 若按 `DPRO = ( 0 )` 取默认，则元件零长、整段都是隐含管身。

目录作者同时定义了 `HEIG` 与 `TLEN` 两个键、标题还不一样，显然不是一回事；把
`TLEN` 当 `HEIG` 是替他编答案。**留空**，返回 `None` 而不是 0——按本 crate
「不发明值」的口径，这 1529 处显式挂账，等 core.dll 那条 `EXPR` 空槽的处理钉死再补。

同样显式挂着的还有 `iparam`（全库无保温件，够不着）与 `design_dimension`
（唯一入口 `TANF` 自己就没钉死），两处都在代码注释里写明了为什么不猜。

## 第三段：接线，以及自证把接线的成果否掉一半

用户「继续下一步」。这一段做的是 `p1-wire`，但真正的产出不是接线本身。

### 接上了什么

新模块 `e3d-model/src/catalogue_point.rs`（`CataloguePoints`）实现 `PPointResolver`：
走 `SPRE →(CATR)→ SCOM → PTRE → PTSE` 拿到 P 点，用 `DbElementParamEnv` 求 `PDIS`
与 `PBOR`、用 `axis_spec::direction` 解 `PAXI`，再套 `world_matrix` 转世界系。
`pipeline` 换掉 `CatalogueNotWired`；`gen_ams` 加了可重复的 `--catalogue`
（目录库与设计库同池，P 点在跨库的另一头）。

`measure_tubes` 顺手把 `DbNotRegistered` 单独接住记成 `ppoint_db_not_open`：
库没开是**配置**问题，不是这棵子树坏了，让它冒泡会把整个生成炸掉；
折进 `missing_ppoint` 又会把配置问题读成数据问题。

### 自证：判共线，不判同向

新探针 `examples/tube_axis_check.rs`。管身沿连接轴生长，所以
`to.pos − from.pos` 必须与两端 P 点的轴**共线**——这是眼下唯一不依赖 E3D 真值的硬判据。

第一版按「出发端同向、到达端反向」写死，跑出来满屏 `180.00°`，判成全错。
**是判据错了，不是数据错了**：两端各自朝里朝外是 E3D 的约定问题。折进 `[0°, 90°]`
判共线、符号另开一栏统计，才问出正确的问题。

### 自证揪出的两件事

1. **`PTCA` 的 `DIR` 是模板缺省值，不是方向。** 全库每个 `PTCA` 上它都是 `[0, 1, 0]`。
   拿它当方向，弯头的两个口解出**同一个**方向（都是局部 +Y 转世界系），
   而管身照建不误、长度也像模像样，只是朝向全错。
   `tubes_measured` 从 1 涨到 156 看着很好看，共线率只有 11%。
   **这种错法比解不出恶劣得多：记账上看不见，几何上看得见。**
   已整类改回 `None`，`measured` 落到 133——数字变小，但剩下的每一条都站得住。

2. **真方向在 `PTCD`，第三套字编码，还没解开。** 首字是含自身的总长：

   ```text
   P1  [6,  5, 2, 21, 11, 61]
   P2  [17, 5, 2, 22, 12, 10, 1, 106, 2, 773119, 1, 1, 0, 1601, 1701, 15, 61]
   ```

   `catalogue_pml`（PML 逆波兰）与 `axis_spec`（轴规格）两个现成解码器都读不通。

### 正面证据：`PTAX` 那条路是对的

分支 `/LV-CO-1R312-D` 的 ELBO 离开点解出 `(-4602.526, 7926.265, 2890)`，
与容器 `TPOS` `(-4602.53, 7926.26, 2890)` 差 **0.005 mm**。
世界矩阵、`ORI` 解码、`PDIS` 求值、`PAXI` 解码这四样被这一条一起钉住了。

### 剩下的疑点：容器头与首件差几十到一百毫米

量出来的 133 条里 `容器头 → 构件到达` 有 58/95 偏差 > 30°，
几乎全是「Z 对齐、XY 差几十到一百毫米」。样本 `/M-OR-1R312-C`：
`HPOS = (-4563.92, 7992.03, 1950)`、`HDIR = +Z`、`HREF = 0/0`（头没接任何东西），
而唯一的成员 FTUB `POS = (-4663.92, 7992.03, 1950)`——整整差 100 mm 的 X。
`构件离开 → 构件到达` 那一类共线率明显更高，所以问题多半在容器头这一侧、
不在目录链。**没有动手改**：先拿全库分布判它是模型噪声还是系统性错读。
