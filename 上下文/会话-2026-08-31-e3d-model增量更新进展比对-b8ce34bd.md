## 缺口清单（按会不会导致错模型排）

### P0-1 属主变更不触发级联 → 静默漏件（真缺陷，本会话独立复核确认）

`increment.rs::placement_drifted` 只比两端 `local_placement`，而
`transform.rs::local_placement` 只读 `POS` / `ORI` 两个属性（已读源码确认）；
`world_matrix` 却吃整条 owner 链。

漏的场景：容器（ZONE/STRU/FRMW/SUBE/CMPF…）改挂到另一个属主下。
它自己 POS/ORI 一字未改 → `placement_drifted` = false → 不级联；
它自己是 List → `nearest_unit` 给 None → 记 `no_model`；
新旧两个属主成员表变了 → 同样是 List → 也记 `no_model`；
子树后代索引记录一字节未动 → 根本没有候选。
→ **整窗口 0 重建，而两端全量会说「变了一片」。**

`local_placement` 的 doc 自己写了「判据必须与矩阵折叠读同一条路，否则会出现
矩阵变了但漂移检测说没变的静默缺件」—— **当前实现没做到它自己写的这条**。

修法：漂移判据从 `(POS, ORI)` 升成 `(owner_refno, POS, ORI)`，或直接比两端 `world_matrix`。

## 0. 最重要的一条：我们照错了机制

Core3D 里有**两套**互不相同的增量机制，此前全部取证（`docs/specs/core3d-partial-update-conformance.md`
的 R1–R29）只覆盖了第一套：

| | `PartialUpdateDesiMgr` | **`DES_DrawListManager`（本轮新发现）** |
|---|---|---|
| 场景 | **会话内**实时重画 | **两个会话之间**（Get Work / 换会话） |
| 输入 | `QCHGLS` 变更表 | `DB_Compare::scan` 两端点扫描 |
| 上卷函数 | `SignificantOwner`（爬到最近 significant 位） | **`findTopLevelElement` → `desdblib/FNDTOP`** |
| 产物 | 重画队列 + PML `PUPDES` | draw list 的增删改 |

**e3d-model 做的是第二套的场景（两个已保存会话之间做差分），却照着第一套的规则实现。**
这是本轮最值钱的结论。

## 1. `DES_DrawListManager::changesBetweenSessions`（0x1052b730）

签名：`void (const DB_DB*, int, int, int, int, set<DB_Element>&, set<DB_Element>&, set<DB_Element>&)`
——两个会话端点（各两个 int）进，三个 `set<DB_Element>` 出。反编译要点：

```
changesBetweenSessions(db, ep1a, ep1b, ep2a, ep2b, &out1, &out2, &out3):
    MTR_Entry("DES_DrawListManager::changesBetweenSessions")
    清空四个成员 set（this+3 / +5 / +7 / +9）
    DB_DBSavedSession saved(db)                       # RAII，退出时恢复当前会话
    DB_DB::switchToOldSession(db, ep1a, ep1b, 0)      # 切到端点 1
    pred = DB_PredicateOr{ SITE, SSOWLD, CURWLD, PNTWLD, FNCAW, FNCCW, SPMSW }
    root = DB_DB::findElement(db, "/*")
    for elem in DB_Iterator(root, pred, DB_LogicalTreeDefinition::definition()):
        if elem.dbno() != db.number(): continue       # 只比本库
        cmp = DB_Compare(elem, ep1a, ep1b, ep2a, ep2b)   # sub_1055FE80
        cmp.scan()                                    # 产出三棵红黑树：v92 / v93 / v94
        # ① 删除
        if switchToOldSession(db, ep2a, ep2b, 0):     # ★ 切到另一端点才读得出删掉的元素
            processDeletes(v92 收成的 set)
        switchToOldSession(db, ep1a, ep1b, 0)         # 切回
        # ② 新增
        processCreates(v93 收成的 set)
        # ③ 修改
        processModifications(v94 收成的 set)
    把四个成员 set 排干到调用方的三个输出 set
```

**三条即用结论**：

- **A1 比较范围不是整库**：从 `/*` 按逻辑树迭代，只取七种世界级容器
  （`SITE` / `SSOWLD` / `CURWLD` / `PNTWLD` / `FNCAW` / `FNCCW` / `SPMSW`），逐个做 `DB_Compare`，
  且过滤 `dbno == db.number()`。我们的 `collect_window` 是整棵索引树一次差分 = 超集。
- **A2 删除侧必须切到旧端点读**——与 indexdiff 计划 §5-1 拍板的「Deleted 句柄绑 base 端点」
  完全一致。e3d-model 开两个各钉一个 sesno 的 `DbSet`，✅ 已对齐。
- **A3 处理顺序是「删 → 增 → 改」**，三类各走独立处理器。我们是单趟 RefNo 序循环 +
  `deferred` + 自创的「Remove 赢」。

## 2. `processModifications`（0x1052cf80）—— 与我们同构

```
for elem in modified:
    top = findTopLevelElement(elem)
    if !top.isNull() && top.isValid(): 插入 set（天然去重）
```

结构与我们的 `nearest_unit` + `BTreeSet` 一模一样。**差别只在上卷函数的判据。**

## 3. `processDeletes`（0x1052cd20）—— 三个落点，我们只有一个半

```
for ref in deleted:
    top = findTopLevelElement(ref)
    if top 为空或无效:                      # 顶层元素自己也没了，库里问不出来
        for child in DES_DrawList::getChildTOPFElements(ref):   # ★ 问「已经画出来的那份」要
            插入「移除」账
    elif top == ref:                        # 删的就是顶层元素本身
        插入「移除」账
    else:                                   # 删的是顶层元素内部的成员
        插入「重建该顶层」账                  # ★ 不是移除！
```

**第三条与我们相反**：e3d-model 的 `IndexCandidate::Deleted` 一律出 Remove，
只有上卷到的属主还活着时才靠 `deferred` 改成重建。core 是**默认重建属主**。

**第一条我们完全没有对应物**：整块子树没了时，core 不去查库（查不到），而是问
**已有的 draw list**「我之前在它下面画过哪些顶层项」。我们没有「已产出模型集」这个输入，
`execute_plan` 只吃 target 端 DbSet。

## 4. `findTopLevelElement`（0x1052c450）→ `desdblib/FNDTOP`（sub_10380E38）

```
findTopLevelElement(out, elem):
    DB_Save 保存当前位置
    if db_go_to_element(elem):
        flag = (elem.type() != NOUN_TUBI) - 1     # TUBI → -1（&1 为真）；其它 → 0（假）
        FNDTOP(&flag, out)                        # sub_10380E38 = desdblib/FNDTOP
```

`FNDTOP` 反编译（MTRENT 字符串坐实名字 `"desdblib/FNDTOP"`）：

```
FNDTOP(isTubi, out):
    DSAVE                                  # 保存位置
    DGETF(→ out)                           # out = 当前元素
    v5 = isTubi ? TUBI(710633) : noun(当前)
    loop:
        if LISTOP(&v5) 到顶: break         # owner 链爬升
        if isTubi:
            v5 = noun(当前)
            if v5 == BRAN(808220): continue    # ★ TUBI 专用分支：BRAN 这一级不记，继续往上
        out = 当前; DGOTO(out)
        if 出错: DCLERR; out = null; end
        if noun(当前) == WORL(781187): out = null; end   # 爬到 WORL = 没有顶层元素
    if v5 != WORL:
        tmp = 当前; DGOTO(tmp)
        if noun(tmp) == TMPL(779672): out = tmp          # ★ 属主是 TMPL 时改取 TMPL
```

数字码已全部反查（`noun_flags.json` 的 `noun_hash`）：
`781187=WORL`、`779672=TMPL`、`710633=TUBI`、`808220=BRAN`。

**与我们的 `nearest_unit` 的差别**：我们爬到「最近的 `is_positive_solid`」，
core 爬到「顶层可画元素」，终止判据是 WORL，另有 TUBI/BRAN 与 TMPL 两条特例。
**TUBI 那条特例正对着我们的 P0-2（隐式管身）。**

> ⚠️ FORTRAN 伪码较松，`LISTOP` 的确切语义（是否每调一次上移一级）没有逐指令验。
> 「TUBI 跨过 BRAN」「WORL 终止」「TMPL 改取」三条是可读出来的，
> **但「最终落在哪一级」需要再做一遍指令流复核**，不要当已坐实。

## 5. ★★ `hasTopLevelGraphicsChanged`（0x1052c850）—— 几何变没变，只看一个属性

伪码被 Hex-Rays 吃掉了（典型症状：`attributesChangedBetween(v5);` 后跟 `return 0`，
与 conformance §1.4 记的坑同款）。**指令流实读**：

```
hasTopLevelGraphicsChanged(elem):
    db = elem->getDB()
    cur = db.currentSession()
    if !db.previousSession(cur, &prev): return false
    changed = []
    elem->attributesChangedBetween(extractNumber(cur), extractNumber(prev), …, &changed, false)
    if changed 为空: return false
    for att in changed:                       # 0x1052C920 循环
        if att == ATT_CACHID: return true     # 0x1052C917 取 ATT_CACHID；0x1052C92D mov bl,1
    return false
```

**core 判断「这个顶层单元的几何变没变」，既不比 POS/ORI，也不看属性全集，
只看变化列表里有没有 `ATT_CACHID` 这一个属性。**

调用方：`DES_DrawListManager::updateGraphics`（0x1052d38b）、
`PostLocalChanges`（0x1052b04a）、`DES_DrawList::getChildTOPFElements`（0x105167b7）。

### 5.1 CACHID 是真字典属性，而且它的分布就是「模型单元」的字典级定义

`all_attr_info.json`（gen-model 从 dabacon 字典导的那份）实查：

- `CACHID` hash **62869719**，`att_type` = **WORD**
- **204 个 noun 带 CACHID**

带的（节选）：`EQUI STRU BRAN SCTN PANE SUBE TMPL CWALL GWALL STWALL WALL FLOOR CFLOOR
HANG BPANEL CPANEL HPANEL GENSEC LUG TRUNNI XGEOM DOOR WINDOW LADDER PLTFRM …`

**不带的**：`SITE ZONE FRMW PIPE TUBI SBFR`

→ 纯容器（SITE/ZONE/FRMW/PIPE）和派生件（TUBI）没有 CACHID；一切可画单元都有。
**这张表就是 core 对「什么是一个几何缓存单元 = 增量的重建单元」的字典级声明**，
而我们用手写的 `Category::is_positive_solid` 名单在逼近同一件事。

## 7. 对 P0-1（属主变更漏级联）的重新定性

**CACHID 不能直接治 P0-1，但它解释了为什么 core 没有这个病。**

core 的图形段树在绘制时才 `CONCAT` 矩阵，所以容器一移动，后代的**几何缓存**根本没变
（CACHID 不翻），core 只要重新拼变换即可。**我们把世界矩阵烘进顶点，才凭空多出「变换级联」
这个 core 没有的问题。**

→ 所以 P0-1 有两条根本不同的解法：

1. **补判据**：漂移判据从 `(POS,ORI)` 升成 `(owner_refno, POS, ORI)`，或直接比两端 `world_matrix`。
   便宜、局部，但级联扇出大、大窗口更慢，而且是在给一个自找的问题打补丁。
2. **改产物形态**：保留 `(共享几何, 实例变换)` 分离，别把世界矩阵烘进顶点——
   这**正是已批准计划 §1.2 图元实例化拍板的方向**（「默认保留分离形态，只有确实要做布尔时
   才烘平」）。一旦产物侧也带实例表，容器移动只需改变换、不必重建网格，
   **变换级联这个问题从根上消失**，和 core 一样。
