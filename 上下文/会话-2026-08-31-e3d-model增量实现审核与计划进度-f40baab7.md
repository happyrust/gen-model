### 2.3 本轮新查到的两条（前序会话没记）

**（新 1）L3 的账根本没有守恒判据，而计划 §4 正是打算靠它兜 P1-1。**
`accounts_for()`（`increment.rs:213`）到今天仍只有两条恒等式：候选账、执行账。
`ChangeTally` 一个字段都不参与判定。更要紧的是账**本身就漏**：
`ledger.created/deleted/record` 三个入口全部写在 `Ok(...)` 分支里，

→ 想把 P1-1 交给「L3 守恒」兜，得先补上 unresolved 侧的记账，否则守恒式一上来就不平。

**（新 2）`collect_unit_subtree` 的 `visited` 是每次调用新建的，级联之间不共享。**
`increment.rs:392`。一窗里 N 个元素触发级联，重叠子树被重复走 N 遍（每遍都在读页）。
ams1112 那种 24674 候选的窗口里，这是 O(级联数 × 子树大小) 的真实读放大。
功能不错，是成本问题；与 §4 表里「大窗口无成本护栏」是同一条，但那条只说了属性差分，
没说级联遍历。

# 第四篇 · L4 粗粒度键设计（用户 22:25 拍板开工）

> 状态：**取证中 → 设计中**。本篇实时续写。

## 11. 先把地基事实读齐（都指到行）

### 11.1 精细键 `GeometryId` 已经存在，而且**上行已经在用它**

`elmodl.rs`：

```rust
pub enum GeometryId {
    Element { refno: String },
    ImpliedTube { container_refno: String, preceding_refno: String, ordinal: u32 },
}
```

- `GeneratedElement.geometry_id` 就是它，全量管线两种都产
  （`pipeline.rs:434` 建管身时填 `ImpliedTube{container, preceding, ordinal}`）。
- 管身的 `refno` 字段**固定填容器 refno**（`pipeline.rs:440`，注释：「绝不制造伪 refno」）。
  所以一个容器名下 N 根管身共享同一个 `refno`，只有 `geometry_id` 能区分它们。
- `IncrementOutcome.upserts: Vec<GeneratedElement>` → **upsert 侧天生带 GeometryId**，
  `update_ams.rs:185` 已经把它写进 `upserts.json`。

### 11.2 真正的畸形在 remove 侧：**上行说 GeometryId，下行说 RefNo**

`IncrementOutcome.removals: Vec<RefNo>`（`increment.rs:307`），
`update_ams.rs:215` 落盘成一串 refno 字符串。

→ **能加一根管身，永远删不掉一根管身**。这不是「缺一层键」，是**同一条通路上的两端
用了两种键**。`is_model_unit` 有意排除 RouteContainer、`stale_route_containers` 记账，
都是在给这个不对称打补丁。

### 11.3 §3.5「已产出模型集是必需输入」——**这条前提对我们不成立**（本轮新发现）

core 需要 `getChildTOPFElements`，是因为它比较时**不保留旧会话的可读视图**。
我们不一样：`plan_update(base, target, window)` 两端各钉一个 `DbSet`，
**base 端整棵树一直可读**。所以

- 「一个 EQUI 整棵被删，它下面曾经有哪些单元」→ `collect_unit_subtree(base, refno)` 直接问得出；
- 「一个 BRAN 上原来有哪几根管身」→ 在 base 端重走一遍 `walk_route` 就能重算出旧的
  `ImpliedTube` 键，管身虽无库记录，**它的键是从库数据推导出来的**。

→ §3.5 说的那份「产出清单」**不是必需输入**，前提是一条硬约束：
**增量窗口的 base 必须就是模型集当初生成时的那个会话**。
今天没有任何东西钉住这一点（`update_ams` 缺省取「最新两环」，跟模型集是哪一环无关）。
**这条约束应该变成门禁，而不是靠一份产出清单去绕开。**

### 11.4 `built = 0`：这条口子今天是**绊线**，不是**火情**（本轮实测）

扫 `out/*/report.json` 的 `implied_tubes`：

| 语料 | count | measured | built |
|---|---|---|---|
| `ams8000-n3` | 3172 | 0 | **0** |
| `ams8000-p1wire` | 3172 | 133 | **0** |
| `aps250110-handrail` | 48 | 0 | **0** |
| `ams1112-n3` | 0 | 0 | 0 |

→ **今天没有任何一根隐式管身真被建出来**（目录几何求值还没接上）。
所以「删不掉管身」现在删不出错——因为根本没有管身可删。
它会在目录求值落地的**那一刻**同时变成四处错误。**现在动键是最便宜的窗口，
等管身亮起来再动就是带数据迁移。**

### 11.5 refno 这个键**贯穿到了裁判本身**（本轮新发现，比 11.2 更严重）

`tests/increment_real.rs`：

- `type Snapshot = BTreeMap<(u32, u32), Invariants>`——**按 refno**；
- `full_generation` 用 `snapshot.insert(key(generated.refno), …)`——**丢掉 geometry_id**；
- 断言 `upserts.len() == 去重后 len`，配文「upsert 里有重复 refno，同一件被重建了两次」。

一个容器名下 N 根管身共享同一个 refno（11.1）。管身一旦建出来：
`full_generation` 会把 N 根**塌成 1 条**记录，而那条重复断言会**当场炸**——
炸得对，但说的理由是错的（不是「重建了两次」，是「键根本不够用」）。

→ 所以这不是「remove 侧缺个键」的局部问题：**计划集、Remove、模型集、裁判——
四处全是 refno 键**，而产物侧早就是 `GeometryId` 了。

### 11.6 换键的代价被高估了：`GeometryId` 全库只有三个消费点

| 位置 | 用法 |
|---|---|
| `gen_ams.rs:127/372/397` | 序列化进 json + OBJ 标签 |
| `update_ams.rs:112/185/204` | 同上 |
| `increment.rs:694` | `upserts.sort_by(geometry_id)` |

**`rvm_compare` 完全不碰 `GeometryId`。** `increment.rs:73` 那句
「换成 GeometryId 会一起动到 update_ams 与 RVM 对拍」**说错了一半**，
RVM 对拍不受影响。这条注释要一并纠正。

### 11.7 `ordinal` 让管身键**位置脆弱**（本轮新发现）

`route.rs`：`Route.tubes` 条数恒为 `members.len() + 1`，`ordinal` 就是槽位下标。
→ **在 BRAN 头部插一个构件，后面每一根管身的键都平移一位**，
于是「全部旧管身消失 + 全部新管身出现」。逐根管身做差分**毫无意义**。

改成按两端定键 `ImpliedTube{container, from, to}`（头/尾站填容器自己的 refno）：
在 A、B 之间插 X → 只有 `(A,B)` 消失、`(A,X)` `(X,B)` 新增，**其余键全部不变**。
同容器内相邻站点对唯一，空容器退化为 `(c,c,c)`，都成立。
