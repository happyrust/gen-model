## 1. 现状核对（只读）

- 已有「增量阶段控制」：`data_incremental` / `model_incremental` / `room_incremental`（`options.rs:671-747`），语义是**只停消费、不删 durable 工作**。
- 模型工作的唯一自动消费口是 `model_update_pending` 的 drain：`render_drain_select_for_scope` → claim / cohort mate claim / `count_pending_work` /
  `has_pending_work` / `/health` 计数，全部共用 `render_automatic_scope_filter(dbnums)`（`watch_dbnums` 的 SQL 谓词，ADR-048）。
  文档明说「Keep this as a SQL predicate rather than filtering decoded rows: excluded durable work must never be claimed, executed, or have its
  retry counter touched」「过滤两侧对哪些行算数的答案必须是同一个」。
- 队列行带 `noun`（`render_upsert`：`noun = '{item.noun}'`）。窗口规划器（direct + DESI）的 `RegenRoot` / `DeleteCleanup` 都带根 noun；
  老规划器只有 `RegenRoot` 带 noun，`Transform` / `DeleteCleanup` / `PostRegenAabb` 的 noun 是空串；房间任务 noun 是元素 noun。
- `RegenRoot` 入队时顺手把 `gen_root` 标 `publication_status = stale/pending`、`desired_revision` 抬高（`render_upsert` 尾段），
  而凭证前移 `render_credential_advance` 守卫要求 `publication_status = ready ∧ desired == published`——**所以「入队但不消费」的根不会被后续窗口
  误前移凭证**；重启后 `reconcile_startup_window` 把未安定行无条件重排。这就是「只停消费」能闭环的原因，也是**不能在计划层直接丢掉工作项**的原因
  （丢掉 = 不标 stale = 下一窗前移凭证 = 陈旧几何被盖新章，且永不回补）。
- 按需 `ensure_model_generated` 是同步生成（先 `ensure_regen_pending_current` 落行再 `generate_unit_model`），不经 drain，不受消费门影响。
