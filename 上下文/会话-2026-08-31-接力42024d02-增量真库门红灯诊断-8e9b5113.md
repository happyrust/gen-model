### 编码格式（钉死备查）

```text
[总长(含自身), 5|6, 2, opcode, 方向码, <PML 程序> 方向码, <PML 程序> 方向码, …, 61]
```

- `opcode = 20 + 方向个数`：`21` 裸轴、`22` 一次转角、`23` 两次；
- 方向码 `11..16` = `X -X Y -Y Z -Z`；
- 每段 `<PML 程序>` 首字是自身长度，内容是普通目录 PML，求值出**角度（度）**，
  语义为「把当前方向朝下一个具名轴转这么多度」；
- 末字 `61` 收尾；`AXIS` 前缀只在首方向是反向轴时打印，纯显示，不影响求值。

### 唯一可疑的算式，实测证明踩不到

解码器把「朝下一轴转 θ」算成：

```rust
vector = [v[0]*cos + n[0]*sin, v[1]*cos + n[1]*sin, v[2]*cos + n[2]*sin];
// 然后归一化
```

`v·cosθ + n·sinθ` 只有在 `n ⊥ v` 时才等于真旋转。不正交时归一化会把结果拉成一个
**角度不对**的方向，而且不报错——`X (45) Z (45) X` 这类会静默出错
（`X (45) -X` 那种正好抵消的还好，会退化成零向量被长度检查挡下）。

所以给 `examples/ppoint_probe` 加了两本账：`ptcd_outcome`（解码结局，按 opcode 分）
与 `ptcd_oblique`（沿转角链走一遍，回报最不正交那一处的 `|cos|`，全正交则不记）。
对 ams8000 设计库 + 六个目录库跑完：

```
PTCD 解码结局（按实例）：
     323x  opcode 21 解出
     193x  opcode 22 解出
  —— 解出 516/516（100.0%）

PTCD 非正交转角（解码器算式在这些链上不成立）：
  无。实测库里每一段转角都朝着与当前方向正交的轴。

PTCA 的方向来源（按实例）：
     516x  DIR 三元组 [0.0, 1.0, 0.0]
```

三件事一次说清：

- **解码率 100%**，`missing_ppoint` 那本账里一条 `PTCA` 都不欠；
- **opcode 只有 21 与 22**，连两段转角的链都不存在，更谈不上非正交；
- **`DIR` 恒为 `[0,1,0]`** 得到再次确认，516 个端点无一例外，坐实它是模板缺省值。

隐患降级为「理论上的」：算式在多段链上确实不严谨，但本项目的目录库里够不着。
真要根治是把 `v·cos + n·sin` 换成先对 `n` 做 Gram-Schmidt 正交化再合成，
一处三行的事——留着，等真撞见 opcode ≥ 23 的库再改，现在改属于无据修改。

### 分母一换，结论反转

先前「涉及容器 130/560」用错了分母——560 里绝大多数容器压根没量出槽位。
换成「至少量出一条槽位」的容器：

```
偏移形态（横向 > 1mm 的 216 条）：
     133x  纯水平（Z 对齐，只差 XY）
      43x  纯铅垂（XY 对齐，只差 Z）
      40x  混合
涉及容器 130/186（69.9%）
偏移量恰好落在整毫米上的 55/216 条，出现最多的：
      12x 100mm   11x 50mm   10x 200mm   5x 30mm   4x 26mm   3x 300mm   2x 400mm
```

两个数字指向相反：70% 像系统性错误，而 100/50/200/300/400 这种整毫米像设计师手填。

**决定性的数不在这 216 条里，在被我一直当背景板的 2493 条零长槽位上。**

```
槽位 3172
  两端解出且非零长    334   ← 前面所有比例的分母
  零长               2493
  解不出 P 点           6
  P 点所在库没开      339
```

零长的判据是 `< 0.051mm`。**2493 条槽位的两个端点，各自沿完全独立的路径解出来
——一头走 `SPRE→SPCO→CATR→SCOM→PTRE→PTSE→PTAX/PTCA` 再乘构件世界矩阵，
另一头走另一个构件的同一条链——落点重合在 0.05mm 以内。** 这种事不可能是巧合：
若目录链、PML 求值、轴解码、`ORI` 折叠、世界矩阵中任何一环有系统性错误，
这 2493 条会当场散架。

而且容器端也在这本账里：`容器头 → 构件到达` 共 559 条槽位、只量出 111 条，
`构件离开 → 容器尾` 559 条、量出 102 条——**剩下约 900 条是 `HPOS`/`TPOS`
与相邻构件 P 点重合到 0.05mm 以内**。`HPOS` 用错坐标系这一类解释，就此排除。

### 结论

排掉库没开的 339 条与解不出 P 点的 6 条，能完整求解的 **2827** 条槽位里
**2493 条（88.2%）两端严丝合缝**，只有 334 条真有间隙，
其中 216 条（占可解槽位的 7.6%）走向是歪的。

**这 7.6% 是模型自己的几何，不是我们的求解错误。** 佐证有三：

1. 同一套求解链在 2493 条上精确到 0.05mm，不可能只在另外 216 条上系统性出错；
2. 偏移量大量落在 100 / 50 / 200 / 300 / 400mm 这种整毫米上，坐标算错不会凑整；
3. 最大的两条来自一个 `POS` 还停在原点、从没摆过位置的游离构件——
   这个样本库本身就含垃圾数据。

E3D 遇到这些槽位也会照画一根歪管，我们与它一致。

### 于是「35.3%」这个指标本身要改

`判据三：横向偏移 < 1mm 的 118/334（35.3%）` 是个**误导性指标**：它的分母
把 2493 条完美连接排除在外，专挑有间隙的槽位算，于是把模型的脏数据读成了我们的错误率。

正确的说法是「可解槽位 2827 条中 2493 条（88.2%）两端重合，216 条（7.6%）歪」。

**已改（19:3x）**：探针的判词区现在分两段印——判据三保留但加了「它的分母是有间隙
的槽位，不要当求解正确率读」的明示；新增「求解正确率 / 模型体检」一段，
分母写全（`可解 = 零长 + 有间隙`，库没开与解不出 P 点各自列出不入分母）。
实跑输出：

```
求解正确率：可解槽位 2827 条（= 零长 2493 + 有间隙 334；库没开的 339 条与解不出 P 点的 6 条不入分母）中，
   2493 条（88.2%）两端重合到 0.051mm 以内。
模型体检：216 条（占可解槽位 7.6%）两端解得出、但走向是歪的。这一批是模型自己的几何，
   不是求解错误——同一套链在上面那 2493 条上是精确的。
```

### 二、但「求得出」不等于「读得对」，这才是真问题

存档里把危险讲清楚了：两种读法几何上**相反**。

| 读法 | 后果 |
|---|---|
| `TLEN = HEIG` | 元件铺满整段，隐式管身长度为零 |
| 空槽当 `DPRO = (0)` | 元件零长，整段都是隐式管身 |

`PXLE := ATTRIB RPRO TLEN` 求得 1500、实例 `HEIG` 同为 1500），一个样本分不开两种读法。

### 三、用一个独立来源把它分开了

关键在于**两端的来源毫不相干**：

- `FTUB` 的**离开点** = 它的 `POS`/`ORI` + 目录 P2 的 `PDIS`，
  而 `PDIS` 整条就是 `( ATTRIB RPRO TLEN )`，也就是这个顶法的产物；
- 它**下一站的到达点** = 另一个构件自己的 `POS`/`ORI` + 那个构件自己的目录 P 点。

两者对得上，只能说明顶法是对的。给 `tube_axis_check` 加了一本按离开端 noun 分的
槽位结局账，跑出来：

```

  FTUB     零长  1294 / 共  1472（87.9%），有间隙 178
  BEND     零长   573 / 共   607（94.4%），有间隙 34
  ELBO     零长   153 / 共   158（96.8%），有间隙 5
  ATTA     零长    27 / 共    32（84.4%），有间隙 5
  REDU     零长     1 / 共     1（100.0%），有间隙 0
  VALV     零长     0 / 共     1（0.0%），有间隙 1
```

**1294 条独立对账，重合在 0.051mm 以内。** 若 `TLEN` 该读成 0，这些离开点会
全部退回到到达点上，零长比例是 0% 而不是 87.9%。两种读法就此分开，
`TLEN = HEIG` 胜出，没有余地。

**对照组更硬**：`BEND` 走的是 `RPRO RADI`、`ELBO` 压根不经这条分支，
它们是 94.4% 与 96.8%。`FTUB` 的 87.9% 与它们同一个量级——说明 `TLEN` 没有
把 `FTUB` 往下拽；剩下那 12% 的间隙各 noun 都有，是第七节说的模型自身几何，
不是这条读法的锅。

物理上也讲得通：`FTUB` 本身就是一段直管元件，它铺满自己那一节、后面不需要
再补隐式管身，正是应有的样子。

## 十、入库前的工作树普查：为什么「P0 分类表」不能单独成一笔

用户要求把未入库的改动拆成两笔（P0 分类表 / P1+P2 几何与目录链）。落手前先量了
工作树，结论是**这个切法做不出两笔都能编译的提交**，原因在下面第二节。

### 一、当前是全绿的

```
lib            104 passed
rvm_compare      6 passed
noun_coverage    7 passed
increment_real   1 passed（4 个真库窗需 --ignored 显式跑，313B 报全过）
clippy / fmt     零告警、零差异
```

所以「能不能提交」不是质量问题，只是切法问题。

### 二、e3d-model 的 src 是一个原子块

新 `category.rs` 相对 HEAD **新增了五个 `Category` 变体**——`RouteContainer`、
`RouteMember`、`GeometrySet`、`NegGeometrySet`、`Composite(_)`（`git show HEAD:src/category.rs`
里这五个字符串出现次数全是 0）。于是一条依赖链把所有文件焊死：

| 想单独提交 | 立刻拖进来什么 | 为什么 |
|---|---|---|
| `category.rs` | `pipeline.rs` | 老 pipeline 的穷举 `match` 少五条臂，编译不过 |
| `pipeline.rs` | `route.rs`、`catalogue_point.rs`、`lib.rs` | 它 `use` 这两个新模块 |
| `lib.rs` | `element_diff.rs`、`ledger.rs` | 新 lib.rs 里声明了这两个模块 |
| `element_diff.rs` | `increment.rs`、`tests/increment_real.rs` | 313B 这轮重构是一体的 |

**「P0 分类表」单独一笔 = 一个编译不过的中间提交**，`git bisect` 会在那一笔上撞墙。
这不是洁癖：这个仓的价值一大半在真库门，一个不能构建的提交等于在历史里挖了个坑。
