## 结论：三条经验证站得住的性质

1. **上卷方向是对的，而且有硬支撑**（我专门去验的一条）：
   `DbElement::members()` 读的是**属主自己记录里的成员表**（`parsed()?.members`），
   不是按 owner 指针扫子节点。所以任何增删成员 / 改挂 / 重排都会重写**属主的记录**，
    30|   属主必然自带一个 Modified 候选。这条是「删除候选上卷到属主重建」能成立的前提。
   同时 `collect_negatives` 只从元素**自己的 members**收负体（CMPF 深层也在自己子树内），
   负体永远落在消费它的正体的 owner 子树里 → 沿 owner 链上卷方向正确，不会跨枝。
   **但这条关键前提在 `increment.rs` 里一个字都没写**，也没有测试钉住它。
2. **先擦后画**：重建 Skipped / 失败一律补发 Remove，不留陈旧网格；`execute_plan` 对
   「上卷选出的单元在 target 里读不出 noun」也是记账 + Remove，不 panic。
3. **真库门是真门，不是空转**：`Shape` 把「这个样本压哪条路径」从注释升成断言，
   裁判在那条路径上看不见东西就当场红；反向断言 `removals ∩ target_full == ∅`
   拦住了「多删」这种比漏建更严重的错。12:5x 实测三条路径精确命中（插入说 3 就建 3、
    40|   修改说 1 就建 1），不是靠保守整库重建骗过覆盖断言。

## 缺陷清单

### P0-1 属主变更不触发级联 → 静默漏件（真缺陷）

`increment.rs::placement_drifted` 只比两端的 `local_placement`，而
`transform.rs::local_placement` 只读 `POS` / `ORI` 两个属性。

**漏的场景**：把一个容器（ZONE/STRU/FRMW/SUBE/CMPF…）改挂到另一个属主下。
它自己的 POS/ORI 一字未改，但它子树里每一件正体的**世界矩阵**都变了。

    50|**为什么整条链都拦不住**：
- 该容器自己是 `List` → `nearest_unit(target)` 给 `None` → 记 `no_model`；
- `placement_drifted` 比 (POS,ORI) → 相等 → **不级联**；
- 新旧两个属主的成员表变了 → 它们也是 Modified 候选，但同样是 `List` → 也记 `no_model`；
- 子树里的后代**索引记录一个字节没动** → 根本没有候选。
→ 整个窗口 0 重建，而两端全量生成会说「变了一片」。这正是 crate 自己宪法里
「静默缺件是最高级别缺陷」点名的那一类。

**修法**：漂移判据从 `(POS, ORI)` 升成 `(owner_refno, POS, ORI)`，或直接比两端
`world_matrix`（后者顺带覆盖以后可能加进矩阵的任何输入，代价是每候选多走一遍 owner 链）。
    60|注意 `local_placement` 的 doc 已经写死「判据必须与矩阵折叠读同一条路，否则会出现
矩阵变了但漂移检测说没变的静默缺件」——**当前实现没做到它自己写的这条**：
`world_matrix` 吃 owner 链，`local_placement` 不吃。

### P1-1 级联 fanout=0 时把有贡献的候选记成 no_model（账目说谎 + 依赖处理顺序）

`increment.rs` 里 `contributed = contributed || fanout > 0`，而 `collect_positive_subtree`
返回的是**新加进集合**的个数。嵌套容器同时漂移时（ZONE 与其下 STRU 都改了 POS），
先处理的那个把整片子树收完，后处理的 fanout=0 → `contributed` 仍是 false →
该候选被记进 `no_model`（文档定义是「改动落在没有正体归属的元素上」）。
账本恒等式照样闭合，但报告在说谎，而且同一份数据换个遍历顺序会给出不同的报告。

    70|### P1-2 `flag_only_drifts` 只记不判

字段注释写「真实语料上恒 0，非零值得人看」，但 `accounts_for` 不看它，
`update_ams` 也不因它非零退非零码。真出现的那天会静默滑过去。

### P1-3 `no_model` 没有合法性守卫

今天 `RouteMember`（104 个管件 noun）/ `Catalog`（FITT/PFIT/…）/ `RouteContainer`
都不产几何，所以它们的改动落 `no_model` 是**正确**的。但 P1 目录求值一落地，
同样一份报告、同样一行 `no_model: {"ELBO": 12}`，性质就从「本来就没模型」变成
「漏了 12 件」——外观完全一样。建议把守卫写成：`no_model` 里出现的 noun，
    80|其 `classify` 结果必须是「本期确定不产几何」的类别，否则当场红。

## 下一个里程碑会打破的三条假设（grill 的输入）

1. **模型单元 = 一个产正实体的元素**。隐式管身（`RouteContainer` 相邻两件之间派生出的管身，
   `pipeline.rs::implied_tube_count` 已经在数了）不属于任何元素，改一件成员会影响它两侧的管身。
   P1 一落地，`is_positive_solid` 这个单元定义就不够用了。
2. **窗口 = 单库 + 两个会话**。目录求值让设计库的几何依赖**目录库**；目录库改了，
   设计库一个候选都不会有 → 整片管件几何静默过期。`collect_window(db_file, base, target)`
   的签名里没有第二个库的位置。
3. **动作集是无状态的**。`IncrementOutcome` 只有 upserts / removals，没有「这批动作的前置状态
   100|   必须是 base_sesno」这条水位线。谁也不保证被应用的那个模型集此刻正停在 base 端。
