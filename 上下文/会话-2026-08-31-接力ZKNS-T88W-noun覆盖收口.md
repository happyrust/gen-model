CONVEY 6 ─→ STRU 18 / EQUI 6 / DDSE 6               （挂在 ZONE 下）

三条结构性事实立刻可读出来：

1. **`CONVEY` 是组织容器**：自己不挂任何图元，几何全在子节点 `STRU`（结构）和
   `EQUI`（设备）里，和 `HVAC`/`PIPE` 是同一类东西（那两个已经判 `Category::List`）。
2. **`HANDRA` 的几何在路径上**：`HANDRA → RPATH → POINTR`，81 条扶手带出 81 条
   路径、352 个路径点。扶手的实体是「截面沿路径扫掠」出来的，不是图元堆出来的。
3. **`TMPL` 底下挂着真图元**（`PANE 84`/`CYLI 48`/`BOX 19`/`EXTR 9`…）。
   这一条要特别小心：它的风险方向和别的都相反——不是漏建，是**可能多建**。

关于第 3 条，实跑账已经能回答一半：`aps250209` 的 `unsupported` 是
`{CONE: 24, DISH: 1}`，而父子表里 `TMPL → CONE 22`、`TMPL → DISH 1`，
说明**流水线确实下钻进了 `TMPL`、它的子图元被正常访问并计账**
（`Unknown` 不消费成员，成员照样入队，DFS 可达数 20993/20993 已验证）。
所以 `TMPL` 判 `Unknown` 没有丢几何。剩下的问题是「这些图元该不该建」，
即模板是原型还是实体——留待 6-5.5 取证。
（**后续更正**：6-5.7 的实跑推翻了「没丢几何」这半句——正体没丢，
`TMPL` 底下的**负体**丢了 1559 件。）

### 6-5.5 `IASLCO` 反编译：`HANDRA` 和我们判「有几何」的结构件同族

`IASLCO` 全文就是一张写死的 noun 名单（`0x561b994`，10 个码）。把码翻译回名字：

|---|---|---|---|---|
| 294018652 | `STRFLT` | `IPFCOM` | 是 | `Composite(Structural)` |
| 196766188 | `PLTFRM` | `IPFCOM` | 是 | `Composite(Structural)` |
| 297914363 | `HRPOST` | `IPFCOM` | 是 | `Composite(Structural)` |
| 196746659 | `HRTERM` | `IPFCOM` | 是 | `Composite(Structural)` |
| 82930076 | `HRGATE` | `IPFCOM` | 是 | `Composite(Structural)` |
| 79747991 | `HRPANE` | `IPFCOM` | 是 | `Composite(Structural)` |
| **24535259** | **`HANDRA`** | `[]` | **否** | **`Unknown`** |
| 108663841 | `STRLNG` | `[]` | 否 | `Unknown` |
| 181440335 | `KICKPL` | `[]` | 否 | `Unknown` |
| 774243 | `RAIL` | `[]` | 否 | `Unknown` |

**`IASLCO` 就是「扶手／平台总成族」谓词**：扶手本体、立柱、端头、门、栏板、
踢脚板、横杆、平台、结构板全在这一张名单上。其中 6 个我们判 `Composite(Structural)`
（记账为有几何待建），4 个判 `Unknown`。

同一张名单被劈成两半，唯一的分界线就是「字典给没给 `IPFCOM` 位」——
这不是语义分界，是**字典标注的疏漏落在了我们的分类结果上**。

`IUPCOM` 顺带也解了（11 个：`IBNDRY ICLIP ICTOUT IFCPLA IHOLE ILIM INOTCH
IPILLR IPLATE ISEAM ISTIFF`），全部带 `IPFCOM`、全部在级联内，无一遗漏，
这一族没有问题。

**`IASLCO` 不在 `GTGEOM` 的级联里。** 反编译 `GTGEOM`（`Core3D.dll` `0x10341d2e`）
确认它依次调 `IPCOMP`/`IHCOMP` → `IFCOMP`/`IPFCOM`/`IECOMP`/`ICABCO`/`INCOMP`
→ `IG2COM`/`IGMCOM`/`INGCOM`/`ICCOMP` → `JSPCL`/`CRDESI`，**没有 `IASLCO`**。
`GTGEOM` 里另外硬编码的 noun 码（`NOZZ`/`ELCONN`/`EQUCOM`/`CTSUPP`/`PTSE`/`PTSS`
以及走 `CRDESI` 的 11 个）逐个核对过，**14 个目标 noun 一个都不在其中**。

所以 `HANDRA` 的处境很明确：**它自己不走 `GTGEOM`，但它是一个总成的根**。
调 `IASLCO` 的 5 个函数（`sub_1024F9F5` `sub_10251012` `sub_1025277E`
`sub_10254579` `sub_102556DE`）里，`sub_1025277E` 同时还调 `GTGEOM`、
`IPFCOM`、`ICABCO`——是遍历总成成员再逐个出几何的上层驱动。

另外两处硬编码名单也把 `HANDRA` 和有几何的结构件放在一起：

- `sub_10089BDC`（**`GTGEOM` 的调用者之一**）：`PJOI SJOI FIXING CMFI CMPF
  SBFI FITT PFIT STRFLT RLADDR SLADDR **HANDRA**`
- `sub_10081F15`：`SUBS SUBE SVOLM PLTFRM STRFLT STRLNG STRWEL **HANDRA**
  STWELD AIDGRO RLADDR SLADDR LADDER`

`RLADDR`/`SLADDR`/`LADDER`（梯子）、`PLTFRM`（平台）、`STRFLT`（结构板）
都是我们记账为有几何的 `Composite(Structural)`。

### 6-5.6 `LPRMTV` 反编译：core.dll 自己说「`TMPL` 的儿子就是图元」

`LPRMTV`（`core.dll` `0x561ce28`）解出来是这样（字段号已回填含义）：

```c
LPRMTV(noun):
    primitive = ATNLOG(noun, 字段 659518 /* primitive */)
    if (primitive && noun != WORL) return true
    owner = DGETF(字段 10206636)                  // 取属主
    if (NULREF(owner)) return false
    DGOTO(owner); ownerType = DGETI(字段 642215)  // 属主的类型
    return  ownerType == TMPL(779672)
        &&  noun != DDSE(643819)
        &&  noun != DPSE(644143)
        &&  noun != PORS(918961)
        &&  noun != LNKS(913827)
```

一句话：**「属主是 `TMPL`」这件事本身就让一个元素被算作图元**，
唯独 `DDSE`/`DPSE`/`PORS`/`LNKS` 四个被显式排除。

这段代码一次给了三个结论，而且都是 AVEVA 自己写的，不是我们推的：

1. `TMPL` 是**几何容器**，它的儿子是图元 —— 我们把 `TMPL` 的子图元照常建出来，
   方向是对的。
2. `DDSE`、`DPSE` 即使挂在 `TMPL` 底下也**明确不算图元** —— 这两个的
   「非图形数据」定性有了硬出处，不再靠推测。
3. `TMPL` 自己不在这张名单里（它是属主，不是图元），所以它本身不出形。

| `NBOX` 25302 | POS(0, 0, 4) XLEN 133.2 YLEN 203.2 ZLEN 8 | Z[0, 8]，**正好一个板厚** |

`NBOX` 的 `ZLEN` 与板厚严丝合缝、`NCYL` 的轴向长度刚好穿透板厚且 XY 落在板轮廓内
——这不是「碰巧挨着」，是**照着那块板配的孔**。四个 `NCYL` 是螺栓孔，`NBOX` 是腹板开口。

**结论：负体是正体的兄弟，扣的是同一个 `TMPL` 下的正体。** 这是本轮改法的判据，
不是推测。另外注意负体在成员表里**正体前后都有**，所以规则与文件顺序无关。

### 6-6.1 `NAPP` 属性：查了，不是兄弟选择器

两个负体都带 `NAPP`（`NCYL` = 7，`NBOX` = 4294967295 即 -1）。官方 XML 只写
`NAPPFLAG ( IN CATALOGUE )`，语义没展开。**但 25291 里正体只有一块 `PANE`**，
两个不同的 `NAPP` 值必须扣同一块板 —— 所以 `NAPP` 不可能是「扣哪个兄弟」的选择器。

全仓 `rg NAPP vendor/e3d-model` **零命中**：现有已过 RVM 对拍的负几何路径本来就不读它。
维持现状（不读），当作一条已知未决项记下，不在本轮扩大战线。

### 6-6.2 为什么不能简单地「让 `TMPL` 消费成员」

待办里原话是「要改成消费成员的类别」。**照字面改会把错误从看得见变成看不见。**

`pipeline::push_members` 里 `consumes_members()` 只决定**成员还入不入栈**：

```rust
let consumed = consumes
    && (matches!(member_category, Category::ProfileData) || member_category.is_negative());
if consumed { *report.consumed.entry(noun)... } else { batch.push(member); }
```

而真正把负体扣掉的是 `elmodl::model_element` → `collect_negatives(el)`，它收的是
**正体元素自己的成员**（外加直属 `CMPF` 里的深层负体）—— 一条**向下**的路径。

`TMPL` 底下负体是正体的**兄弟**，不在任何正体的子树里。所以只把 `TMPL` 改成
「消费成员」的结果是：1559 件负体从 `orphans`（看得见的欠账）挪进 `consumed`
（正常账），孔照样一个都不开，而报告从「1790 件孤儿」变成全绿。
**这比现在更糟**：现在至少孤儿账在喊。

### 6-6.3 选定改法：横向负几何作用域，而不是把 `TMPL` 做成一件聚合体

两条路：

| | 做法 | 判据 |
|---|---|---|
| **A 横向作用域**（选中） | `TMPL` 是容器：正体成员照旧各建各的**独立单元**，`TMPL` 的负体成员扣到这些正体上 | `LPRMTV`「属主是 `TMPL` 即算图元」= Core3D 把 `TMPL` 的孩子当图元逐个走；`elements.json` 的 RVM 主键本来就是 `CYLINDER n of TMPL …`，说明 E3D 侧也是一件件出 |
| B 聚合体 | `TMPL` 自己建一件 = 正体并集 − 负体并集，吃掉全部成员 | 会把 1385 件独立单元压成 147 件，**改掉 RVM 对拍主键与增量 Remove 的键**，且与上面两条证据相反 |

A 在数学上与「先并再减」等价：`⋃(Pᵢ − N) = (⋃Pᵢ) − N`，所以逐正体扣不会扣出别的形状。

**A 的两处代价，必须一起处理，否则是拆东墙补西墙：**

1. **基本体实例缓存**：`model_element` 里 `had_negative_members` 一旦为真就不给
   `primitive_instance`。`TMPL` 底下 617 个 `CYLI` 要是全部「有负体」，实例缓存整片失效
   （上一轮 `hits: 678`）。
2. **无谓的 CSG**：25164 那种 31 正体 × 2 负体 = 62 次布尔，其中绝大多数负体离正体十万八千里。

两条的解是同一个：**按包围盒先筛**——不相交的负体扣了也是恒等操作，跳过它不改变几何，
但能同时保住实例缓存和速度。筛选要带 `MANIFOLD_NUDGE_MM` 的让刀余量。

### 6-6.5 改法定稿

新增一个类别 `Category::PrimitiveContainer`，与 `RouteContainer` 同构
（自己不出几何、成员才是内容），语义是：

> 图元容器：成员里的正体各自成件、各建各的；成员里的负体**扣在这些正体兄弟身上**。

出处是 core.dll 的 `LPRMTV`——「属主是 `TMPL` 即算图元」，即 Core3D 把 `TMPL` 的孩子
当图元逐个走，`TMPL` 自己不是图元。

改动四处：

| 文件 | 改动 |
|---|---|
| `category.rs` | 加变体；`TMPL` 改判；`consumes_members()` 纳入；`build_disposition()` 归 `ProvenNonGraphic`；`is_model_unit()` 显式 false；`decision()` 证据串；回归测试 |
| `elmodl.rs` | `collect_negatives` 加一条**向上**的支路：属主是 `PrimitiveContainer` 时把属主的负体成员一并收进来 |
| `pipeline.rs` | 新类别的分支 + 新账 `primitive_containers`（`merge` 的解构会强制我处理它）+「容器有负体却无正体兄弟」的观察记录 |
| `docs/noun-coverage-matrix.md` | 基线同步 |

数学上 `⋃(Pᵢ − N) = (⋃Pᵢ) − N`，逐正体扣与先并再减同形，不会扣出别的东西。

**不做的事**：不加包围盒预筛。它能省掉「负体离正体十万八千里」的空布尔、也能保住
基本体实例缓存（上一轮 `hits: 678`），但那是**先猜性能再写代码**。先按最直白的写法跑一遍，
拿 `primitive-cache.json` 与耗时跟 20:51 的基线比，数字说要才加。

### 6-6.8 改判：`TMPL` 的负体是**宿主负体**，不是兄弟负体

> `TMPL` 底下的负体扣的是**容器之外的宿主**——水带箱扣的是墙、端板扣的是梁与被连接的构件
> ——而不是 `TMPL` 自己的正体成员。

于是原始待办那句「`TMPL` 判 `Unknown` 不消费成员是根因，正体照建但该开的孔全没开」
**前提就是错的**：那些孔本来就不开在 `TMPL` 自己的零件上。上一轮 §6-5.7 从
「1559 件负体成孤儿」直接推到「124 个立柱模板该开的孔没开」，中间那一步没有证据，
是我（RJYQ）上一轮下早了的结论。**这一轮把它推翻，账记在这里。**

真正的缺口比原来那笔大也更靠后：**我们的负几何模型只有「属主向下」一条路，
E3D 还有一条「构件在别处、洞开在宿主上」的路，整条都没有。** 那条要先解决
「怎么找到宿主」（`NAPP`？`FITT`/`STWALL` 的连接关系？还是 core.dll 里另有机制），
不是这一轮能收的。

### 6-6.9 本轮最终落地：保住分类，撤掉横向扣减，把负体单独立账

| 动作 | 结果 |
|---|---|
| `TMPL` 判 `PrimitiveContainer`（保留） | 370 件从 `Unknown` 下账；正体照旧各自成件，几何与 20:51 基线**逐件相同** |
| `collect_container_negatives`（撤销） | 不再拿宿主负体去扣兄弟，155 件误删复原 |
| 新账 `host_negatives` | 1559 件负体不再混在 `orphans`（语义是「数据或分类有问题」）里，也不许无声进 `consumed`，单开一本写明「宿主在容器之外，机制未实现」 |

这比 20:51 的状态严格更好：几何零变化、370 个 noun 有了名分、
1559 件负体从一个**名字不对**的账挪进一个**名字对**的账，且账仍然平。
